# Идея архитектуры системы учета сертификатов и лицензий КриптоПро

## 1. Статус решений и границы документа

Это архитектурная концепция для последующей реализации, а не отчет о работающей системе. Продуктовый Go-агент и бэкенд еще не реализованы. Стендовый прототип C#/PowerShell подтвердил WinAPI-механизмы; границы доказанного описаны в RESEARCH.md. Порядок реализации — IMPLEMENTATION_PLAN.md.

- **Согласовано** — прямо задано пользователем или подтверждено в ответах.
- **Предлагается** — проектное решение, выведенное из согласованных требований, но еще не проверенное реализацией.
- **Открыто** — механизм или деталь будут определены позже; агент-разработчик не должен считать их уже выбранными.
- **Подтверждено исследованием** — выполнена конкретная проверка на стенде; не означает поддержку всех версий и источников данных.
- **Технический выбор** — решение для реализации на основе требований и исследования, отдельно от формального требования кейсодержателя.

Актуальные уточнения этого документа заменяют более ранние гипотезы: СУБД — именно SQL Server 2019; агент обязан работать Windows-службой по новому ответу кейсодержателя; для проверенного локального физического MY-хранилища пользовательские подпроцессы не нужны: служба читает загруженные и временно подключенные незагруженные профили напрямую через WinAPI. Бэкенд — один portable `.exe` на 200+ машин, без обязательного балансировщика и нескольких экземпляров. Прочие требования TASK.md сохраняются. Требования кейсодержателей, пожелания и опциональные функции не становятся равнозначными из-за включения в архитектуру.

## 2. Цель и основные ограничения

**Согласовано:** система автоматически получает открытые сертификаты и сведения о лицензиях КриптоПро CSP 4/5 с рабочих станций, агрегирует их на сервере и показывает администратору. Пароли пользователей и закрытые ключи для сбора не нужны и не собираются. Участие владельца сертификата в обычном цикле работы не предполагается.

Текущая целевая ОС рабочей станции — Windows 10; Windows ниже 10 не поддерживается. Будущие цели — Astra Linux SE и ALT Рабочая станция. Полная кроссплатформенная реализация агента сейчас не требуется.

Охват пользователей выбирается в следующем порядке:

1. Актуальные данные всех доступных локальных профилей, включая пользователей без сеанса, если это реализуется с разумной сложностью.
2. Если актуальный сбор невошедших пользователей слишком сложен — последние результаты сбора, сделанного в их пользовательском контексте.
3. Если и такой вариант чрезмерно сложен — сбор только вошедших пользователей с явным указанием ограничения.

Исследование подтвердило вариант 1 для registry-backed MY на CSP 5.0.13003 и 4.0.9963: 3/3 сертификата незагруженного user1/user2 прочитаны LocalSystem-службой. Для этого источника fallback не используется как базовая реализация. Для непроверенных источников остаются явные статусы охвата и частичного результата. Давний или неполный результат нельзя выдавать за актуальный полный сбор.

## 3. Состав и размещение

| Компонент | Ответственность | Размещение |
| --- | --- | --- |
| Агент, Go | Идентификация машины, регистрация, получение конфигурации и заданий, сбор, локальная очередь, отправка, логи | Windows-служба на рабочей станции; установка из MSI |
| Бэкенд, Go | REST API, проверка подписей, конфигурация, задания, агрегация и сохранение, авторизация админа, раздача фронтенда | Отдельный сервер; обязан запускаться обычным `.exe` на Windows Server |
| Админка, Vue + Vite | Вход, машины, пользователи на машинах, сертификаты, лицензии, параметры сбора, ручные задания, конфликты регистрации | Браузер; собранные файлы встроены в бэкенд |
| SQL Server 2019 | Постоянное состояние единственного экземпляра бэкенда | Доступен бэкенду по сети; учетные данные предоставляются отдельно |
| Active Directory / GPO | Развертывание агента | Существующая доменная инфраструктура |

AD не является источником пользователей/машин системы и не участвует во входе в админку первой версии. Агент должен работать и вне домена: кейсодержатель запускает его вручную, далее он инициируется самостоятельно. Для локальных профилей источником сведений служит сама рабочая станция.

Бэкенд желательно размещать вне контроллера домена. VM, контейнер, ОС промышленного развертывания пока не выбраны. Linux-развертывание бэкенда допустимо как направление, но не заменяет обязательный запуск `.exe` на Windows Server. Windows Server 2019 пока рассматривается предварительно: пользователь ожидает подтверждения кейсодержателя. При следующем обсуждении требований к ОС вернуться к этому вопросу. Стенд фактически имеет Windows Server 2022 Standard build 20348 и SQL Server 2019 Express 15.0.2000.5 RTM. Это подтверждает состав стенда, но не утверждает Windows Server 2022 единственной целевой ОС. SQL Server 2019 остается обязательной СУБД.

## 4. Сетевые связи

| Инициатор | Получатель | Канал и назначение |
| --- | --- | --- |
| Браузер администратора | Бэкенд: административный порт | HTTPS: фронтенд и административный REST API |
| Агент | Бэкенд: агентский порт | HTTPS: регистрация, конфигурация, задания, отчеты |
| Бэкенд | SQL Server 2019 | Соединение с БД по заданным параметрам |
| Средства развертывания AD | Рабочая станция | Установка через GPO; отдельна от рабочего протокола агента |

**Согласовано:** административный и агентский API используют разные настраиваемые порты для независимых правил межсетевого экрана. Входящие сетевые порты на рабочих станциях не открываются. Сервер не подключается к агенту для запуска сканирования.

REST/HTTPS выбран для первой версии; gRPC и WebSocket сейчас не рассматриваются. Отдельный API интеграций и отдельный порт под него только предусматриваются архитектурно. Состав интеграционных методов пока не задан.

Порты, DNS-имена, выдача TLS-сертификата сервера и распространение доверия к нему открыты. Подпись агентского запроса дополняет HTTPS, не заменяет проверку сервера и шифрование канала. Публичная доступность в интернете не является требованием.

## 5. Регистрация и идентичность агента

### 5.1. Первый запуск

**Согласовано:** агент генерирует случайный UUID и пару ключей, сохраняет их локально и регистрирует UUID, hostname и публичный ключ подписанным запросом. Название UUID используется и в документации, и в протоколе; прежнее название идентификатора отменено. Бэкенд резервирует hostname. Проверка hostname → DNS-адреса → source IP соединения используется как согласованный доверительный сигнал; она не заменяет проверку подписи. При конфликте hostname уведомляется администратор. При переименовании машины агент меняет UUID. Алгоритм ключей — ECDSA P-256; нормализация имени и short name/FQDN пока открыты.

Публичный ключ позволяет проверить владение соответствующим приватным ключом. При автоматической первой регистрации это не является независимым подтверждением принадлежности машины организации; ручное одобрение или регистрационный код сейчас не согласованы и не добавляются как обязательный шаг.

| Ситуация | Согласованное поведение |
| --- | --- |
| Новый UUID и новая пара ключей | Зарегистрировать новую машину автоматически |
| Известный UUID и прежний публичный ключ | Повторная регистрация допустима и не создает дубль |
| Новый UUID и ранее использованные ключи | Допустить регистрацию для нового UUID; не переносить молча прежнюю машину и не объединять записи |
| Известный UUID и другой публичный ключ | Отклонить до разрешения администратора; прежний ключ автоматически не менять |
| Обнаружен конфликт UUID | Сообщить администратору; не объединять разные машины молча |
| Ключ потерян / агент переустановлен с новым ключом | Предусмотреть действие администратора для разрешения перепривязки |

Последняя колонка не задает точный интерфейс операции перепривязки. Ее аудит, отмена старого ключа и безопасный порядок подтверждения — детали реализации.

**Открыто:** одинаковые UUID и ключ у двух клонов невозможно надежно различить только по этим двум значениям. Нужны правила диагностики конфликтов, допустимых изменений оборудования и переустановки ОС. Уникальность публичного ключа между разными UUID не должна запрещать явно согласованный сценарий повторного использования ключей.

### 5.2. Последующие запросы

**Согласовано:** агент указывает UUID и hostname, подписывает `data` приватным ключом; сервер проверяет подпись по сохраненному публичному ключу. Формат конверта:

```text
{data: {}, sign: base64(sign(data)), host: {uuid: string, hostname: string}}
```

Это структура сообщения, а не выбранный криптографический алгоритм. **Согласовано:** UUID и hostname также находятся внутри подписанного `data`; бэкенд проверяет их совпадение с внешним `host`. Представление байтов `data` при подписании — UTF-8 канонического JSON JCS (RFC 8785). Утвержден ECDSA P-256 + SHA-256 с кодированием подписи ASN.1 DER и передачей DER-байтов в Base64; см. раздел 16.

**Утверждено:** защита от повторного воспроизведения через уникальный `request_id` внутри подписанного `data`. Временное окно и серверный challenge не выбраны и не вводятся как обязательные. Предлагается также включать метод и путь в подписанное `data` и сверять их с фактическим запросом. Повторная доставка результата должна быть идемпотентной на уровне бизнес-операции независимо от защиты транспорта от replay. Подробности — раздел 18.

Ключи и идентификатор должны переживать перезапуск и штатное обновление. **Утвержден DPAPI**; предлагается защищенный им файл с ACL. Для Windows-реализации выбран LocalSystem по результатам исследования; scope DPAPI еще нужно проверить и зафиксировать; альтернативы раздела 15 сохранены для обоснования. Приватный ключ не передается серверу и не включается в журналы. Стартовая конфигурация читается из файла, создаваемого GPO; он содержит адрес сервера. Путь и формат файла еще нужно выбрать. Для теста вне домена тот же файл должен создаваться вручную. HTTPS использует доверенные сертификаты ОС, без отключения проверки сертификата.

## 6. Цикл работы агента

1. Загрузить локальную идентичность и стартовые параметры; при первом запуске выполнить регистрацию.
2. Раз в **10 минут** обращаться к бэкенду за актуальностью конфигурации и ручными заданиями. Ошибки связи не должны требовать ручного восстановления в штатном сценарии.
3. Использовать кэширование конфигурации по хешу: при совпадении сохранять локальную версию, при изменении получить и применить новую. Точный протокол хеша и ответа без тела открыт.
4. Первый сбор выполнить **сразу после установки**, как только доступны необходимые параметры. Далее проверять срок сбора: период задается в админке как **n дней**, по умолчанию **1 день**. Локально учитывать время последнего соответствующего сбора.
5. При наступлении срока или получении ручного задания выполнить сбор, сформировать отчет с полнотой и временными метками, сохранить его в локальную очередь.
6. Хранить в устойчивой локальной очереди **не более двух последних элементов** и отправлять исходящим HTTPS-запросом. Подтвержденный отчет удалять после принятия сервером; при добавлении третьего неподтвержденного элемента старейший вытесняется по согласованному лимиту. Поэтому очередь не гарантирует доставку каждого исторического отчета при долгом отсутствии связи. **Утверждено:** частичный отчет не затирает последнее полное состояние необследованных профилей. При вытеснении элементов очереди нужно сохранять эту семантику; перенос ошибок/подтверждений заданий еще проектируется.
7. При недоступности сервера продолжать работу по последней принятой конфигурации и повторять отправку накопленных результатов после восстановления связи.

**Предлагается:** ограничить одновременные сканирования на одной машине, задавать уникальный ID отчета/задания, применять повторы с увеличением интервала и небольшим случайным сдвигом для распределения нагрузки. Эти механизмы не меняют согласованный базовый интервал проверки в 10 минут.

Кэш конфигурации не должен блокировать получение новых ручных заданий: задания проверяются даже при неизменном хеше. Отправка уже накопленного отчета не должна ждать следующего срока сбора через n дней.

Ручная команда не доставляется мгновенно: обычное ожидание — до следующего обращения агента, около 10 минут при доступной сети, плюс время обработки. При выключенной машине или отсутствии связи задержка не ограничена этим интервалом.

**Открыто:** области действия расписания, путь/формат стартового GPO-файла, ограничение размера отдельного элемента очереди, поведение при заполнении диска и разрешение старых заданий. Лимит количества элементов не ограничивает их суммарный размер в байтах.

## 7. Windows-служба и доступ к профилям

**Согласовано:** агент работает Windows-службой. **Технический выбор по исследованию:** LocalSystem, с отдельными Windows-адаптерами профилей, CryptoAPI и COM. Нет обязательного Планировщика, пользовательских фоновых процессов, сохранения паролей или запуска помощников под владельцами сертификатов.

Подтвержденный путь для локального физического MY:

1. Перечислить пользовательские профили и их SID/путь, исключить системные профили и машинные хранилища.
2. Для загруженного профиля открыть `HKU\SID\Software\Microsoft\SystemCertificates\My` read-only.
3. Для незагруженного профиля включить SeBackupPrivilege/SeRestorePrivilege, временно подключить NTUSER.DAT под собственным уникальным именем, открыть то же физическое хранилище read-only и перечислить DER через CryptoAPI.
4. Закрыть все handles, выгрузить только созданное агентом подключение. Пользовательские сертификаты и содержимое hive сборщик не изменяет.
5. Если профиль успел загрузиться, hive занят, поврежден или недоступен — повторить безопасный выбор источника либо вернуть частичный результат с причиной. Не объявлять такой профиль пустым.

Проверено настоящей SCM-службой в session 0 на .136 (CSP 5.0.13003) и .137 (4.0.9963), без пользовательского входа. Временная запись фикстур была только частью эксперимента; в продукте нет этапа добавления сертификатов в профили. Исследовательский прототип не превращается в runtime-зависимость от C#/PowerShell: реализацию перенести в Go через WinAPI/cgo-адаптеры.

Пользовательские подпроцессы могут рассматриваться позже только для доказанно недоступных иных источников. Наличие успешного чтения одного physical store не доказывает полноту всех логических/роуминговых хранилищ.

CLI — для установки/статуса/диагностики/удаления администратором, без участия в штатном цикле. MSI устанавливает EXE как службу; обновление сохраняет идентичность/состояние, удаление полностью очищает собственное локальное состояние. Повышение прав при установке не обходится скрыто.

## 8. Интеграция с КриптоПро и границы ОС

В `node_modules/cpro-go` находится локальный Go-модуль `cpro`, использующий cgo. В просмотренном коде:

- На Windows используются системные заголовки Windows/WinCrypt и библиотека `crypt32`.
- На Linux/macOS используются заголовки и библиотеки КриптоПро из `/opt/cprocsp`.
- Есть перечисление сертификатов MY текущего контекста и экспорт открытого сертификата DER/PEM.
- Публичная структура содержит отпечаток, CN, имя контейнера, ИНН и СНИЛС; требуемые серийный номер, УЦ и срок действия еще нужно получать/представлять в модели системы.
- В просмотренном исходном коде нет готового API проверки лицензии, версии установленного CSP и перечисления всех чужих профилей.

**Согласовано:** использовать SDK/API КриптоПро через имеющуюся Go-обертку, расширяя ее для недостающих сведений. В `node_modules` обнаружен исходный модуль `cpro-go`, а не полный комплект заголовков/дистрибутив SDK. Сама Go-обертка еще не проверена как продуктовый агент на Windows. WinAPI-доступ к незагруженным профилям и получение лицензий COM уже проверены отдельным прототипом; см. RESEARCH.md. Эти уровни доказательств нельзя смешивать. Криптографические операции подписи/шифрования из обертки не требуются для инвентаризации сертификатов.

**Предлагается:** отделить сбор сертификатов, чтение лицензии, перечисление/подключение профилей, управление жизненным циклом и локальное хранение за отдельными интерфейсами. Бэкенд не должен зависеть от установленного CSP или агентского cgo-слоя.

ОС-зависимые реализации выбирать при сборке/через адаптеры. Для не реализованных ОС предусмотреть явный отказ; пользователь допускает panic в заглушках неподдерживаемых платформ. Не распространять такой отказ на бэкенд и не подменять им обычные ошибки сбора. Отсутствие КриптоПро на поддерживаемой ОС — отчетное состояние, а не причина аварийно завершать весь агент.

Будущие Astra Linux SE и ALT не считаются поддержанными из-за наличия Linux-директив в обертке. Потребуется отдельно решить доступ к пользовательским данным, привилегии, упаковку и жизненный цикл демона.

## 9. Модель данных

**Согласованные основные сущности и связи:**

| Сущность | Содержание и связь |
| --- | --- |
| Рабочая машина | UUID, название и другие атрибуты; одна машина имеет много пользователей на этой машине |
| Пользователь на машине | Локальная сущность, принадлежащая одной рабочей машине; имеет много сертификатов |
| Сертификат | Одна общая запись сертификата; может быть связан со многими пользователями на разных машинах |
| Пользователь ↔ сертификат | Таблица связи many-to-many; через пользователя получается полный список машин сертификата |

Для сохранения связей при переименовании предлагается внутренний неизменный `machine_id` БД и отдельные UUID регистраций агента. Изменение UUID не переносит данные между независимыми машинами без подписанного перехода.

Пользователь на машине не равен глобальной записи человека в AD: один человек на двух ПК имеет две записи в контексте этих машин. **Предлагается** использовать SID как локальный идентификатор Windows-пользователя в паре с ID машины; общее представление пользователя не привязывать навсегда к Windows SID.

Предлагаемые вспомогательные сущности:

| Сущность | Назначение |
| --- | --- |
| Наблюдение / состояние связи | Источник, first_seen/last_seen, признак «больше не обнаружен», ссылка на результат сбора |
| Результат сбора | ID отчета, машина, время сбора и приема, обследованные профили/источники, полнота, ошибки |
| Состояние CSP и лицензии | Версия продукта/ядра, наличие ПО, тип client/server/unknown, состояние и срок лицензии, источник/сырой код; связь как минимум с машиной |
| Регистрация агента / ключ | UUID, публичный ключ, состояние допуска и история разрешенной перепривязки |
| Конфигурация | Версия/хеш и параметры, в том числе n дней |
| Задание сканирования | Целевая машина, состояние, ID и подтверждение выполнения |
| Администратор / сеанс | Локальный вход в админку и общее состояние сеансов |
| Событие изменения | Изменение сертификатов, связей, лицензии, конфликт UUID и действия администратора |

Таблицы являются проектным предложением, не готовой схемой из ТЗ. Точный состав ключей, типов и миграций определится при проектировании БД.

### 9.1. Дедупликация

**Утверждено:** технический идентификатор сертификата — SHA-256 его полного DER. Один и тот же сертификат на нескольких ПК и у нескольких пользователей имеет одну запись и разные связи. Серийный номер и издатель сохраняются как поля и используются для поиска. Совпадение номера у разных сертификатов не приводит к перезаписи или объединению.

Это явное уточнение прежнего правила исходного ТЗ о поиске только по серийному номеру. Время создания сохраняется, время обновления актуализируется. Хеш содержимого не означает проверку доверия, срока или отзыва сертификата.

### 9.2. Актуальность и исчезновение

**Согласовано:** хранить время последнего успешного сбора и полноту; исчезновение фиксировать только после полного успешного обследования соответствующей области. Ошибка чтения, недоступный профиль, невыполненный пользовательский сбор не означают отсутствие сертификатов.

Сертификат, больше не найденный у пользователя на машине, теряет активное наблюдение в этой области, но сохраняется в истории и может оставаться активным на других ПК. Для сохраненного пользовательского результата показывать исходное время сбора, а не время повторной отправки.

**Временно утверждено:** текущее состояние и события изменений, с метаданными сборов. Вопрос о глубине истории отправлен кейсодержателю; вернуться к нему после ответа. Полные снимки каждого сканирования пока не требуются; сроки хранения открыты. Отчеты, доставленные с задержкой, не должны откатывать более новое состояние; способ упорядочивания нужно определить вместе с форматом отчета.

**Утверждено:** системные/машинные хранилища сертификатов не обследуются; собираются только личные сертификаты и дополнительно сертификаты из `.cer`-файлов в папках, заданных в админке. Лицензия CSP остается отдельным состоянием, а не пользовательским сертификатом. Для `.cer` фиксировать источник и путь; если владелец локального профиля не установлен, не приписывать файл произвольному пользователю. **Технический выбор:** наблюдение сертификата содержит machine_id, тип/ключ источника, путь файла или SID/store и nullable-связь с пользователем. Обязательная связь user↔certificate сохраняется для пользовательских хранилищ; файл из общей папки не создает фиктивного пользователя. Владелец в Subject не отождествляется автоматически с локальной учетной записью.

## 10. Один экземпляр бэкенда и целевая нагрузка

**Согласовано новое уточнение:** один процесс portable `.exe` напрямую обслуживает **200+ рабочих станций**. Несколько экземпляров сервиса и распределитель запросов не входят в текущую схему. Ранее обсуждавшееся масштабирование несколькими процессами этим решением заменено.

Постоянные данные хранятся в SQL Server 2019. Процесс может иметь пулы соединений, кэши и выполняемые задачи в памяти, но после перезапуска должен восстанавливать конфигурацию, идентичность агентов, результаты и состояние заданий из устойчивого хранилища. Требование stateless ради балансировки между экземплярами больше не является необходимым условием первой версии.

**Предлагается:** конкурентная обработка запросов внутри одного Go-процесса, ограничение параллелизма тяжелых операций, индексы БД, транзакции и ограничения уникальности для защиты от повторной доставки. Отдельные Redis, брокер, reverse proxy, контейнер и балансировщик не обязательны для запуска.

Целевую производительность проверять на одном процессе: регистрация и опрос 200+ агентов, синхронный первый сбор, прием отчетов и работа админки. Интервал опроса 10 минут не исключает кратковременных всплесков. Параметры CPU/RAM, объем отчета и измеримые пределы задержки пока не заданы; нагрузочная способность еще не подтверждена тестом.

## 11. Фронтенд и административные операции

**Согласовано:** Vue + Vite; React и Angular не используются. Целевая сборка — один HTML, один CSS и один JS, встроенные в бинарник бэкенда. Отдельный Node.js-сервер для работы админки не требуется.

**Предлагается:** включать готовые статические файлы средствами Go embed и контролировать состав сборки. Шрифты, иконки и динамические импорты не должны незаметно добавлять обязательные внешние ресурсы или дополнительные чанки. Конкретная настройка Vite выбирается при реализации.

Вход — локальная учетная запись администратора на бэкенде, без AD. Администратора создают **непосредственно в БД**. Предлагается документировать SQL-процедуру внесения записи с корректным хешем пароля, не хранить пароль открытым текстом. Алгоритм хеша, способ получения совместимого хеша, сеансы и восстановление доступа открыты; регистрационный UI администратора не требуется. Секреты не встраиваются во фронтенд.

Основные экраны: машины и связь с агентами; пользователи машины; сертификаты и все места обнаружения; лицензии/версии CSP; время и полнота обследования; расписание n дней; постановка ручного задания и его статус; конфликты UUID и разрешенная администратором перепривязка ключа.

Проверка специальных расширений для внешних платформ и реестр должностных лиц не входят в согласованный объем. Токены и ИНН остаются опциональными по TASK.md.

## 12. Логи и эксплуатация

**Согласовано для агента:** файловые логи значимых событий и обязательно ошибок/аварийных сбоев; подробная запись каждого штатного действия не нужна. Временные метки — до миллисекунд по исходному ТЗ. Предварительный размер файла перед ротацией — **10 MB**.

Логи — обычные **`.txt`**, без сжатия и накопления архивов. **Утверждена ограниченная ротация:** `current.txt` и один `previous.txt`. По достижении 10 MB прежний `previous.txt` удаляется, текущий становится предыдущим, создается новый текущий. Точное значение MB и путь открыты. Ротация циклически удаляет старые файлы, а не бесконечно накапливает историю. Для Go требуется охват `error` и диагностируемых аварий; обещание записи абсолютно любого сбоя процесса, включая принудительное завершение ОС, не делается.

**Предлагается:** связывать записи с ID машины, задания и отчета; не писать приватные ключи, пароли и лишнее содержимое сертификатов. Ошибка одного профиля должна давать частичный результат с причиной, а не скрыто превращаться в пустой успешный отчет.

Правила серверных логов и резервного копирования БД нужно определить отдельно. Состав MSI, обновление через новый MSI/GPO (вне домена — вручную) и CLI/uninstall-оболочка штатного MSI-удаления утверждены; самообновление остается вне первой версии. Детали приведены в разделе 15.

## 15. Варианты для следующего согласования

Статус уточнен по последним ответам пользователя: UUID, DNS как доверительный сигнал, DPAPI, SHA-256 DER, состояние + события и MSI/GPO утверждены. Альтернативы ниже сохранены как обоснование выбора, а не как открытые решения.

### 15.1. UUID и hostname

**Утверждено:** случайный UUID создается при инициализации и сохраняется при штатном обновлении. При переименовании hostname UUID меняется. Это ID регистрации, а не аппаратный отпечаток.

Бэкенд резервирует hostname и сообщает администратору о конфликте. DNS-проверка соответствия hostname исходному IP соединения используется как доверительная. Предлагается положительным результатом считать наличие source IP среди A/AAAA-адресов имени. Нормализация IPv4/IPv6, DNS-кэш, при несовпадении или недоступном DNS принимается корректно подписанный отчет, отсутствие DNS-подтверждения отмечается и сообщается администратору (утверждено). В прямой схеме source IP берется из соединения, а не из присланного агентом заголовка.

При NAT/VPN адрес, видимый бэкенду, может не совпадать с DNS-адресом ПК; действует утвержденная политика отсутствия DNS-подтверждения без блокировки корректно подписанного отчета. Конфликт зарезервированного hostname показывается как ошибка конфликта администратору; владелец имени автоматически не перезаписывается.

Изменение UUID при переименовании должно регистрироваться подписанным запросом с прежней идентичностью, чтобы иметь возможность связать старую и новую регистрацию. **Утверждено:** смена UUID подтверждается прежней идентичностью, связи и история машины сохраняются. Освобождение/резервирование прежнего hostname и точную транзакцию еще нужно определить. Совпадение публичного ключа само по себе не должно автоматически объединять разные UUID.

### 15.2. Хранение ключа агента

Речь о собственном ключе транспортной идентичности агента, а не о закрытых ключах пользовательских сертификатов.

| Вариант | Преимущества | Компромисс |
| --- | --- | --- |
| Файл под ProgramData, права только службе/SYSTEM и администраторам | Самый простой; переносимая модель для будущего Linux | Ключ в файле не зашифрован; права доступа критичны |
| Такой же файл, ключ защищен DPAPI | Дополнительная защита при хранении, небольшой объем Windows-интеграции | User-scope зависит от учетной записи службы; machine-scope требует файловых ACL, поскольку сам по себе допускает расшифрование другими пользователями этой машины |
| Именованный ключ в Windows CNG KSP | Управление ключом через ОС, можно ограничить экспорт и доступ | Больше Windows-зависимого кода; выбор алгоритма должен соответствовать возможностям провайдера |
| Ключ в TPM через соответствующий KSP | Аппаратная привязка при наличии подходящего TPM | Требования к оборудованию и восстановлению, сложнее для тестового стенда; не предлагается как обязательный вариант первой версии |

**DPAPI утвержден.** Предлагаемое физическое хранение — файл с ACL; для выбранного LocalSystem предлагается user-scope DPAPI в контексте SYSTEM; подтвердить сохранение/чтение после перезапуска и MSI-обновления до фиксации scope. Для неизменной LocalSystem можно исследовать защиту в контексте этой учетной записи; при machine-scope ACL остаются обязательными. Запись в реестр сама по себе не заменяет ни ACL, ни защиту ключа. Защита от администратора, полностью контролирующего работающий ПК, этим решением не обещается.

Источники: [Microsoft DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata), [CNG Key Storage](https://learn.microsoft.com/en-us/windows/win32/seccng/key-storage-and-retrieval), [CNG KSP и TPM](https://learn.microsoft.com/en-us/windows/win32/seccertenroll/cng-key-storage-providers).

### 15.3. Одинаковые серийные номера сертификатов

| Вариант ключа | Поведение | Ограничение |
| --- | --- | --- |
| Только серийный номер | Ближе всего к буквальному исходному ТЗ | Разные сертификаты разных УЦ могут ошибочно объединиться; при несовпадении содержимого нужно сообщать конфликт |
| УЦ + серийный номер | Разделяет серийные номера разных издателей | Нужно строгое представление издателя; отображаемой строки имени УЦ недостаточно для всех случаев |
| SHA-256 от полного DER сертификата | Дедуплицирует именно один и тот же открытый сертификат на всех ПК | Изменяет буквальный ключ исходного ТЗ; серийный номер остается поисковым полем |
| SHA-256 DER + контроль УЦ/серийного номера | Один сертификат определяется по содержимому, спорные совпадения номера видны отдельно | Чуть больше логики; также требует согласовать уточнение исходного ТЗ |

**Утверждено:** SHA-256 полного DER как технический идентификатор; серийный номер и издатель — отдельные поля и индекс поиска. При совпадении DER связываются разные пользователи/ПК, при различии DER данные не перезаписываются молча. Это хеш содержимого, а не проверка доверия или подписи сертификата.

Основание: уникальность серийного номера задается в пределах выдающего УЦ, а не всех УЦ мира: [RFC 5280, раздел 4.1.2.2](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.1.2.2).

### 15.4. Что означает выбор глубины истории

Пример: 1 ноября у пользователя было три сертификата, 5 ноября один исчез, 7 ноября появилась новая лицензия.

- **Только текущее состояние:** видно, что есть сейчас; восстановить картину на 1 ноября нельзя.
- **Текущее состояние и события:** видно нынешний список и события «сертификат исчез», «лицензия изменилась». Повторный сбор без изменений не создает полный снимок. Рекомендуется для первой версии.
- **Все снимки:** каждый отчет хранится целиком, включая неизменившиеся данные. Проще просмотреть состояние на дату конкретного сбора, но больше данных и нужны сроки хранения.

**Временно утвержден вариант «текущее состояние + события»**. Вопрос отправлен кейсодержателю; вернуться после ответа. Лимит агентской очереди в два элемента отдельно означает, что при длительном отсутствии связи сервер в любом случае не получит каждый промежуточный снимок.

### 15.5. Состав MSI и удаление

**Утвержденный минимальный состав MSI:**

- Агентский EXE, регистрация Windows-службы, автоматический запуск и параметры восстановления после сбоя.
- Необходимые runtime-зависимости, только если их наличие подтвердит целевая сборка cgo. Заголовки и компилятор на рабочей станции не нужны.
- Каталоги состояния/очереди/логов с правами доступа. Ключ и ID создаются индивидуально на машине, никогда не включаются общими в MSI.
- CLI в том же EXE либо отдельная утилита для статуса, диагностики и вызова штатного удаления.
- Windows Installer-метаданные версии, обновления и удаления; краткая инструкция и пример GPO-конфига, который не перезаписывает управляемый GPO файл.

Не устанавливать и не обновлять КриптоПро самим MSI агента без отдельного согласования. Не добавлять входящих правил межсетевого экрана.

**Утверждено:** CLI/uninstall EXE служит оболочкой штатного Windows Installer-удаления продукта: остановить службу и вызвать согласованный uninstall, а не удалить EXE и оставить запись MSI. **Утверждено:** при удалении агент полностью удаляет свое локальное состояние, включая UUID, ключ, очередь и логи; при штатном обновлении идентичность и состояние сохраняются. Управляемый GPO конфиг и системные доверенные сертификаты ОС не являются собственным состоянием агента; их не удалять автоматически. Удаление не должно автоматически стирать историю машины на сервере.

### 15.6. Варианты обновления агента

1. **Новый MSI через GPO** — утвержденный основной путь для домена. Настроить upgrade-пакет, остановку службы, замену файлов, сохранение состояния и запуск. Обычный/major upgrade требует правильно описанного жизненного цикла пакета, а не просто перезаписи EXE.
2. **Ручной запуск нового MSI администратором** — утвержденный механизм для тестового ПК вне домена.
3. **Самообновление по команде бэкенда** — агент скачивает и проверяет пакет, отдельный помощник запускает установку и перезапускает службу. Дополнительны проверка издателя/целостности, восстановление после неудачи и защита от отката; сложнее, пока не предлагается для первой версии.
4. **Ручная замена EXE после остановки службы** — подходит для разработки, но обход жизненного цикла MSI может рассогласовать установленный продукт; не предлагается штатным обновлением.

Основа механизма MSI: [Microsoft — Major Upgrades](https://learn.microsoft.com/en-us/windows/win32/msi/major-upgrades). Конкретный инструмент сборки установщика пока не выбран.


## 16. Утвержденный алгоритм подписи запросов

**Утверждено пользователем:** ECDSA, кривая P-256, хеш SHA-256, кодирование подписи ASN.1 DER. Это ключ самого агента, независимый от пользовательских сертификатов и состояния лицензии CSP. Таблица ниже сохраняет рассмотренные альтернативы, но не отменяет выбранный вариант.

| Вариант | Преимущества | Компромисс |
| --- | --- | --- |
| Ed25519 | Стандартная библиотека Go, публичный ключ 32 байта, подпись 64 байта, одинаковый прикладной код на Windows/Linux | Не ГОСТ; нельзя выдавать за соответствие отдельным требованиям к сертифицированной криптографии |
| ECDSA P-256 + SHA-256 | Стандартная библиотека Go; подходит при будущей интеграции с соответствующим хранилищем ключей ОС | Нужно явно зафиксировать кодирование подписи и публичного ключа |
| RSA-PSS + SHA-256 | Стандартная библиотека Go, распространенный формат; например, RSA 3072 | Более крупные ключи/подписи; преимущества для данной задачи пока не выявлены |
| ГОСТ Р 34.10-2012 через CSP | Вариант при явном требовании заказчика использовать ГОСТ | Отдельный ключ/контейнер агента, зависимость от CSP и его лицензии; усложняется отчет об отсутствующем или неработающем CSP |

Порядок формирования подписи:

1. Канонизировать `data`, включающий UUID, hostname и request_id, по JCS (RFC 8785), получить UTF-8 байты.
2. Вычислить SHA-256 этих байтов.
3. Подписать хеш ключом ECDSA P-256, закодировав пару `(r, s)` в ASN.1 DER.
4. Передать `sign` как Base64 от DER-байтов подписи.
5. Бэкенд декодирует Base64, вычисляет SHA-256 того же представления `data`, проверяет DER-подпись и совпадение UUID/hostname с внешним `host`.

DER подписи и DER содержимого публичного ключа — разные структуры. **Утверждено:** публичный ключ передается как PEM `PUBLIC KEY` со SPKI DER внутри, `data` сериализуется JCS, от повторов защищает подписанный уникальный request_id. Подробности — раздел 18.

Подписание выполняется независимо от CSP: агент должен уметь сообщить об отсутствии КриптоПро. DPAPI защищает ключ при хранении. В Go выбранному формату соответствуют `ecdsa.SignASN1` и `ecdsa.VerifyASN1` над SHA-256-хешем.

Источники для первых трех вариантов: [Go Ed25519](https://pkg.go.dev/crypto/ed25519), [Go ECDSA](https://pkg.go.dev/crypto/ecdsa), [Go RSA/PSS](https://pkg.go.dev/crypto/rsa). Размеры приведены для Ed25519 до Base64.

## 17. Windows SDK/COM лицензирования и обязательный тип лицензии

**Новое обязательное требование пользователя:** учитывать тип лицензии **клиентская / серверная**. Тип не выводится из редакции Windows, названия рабочей станции, истечения срока или слов «пробная/постоянная».

В отчете/БД/UI разделить независимые признаки:

| Поле | Назначение |
| --- | --- |
| `license_kind` | client / server / unknown; дополнительное other допускается при ином документированном ответе API |
| `license_kind_raw`, `license_kind_source` | Сырой код/строка и использованный API, чтобы не терять данные при неизвестной классификации |
| `license_state` | valid / expired / not_installed / unknown / error — итоговая схема будет закреплена в контракте |
| `license_valid_to_raw`, `license_time_basis` | Дата API и известность часового пояса; не назначать UTC неуточненной COM-дате |
| `license_term_kind` | trial / time_limited / perpetual / unknown, только если это можно достоверно определить; не смешивать с client/server |
| `csp_product_version`, `csp_core_version` | Например, 5.0.13003 и 5.0.10013, а не версия произвольной DLL |

На Windows .136/.137 из LocalSystem подтверждены CPCSPLicense.CPCSPLicense.GetType/GetInstallDate/GetExpireDate. Для CSP 5 Product GUID `{50F91F80-D397-437C-B0C8-62128DE3B55E}`, для CSP 4 — `{407E5BA7-6406-40BF-A4DC-3654B8F584C1}`. Срок в обоих случаях — 14.02.2027; сырой GetType — 0 и 1 соответственно. Дополнительным независимым сопоставлением с SDK-флагом LICENSE_EXTRA_SERVER подтверждено для этих сборок: 0 — client, 1 — server. Сохранять сырой код/версию/источник; иные значения не угадывать.

Дополнительное исследование: на .136 документированный `CAdESCOM.CPLicense.Type()` вернул **Client**, то есть клиентскую лицензию. На .137 CAdESCOM отсутствует (Class not registered). Базовый путь CSP 4 подтвержден без плагина: CPCSPLicense.GetType=1 сопоставлен с SDK server-флагом. В Go использовать базовый COM, не вводить обязательную установку браузерного плагина; ошибки/новые значения обозначать unknown.

CAdES API является дополнительным доступным источником, а не универсально доказанной зависимостью на обоих стендах. Документация: [ICPLicense::Type](https://docs.cryptopro.ru/cades/reference/cadescom/cadescom_interface/icplicensetype). Полные результаты — RESEARCH.md, раздел 11. SDK-проверка номера лицензии здесь не заменяет Windows COM-срок: фактически обнаружено расхождение дат. Номер лицензии не должен передаваться бэкенду ради определения типа.

Найденные ранее на macOS license_get/license_check и PP_LICENSE/OID встроенной лицензии остаются материалом для будущих адаптеров. Не считать их Windows ABI доказанным. Встроенная лицензия сертификата и лицензия установки CSP — разные источники. SDK-компоненты сборщика не используются для собственной ECDSA-авторизации агента. Ни `license_set`, ни изменение лицензий в продуктовый сбор не входят.

## 18. Форматы публичного ключа, data и защита от повторов

### 18.1. Публичный ключ

**Утвержден PEM `PUBLIC KEY`.** Внутри PEM — DER SubjectPublicKeyInfo (SPKI), содержащий ECDSA-ключ P-256 и обозначение кривой. Это публичный ключ, не сертификат X.509 и не приватный ключ. Передается строкой в регистрационных данных; переносы строк кодируются обычными правилами JSON. Предлагаемое имя поля — `public_key`.

Бэкенд должен разобрать PEM/SPKI и проверить ожидаемый тип ключа и P-256. Сравнивать идентичность ключа следует по разобранному ключу/нормализованному SPKI, а не по пробелам и переносам PEM. В Go соответствуют MarshalPKIXPublicKey/ParsePKIXPublicKey и стандартное PEM-кодирование. Источник: [Go x509](https://pkg.go.dev/crypto/x509#MarshalPKIXPublicKey).

### 18.2. Каноническое data

**Утвержден JCS по RFC 8785.** Агент канонизирует объект `data`, вычисляет SHA-256 UTF-8-байтов JCS и подписывает хеш ECDSA P-256. Бэкенд канонизирует полученное `data` по тем же правилам и проверяет ASN.1 DER-подпись из Base64. Внешний host сверяется с подписанными UUID/hostname.

Нельзя считать произвольный json.Marshal реализацией JCS. Требуется совместимая реализация, отклонение повторяющихся имен свойств и соблюдение ограничений JCS на числа и строки. Предлагается UUID, серийные номера и даты передавать строками; не использовать числа JSON для больших идентификаторов. Конкретная схема полей пока проектируется.

Источник: [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html).

### 18.3. Уникальный request_id

**Утверждено:** каждый запрос содержит уникальный `request_id`, находящийся внутри подписанного `data`. Предлагается случайный UUID из криптографического генератора. UUID регистрации машины и request_id — разные идентификаторы.

Бэкенд после проверки подписи и области действия запроса атомарно регистрирует использованный ID в устойчивом хранилище SQL Server. Повторный ID в той же области отклоняется и не исполняет операцию повторно. Предлагаемая область уникальности — `(UUID регистрации, request_id)`; правила поколения регистрации при смене ключа/UUID следует уточнить.

Проверка наличия ID и его добавление должны быть защищены уникальным ограничением/транзакцией: два одновременных одинаковых запроса не должны оба пройти. Исполнение изменяющей операции и фиксация ID должны быть согласованы транзакционно, чтобы ошибка или падение не оставили неопределенное состояние. Реестр не может существовать только в памяти: перезапуск portable EXE не должен разрешать уже использованные запросы.

**Следствие выбранной схемы без временного окна:** старый неиспользованный подписанный запрос не становится недействительным только от возраста. Чтобы ранее принятый запрос не прошел заново, записи его ID нельзя удалять по произвольному TTL, пока соответствующая идентичность/ключ могут авторизовать этот запрос. Очистка возможна после надежного прекращения приема старой области регистрации либо после отдельно согласованного механизма срока действия. Это не вводит временное окно без согласования пользователя.

### 18.4. Повторы доставки отчетов

**Утверждено пользователем:** разделить идентификаторы:

- `request_id` — новый для каждой HTTP-попытки, защищен подписью.
- `report_id` — постоянный для одного результата сканирования, сохраняется при повторной доставке.

Если ответ потерян, агент формирует новый подписанный запрос с новым request_id и прежним report_id. Сервер не вносит отчет повторно, а возвращает результат уже принятой операции. Тот же report_id с другим содержимым должен давать конфликт. Сведения о времени фактического сбора остаются исходными, даже если отчет отправлен спустя несколько дней.

Идемпотентность report_id и защита от replay request_id решают разные задачи. Разделение ID и новый request_id на каждую попытку утверждены; срок хранения бизнес-дедупликации и детали ответов нужно определить при проектировании API; они не должны допускать повторное применение принятого отчета после очистки технических таблиц.
