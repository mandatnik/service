# Исследование стенда: КриптоПро, личные сертификаты и SQL Server

Дата: **2026-11-14**, часовой пояс пользователя Asia/Yekaterinburg (UTC+05:00).

## Итог

**На обеих рабочих станциях подтвержден сбор открытых личных сертификатов пользователя без сеанса из настоящей Windows-службы LocalSystem.** Для протестированного локального хранилища MY не понадобились пароль пользователя, вход в его сеанс или запуск пользовательского подпроцесса.

Также из службы получены сроки лицензий КриптоПро, уточнены версии продуктов до сборки и проверено сетевое подключение к SQL Server под предоставленной учетной записью.

Это экспериментальный прототип, а не реализация готового Go-агента. Положительный результат относится к указанному ниже физическому хранилищу и условиям стенда; универсальный охват всех вариантов хранения сертификатов пока не доказан.

На обеих машинах из службы созданы COM-объекты `CPCSPLicense.CPCSPLicense`; успешно вызваны `GetType`, `GetInstallDate` и `GetExpireDate` с GUID установленного продукта.

| GetInstallDate, как возвращено COM | 2026-11-13 13:41:50 | 2026-11-13 13:42:12 |

На момент проверки срок обеих лицензий не истек; получение лицензирующих сведений из службы работает. **В дополнительном эксперименте для этих сборок подтверждено: GetType=0 — клиентская, GetType=1 — серверная**; доказательства и границы — раздел 11. Эти коды не обозначают пробность или бессрочность. Эти вызовы сами по себе также не доказывают применимость лицензии к каждому сценарию использования и каждому сертификату.

Важное ограничение времени: COM вернул даты без часового пояса. ОС имеет `Ekaterinburg Standard Time` (+05:00). Поле `ExpireInterpretedUTC` в JSON вычислено *при предположении*, что COM-дата местная; это не независимое доказательство, что COM использует именно местное время. До проверки документации/интерфейса продукта не выдавать `2027-02-14T13:59:59Z` за окончательно подтвержденный срок в UTC. Дата окончания **14.02.2027** подтверждена непосредственно.

По новому требованию пользователя тип client/server должен присутствовать в отчете агента, БД и админке отдельно от срока действия и trial/perpetual. Определять его по Windows Client/Server нельзя.

Выполнена дополнительная read-only проверка из административного SSH-контекста HACK\agent (не повторный запуск SYSTEM-службы):

| .136, CSP 5.0.13003 | CAdESCOM.CPLicense.Type() | **Client — клиентская** |

Метод Type возвращает строку по документированному контракту: [ICPLicense::Type](https://docs.cryptopro.ru/cades/reference/cadescom/cadescom_interface/icplicensetype). Это независимый контроль, а не основание навязывать установку CAdES-плагина.

На предварительном этапе CSP 5 GetType=0 был сопоставлен с Client, а CSP 4 GetType=1 оставлен unknown. **Теперь эта неопределенность закрыта дополнительным SDK-сопоставлением: на .137 серверная лицензия; см. раздел 11.** Проверка не опиралась на тип Windows и не изменяла лицензию.

Серийные номера/ключи лицензий не извлекались и не сохранялись. Лицензии не устанавливались и не менялись. Встроенная лицензия сертификата в этом эксперименте не проверялась.

На Windows обнаружена `cplicmgmt.dll`, экспортирующая COM-входы, а не функции `license_get/license_check` из найденной ранее macOS-библиотеки. Не переносить macOS ABI на Windows без проверки. Возможный Go-путь — Windows COM-адаптер, без запуска PowerShell в продуктовой реализации.

Источник направления API: [ответ сотрудника КриптоПро о GetExpireDate/GetType](https://cryptopro.ru/forum2/default.aspx?g=posts&t=21285). Доказательства фактических вызовов — раздел Licenses отчетов служб.

## 4. Как проверяли именно службу и невошедшего пользователя

Использована временная **настоящая SCM-служба** `TelehackResearchProbe`, а не обычный административный SSH-процесс и не задача Планировщика.

- Оболочка на C#/.NET ServiceBase запускает диагностический PowerShell-процесс, наследующий контекст службы.
- В обоих отчетах подтверждены **NT AUTHORITY\SYSTEM**, SID **S-1-5-18**, **SessionID = 0**.
- В процессе включены `SeBackupPrivilege` и `SeRestorePrivilege`, необходимые для загрузки/выгрузки offline hive.
- На .136 выбран **C:\Users\user1**, SID `S-1-5-21-2458881001-951638917-3945708937-1106`.
- На .137 выбран **C:\Users\user2**, SID `S-1-5-21-2458881001-951638917-3945708937-1107`.
- Для обоих целей `Win32_UserProfile.Loaded = false` до записи фикстур, между этапами и после проверки. В пользовательские сеансы не входили.

На станциях одновременно могли быть другие активные или отключенные сеансы. Это не меняет факта отсутствия загруженного профиля у выбранных user1/user2. `Loaded=false` проверялось для конкретного SID, а не предполагалось из общего состояния машины.

### Контролируемые тестовые данные

До эксперимента у обоих выбранных пользователей физическое личное хранилище было пустым. Проверка пустого списка сама по себе ничего не доказывала бы, поэтому временно добавлены **только три открытых сертификата** из ранее выпущенного набора:

| Сертификат | Серийный номер, hex | Сценарий |
| --- | --- | --- |
| 01-individual-valid.cer | 02 | Действующий |
| 02-individual-expired.cer | 03 | Просроченный |
| 03-individual-future.cer | 04 | Еще не вступил в силу |

Корневой УЦ не устанавливался в доверенные хранилища. Закрытые ключи не переносились, не открывались и не использовались. Это тест извлечения открытых данных, не проверка подписи закрытым ключом.

### Последовательность

1. Служба определяет профиль по SID и пути через Win32_UserProfile.
2. Временно загружает **реальный NTUSER.DAT** выбранного невошедшего пользователя в отдельную ветку `HKU\TelehackResearch_<random>` через `reg load` (RegLoadKey).
3. Сохраняет исходный список сертификатов, добавляет три фикстуры через CryptoAPI `CertAddEncodedCertificateToStore`, закрывает handles и **выгружает hive**.
4. Повторно проверяет `Loaded=false`, заново загружает тот же hive. Таким образом проверяется чтение данных, реально сохраненных в профиле, а не оставшихся только в памяти первого store handle.
5. Открывает `Software\Microsoft\SystemCertificates\My` провайдером **CERT_STORE_PROV_REG** с **READONLY / OPEN_EXISTING**, перечисляет контексты через `CertEnumCertificatesInStore`.
6. Извлекает исходный DER, SHA-256, серийный номер, Subject, Issuer, NotBefore/NotAfter. Сравнивает SHA-256 с оригинальными .cer.
7. Удаляет только внесенные тестовые записи, проверяет возврат списка к исходному, закрывает handles и выгружает hive.

Читающий этап read-only; временное добавление/удаление фикстур выделено отдельно. Исходные сертификаты не перезаписывались.

## 6. Что это означает для агента и чего пока не доказано

Для протестированного локального физического MY-хранилища **можно делать актуальный сбор невошедших пользователей одной системной службой**, без ожидания их входа. Предварительно выбранный fallback на последние результаты/только вошедших пользователей для этого случая не нужен.

Предлагаемая реализация Windows-адаптера Go:

- Загруженный профиль: read-only доступ к MY через HKU\SID.
- Незагруженный профиль: временная загрузка NTUSER.DAT под уникальным именем, read-only CryptoAPI-перечисление и обязательная выгрузка в finally/defer.
- Собственное MY службы не использовать как замену хранилищам владельцев.
- Если пользователь вошел между проверкой и загрузкой либо hive заблокирован, повторить выбор источника/выдать частичный результат; не объявлять список пустым.

Ограничения и следующие проверки:

- В эксперименте подтвержден **registry-backed физический MY**. Дополнительные physical stores, файловое/роуминговое хранение, Group Policy, перенаправленные/зашифрованные профили и данные на отключенных токенах не проверены.
- Нет проверки закрытых ключей, PIN, наличия рабочего контейнера или встроенной лицензии сертификата. Они не требовались для чтения DER.
- Доверие цепочки и отзыв не проверялись; попадание в интервал дат не равно полной криптографической пригодности.
- На стенде проверены конкретные сборки CSP 4/5, не все релизы этих веток.
- Оболочка исследования написана на C# и PowerShell исключительно для быстрой проверки WinAPI; выбранный язык продукта Go не изменен. Реализация тех же вызовов в Go и интеграция с cpro-go еще не выполнены.
- Нужны обработка гонки входа пользователя, тайм-аутов, ошибок доступа и доказательство выгрузки при сбое. Успешная очистка прототипа не заменяет проверку всех аварийных сценариев продукта.

## 8. Очистка после эксперимента

На обеих рабочих станциях:

- Удалены три внесенных открытых сертификата; исходный список MY восстановлен.
- Выгружены временные ветки hive; оставшихся HKU\TelehackResearch_* нет.
- Остановлена и удалена временная SCM-служба TelehackResearchProbe.
- Удалены исследовательские каталоги C:\ProgramData\TelehackResearch-* с EXE, скриптами и копиями .cer.
- Корневые доверенные сертификаты, ключевые контейнеры, лицензии и существующие службы не менялись.

Финальная независимая проверка очистки: [cleanup .136](research/2026-11-14/136/cleanup-verification.json), [cleanup .137](research/2026-11-14/137/cleanup-verification.json). Целевые user1/user2 остались незагруженными.

При подготовке временного диагностического инструмента исправлены ошибки компиляции/кодировки и загрузки .NET-сборки. Неудачные запуски до основного теста не дошли до изменения сертификатов. Остатки этих попыток также удалены. В отчеты итогов включены успешные запуски с нулевым exit code.

## 9. Артефакты и воспроизводимость

- `tools/research/ServiceProbe.cs` — SCM-служба и native CryptoAPI/привилегии.
- `tools/research/probe.ps1` — получение версии/лицензии, тест offline-профиля, проверка и очистка фикстур.
- `tools/research/run-probe.py` — доставка, компиляция на стенде, запуск, получение доказательств и удаление временной службы/каталога. Использует готовое SSH-соединение, пароль не содержит.
- `research/2026-11-14/136/` и `137/` — JSON-отчеты и результаты очистки.
- `research/2026-11-14/provider-verification.json` — версии провайдера/csptest и COM-библиотеки.
- `research/2026-11-14/sql-connectivity.json` — санитизированные результаты SQL-подключения.

Не запускать прототип на произвольной рабочей машине без адаптации: он намеренно выбирает незагруженный тестовый user1/user2 и временно добавляет фикстуры. Это инструмент контролируемого стендового исследования, не готовый сборщик для эксплуатации.

## 11. Дополнительный эксперимент: тип лицензии CSP 4 без CAdES

**Результат:** установленная на .137 КриптоПро CSP **4.0.9963** определяется как **серверная**, базовый API возвращает `GetType = 1`. На .136 CSP **5.0.13003** — **клиентская**, `GetType = 0`. CAdES на .137 не устанавливался, регистрации DLL и лицензии не менялись.

### Независимое сопоставление

1. На Windows штатным `CPCSPLicense.CPCSPLicense.GetType(ProductGUID)` прочитан код типа. В предыдущем эксперименте тот же результат был получен из SYSTEM-службы, в этом — из административного SSH-сеанса.
2. Через CryptoAPI открывается контекст провайдера типа 80 с `CRYPT_VERIFYCONTEXT | CRYPT_SILENT`, без создания/открытия пользовательского ключевого контейнера.
3. `CryptGetProvParam(PP_LICENSE = 158)` возвращает данные установленного номера лицензии. Они передаются через SSH только в память проверяющего процесса, не печатаются и не записываются в файлы.
4. Установленная на текущем Mac SDK-библиотека `libcsplicense.dylib` выполняет read-only `license_check` этих данных. Она возвращает признаки лицензии отдельно от Windows COM.
5. В SDK-заголовке `/opt/cprocsp/include/cpcsp/license_api.h` явно определен `LICENSE_EXTRA_SERVER = 2`. У .137 получен этот флаг, а у .136 он отсутствует. Локальная контрольная клиентская лицензия Mac также не имеет server-флага. Ранее .136 дополнительно подтверждена строкой Client из документированного CAdESCOM API.

| Источник | .137, CSP 4.0.9963 | .136, CSP 5.0.13003 |
| --- | --- | --- |
| Windows CPCSPLicense.GetType | **1** | **0** |
| Результат вызова license_check | 0, вызов успешен | 0, вызов успешен |
| SDK pType, сырой код | 2 | 1 |
| SDK pExtra | 2 | 1 |
| pExtra & LICENSE_EXTRA_SERVER | **Да** | **Нет** |
| pExtra & LICENSE_EXTRA_DEMO | Нет | Да |
| Классификация client/server | **Server** | **Client** |
| Независимый CAdES Type | Компонент отсутствует | Client |

**Не путать перечисления:** COM GetType и SDK pType — разные поля с разными числовыми значениями. Число 1 означает Server в проверенном GetType, но pType=1 SDK встречается у Client. Признак demo в SDK pExtra также независим от server/client.

### Почему на CSP 4 получен Server, а на CSP 5 — Client

Подтверждено **различие конкретных лицензий на стенде**, а не правило «CSP 4 — серверная, CSP 5 — клиентская». Версия продукта, клиентский/серверный тип лицензии и версия/редакция Windows — независимые поля. Обе ветки CSP могут использовать разные лицензии; Windows 10 не является основанием подставлять client в результат учета.

Точная причина происхождения этих лицензий **не установлена**: не проверены история установки, ввод лицензии вручную, состав исходных дистрибутивов и эффективный временный режим. Различия демонстрационных лицензий в дистрибутивах — гипотеза для последующей проверки, не результат текущего эксперимента.

Наблюдаемые факты не доказывают общее объяснение происхождения:

- На .136 SDK прочитанного номера дал demo-флаг и отсутствие server-флага; Windows CAdES отдельно вернул Client.
- На .137 SDK прочитанного номера дал server-флаг, но **не** demo-флаг. Следовательно, утверждение «на .137 точно серверная демо-лицензия из дистрибутива» текущими данными не подтверждено.
- Windows COM и проверка закодированного номера через другой SDK возвращают разные сроки; нельзя автоматически отождествлять признаки номера, эффективное состояние установки и происхождение лицензии.

Для продукта происхождение не нужно угадывать: показывать подтвержденный client/server, отдельно срок/состояние и отдельно пробный/постоянный режим при наличии достоверного источника. Несовпадение типа лицензии и клиентской ОС не является само по себе ошибкой сбора или основанием менять установленную лицензию.

### Важное ограничение срока лицензии

Вызов `license_check` успешно разобрал номер, но вернул `pValidity = -1` для обоих Windows-образцов. Дата окончания закодированного номера — **2020-01-01T00:00:00Z** на CSP 4 и **2026-08-07T18:59:59Z** на CSP 5. При этом Windows COM по-прежнему возвращает **14.02.2027**, а контрольный AcquireContext ранее был успешен.

Это разные источники/семантика: математическая проверка переданного номера через другую версию SDK не равна проверке эффективного режима лицензирования текущей Windows-установки. Возможно участие временного режима/правил конкретной версии, но причина расхождения отдельно не доказана. **Не заменять Windows GetExpireDate результатом SDK и не объявлять Windows-установку неработоспособной по одному pValidity=-1.** В этом опыте SDK использован для независимого определения server-флага, а не как окончательный источник статуса/срока.

### Практическая реализация на Windows

Для проверенной CSP 4.0.9963 использовать базовый COM без CAdES:

```powershell
$license = New-Object -ComObject 'CPCSPLicense.CPCSPLicense'
$product = '{407E5BA7-6406-40BF-A4DC-3654B8F584C1}'
$rawType = $license.GetType($product)
$kind = switch ($rawType) {
    0 { 'client' }
    1 { 'server' }
    default { 'unknown' }
}
```

Для CSP 5 Product GUID другой, как указано в разделе 3; на проверенной 5.0.13003 сопоставление 0/1 совпадает. В Go нужен COM-вызов, сохранение rawType/версии/источника и unknown для ошибки или неподтвержденного нового значения. Постоянная зависимость агента от macOS SDK, перенос номера лицензии на бэкенд и установка CAdES для этой задачи не нужны.

Граница доказательства: соответствие проверено экспериментально на двух конкретных сборках; это не заменяет нормативный SDK-контракт для всех старых/будущих выпусков. Перенос в продуктовый Go-адаптер еще не сделан. Сроки, встроенная лицензия и пробность остаются отдельными признаками.
