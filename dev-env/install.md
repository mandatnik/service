# Мандатник: подготовка чистой Windows 10, сборка и тестовая установка

Эта инструкция получена из [DEPLOY.md](../DEPLOY.md) и адаптирована под новый
порядок первичной настройки: сначала инструменты, SQL и пустая БД, затем
консольный мастер бэкенда. Она предназначена для Миши и проверяющего,
который разворачивает отдельный стенд из исходников.

**Состояние на 15.11.2026:** мастер согласован в чате
[«Спроектировать первичную установку бэкенда»](codex://threads/01a1de18-f6ff-79f0-aa87-339ee8cedf37),
но в текущем `cmd/backend/main.go` команд `setup`/`configure` ещё нет.
Разделы 1–5 можно выполнять сейчас. Раздел 6 описывает согласованный сценарий
для сборки с реализованным мастером; он не означает, что мастер уже поставлен.
Если `help` не содержит `setup`, остановись перед разделом 6 и получи нужную
сборку. Старый ручной способ сохранён в корневом DEPLOY.md, но не заменяет
проверку нового мастера. Реализация самого мастера не входит в скрипт окружения.

## 1. Схема стенда и данные до начала установки

Для подготовки и сборки — **Windows 10 x64, 22H2**, актуальные обновления,
64-разрядный Windows PowerShell 5.1, локальный администратор и Интернет.
Для сервера ранее проверялся Windows Server 2022; установка всего стенда
на одной Windows 10 — вариант для разработки, который нужно отдельно проверить.
Сборочную машину, WS с backend/SQL и АРМ можно разделить. Домен для ручного
развёртывания не нужен, для GPO — нужен AD и тестовая OU.

До настройки запиши реальное DNS-имя или постоянный IP WS. **192.168.1.50 —
только пример**. Адрес в браузере, конфиге агента и SAN сертификата должен
совпадать. `0.0.0.0` — привязка слушателя, её нельзя сообщать клиентам как URL.

| Соединение | Предлагаемый TCP-порт | Источники |
| --- | --- | --- |
| АРМ → backend | 8443 | Сеть тестовых АРМ |
| Браузер → админка | 8444 | Машины администраторов |
| Внешняя система → интеграция | 8446 | Только доверенные системы, если используются |
| Backend → SQL | 1433 | Backend; локальный SQL не открывать наружу |

Для разработки скрипт готовит `C:\MandatnikDev`: `downloads` — загруженные
установщики, `logs` — журнал, `src` — место для исходников, `server` — место
поставки серверного EXE, `deploy` — MSI/публичный корень для переноса на АРМ.
Это рабочие каталоги администратора, а не окончательные каталоги службы.
Пути службы, защищённых настроек и ключей должен назначить мастер; не меняй
им ACL вручную после его работы.

Выбери **один** способ установки инструментов: раздел 2 или раздел 3.
Разделы 4–8 общие. На машине только с готовым агентом инструменты не нужны. Для проверки
лицензий отдельно установи КриптоПро CSP 4/5 и подходящую лицензию:
ни MSI агента, ни скрипт окружения их не содержат. Без CSP можно проверить
связь, установку и сбор сертификатов.

сборки ниже. Создай рабочие каталоги:

## 3. Вариант Б — подготовить окружение PowerShell-скриптом

Файл: [prepare-windows.ps1](prepare-windows.ps1). Скопируй полученную папку
`dev-env` на чистую Windows или распакуй архив исходников целиком. Git заранее
не требуется. Скрипт запускается с диска, не через вставку его текста в консоль.

Открой **64-разрядный Windows PowerShell от имени администратора**, перейди
в свою папку `dev-env`, затем выполни:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\prepare-windows.ps1
```

`Bypass` действует только для этого процесса. Доменные ограничения выполнения
скрипт не переопределяет. Он установит .NET Framework 4.8 при необходимости,
Chocolatey при отсутствии, Git, Go 1.26.3, Node 22.22.3, Make 4.4.1 и WiX
3.14.1; подготовит каталоги, сохранит системный PATH и WIX_DIR для новых сеансов и проверит инструменты.
Chocolatey и его пакеты устанавливаются с правами администратора из сети.
Проверки TLS, подписей Microsoft и контрольных сумм пакетного менеджера
не отключаются. Для архива WiX используется HTTPS-загрузка из релиза проекта;
SHA-256 загрузок записывается в журнал, это не независимая проверка издателя.

Журнал — `C:\MandatnikDev\logs\prepare-*.txt`, итог —
`C:\MandatnikDev\environment.json`. При ошибке скрипт прерывается; успешно
установленные инструменты сохраняются. Повторный запуск допустим: он не удаляет
исходники и не сбрасывает продуктовые данные. Неполный существующий каталог
WiX не перезаписывается — укажи новый `-WixDir` или восстанови его вручную.
При несовпадении уже установленной версии Go/Node скрипт остановится:
удаление/смена существующего инструмента остаётся явным действием администратора.

Если требуется перезагрузка, скрипт сообщает об этом и сам её не выполняет.
Перезагрузи Windows, открой новое окно и повтори нужный запуск. PATH OpenSSL/WiX и `WIX_DIR` сохраняются в системном окружении. Уже открытые
консоли не обновляются: открой новую через меню «Пуск», а если она ещё
получает старое окружение — выйди из учётной записи или перезагрузи Windows.
После этого в папке исходников достаточно `make build` без ручной настройки
PATH; для MSI можно выполнять `make package` без параметра WIX_DIR.

Дополнительные режимы:

```powershell
# Запустить установщик SQL Server 2019 Express и установить SSMS.
# SQL требует выбора параметров в открывшемся окне; это не тихая установка.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\prepare-windows.ps1 -InstallSqlExpress -InstallSSMS

# Проверить и собрать уже полученные полные исходники.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\prepare-windows.ps1 -SourcePath C:\MandatnikDev\src\mandatnik -Build
```

SQL запускается официальным bootstrapper Microsoft; выбери **Custom**, затем
Database Engine, экземпляр **SQLEXPRESS**, смешанный режим и администратора SQL.
Параметр `-InstallSqlExpress` рассчитан на машину без SQL; при существующей
SQL-службе он остановится, чтобы не создавать второй экземпляр. На повторном
запуске после установки убери этот параметр. SSMS ставится отдельным
официальным установщиком SSMS 22; его совместимость должна проверяться на
фактической версии Windows по [требованиям Microsoft](https://learn.microsoft.com/en-us/ssms/install/system-requirements).
Если текущий SSMS не поддерживает твою Windows, выбери поддерживаемую версию
SSMS вручную и не передавай `-InstallSSMS`.

Можно переопределить `-WorkRoot`, `-SourcePath`, `-WixDir`, `-GoVersion`,
`-NodeVersion`, `-MakeVersion`; для воспроизведения используй значения по умолчанию.
Без `-Build` скрипт не собирает код; при запуске внутри полного проекта
`SourcePath` по умолчанию — родительская папка `dev-env`. Если исходники
найдены, скрипт выдаёт текущему пользователю право изменения этой папки,
чтобы последующая сборка работала и в обычной консоли. `make check` с
Windows ACL-тестами по-прежнему запускай от администратора.

**После скрипта ещё нужны:** настройка SQL TCP, пустая БД и логин, DNS,
мастер приложения и сетевые правила. Скрипт не запрашивает `sa`/пароли,
не создаёт БД, конфиг backend, сертификаты и Windows-службу, не открывает порты
и не устанавливает CSP/агент. `environment.json` явно содержит
`backend_configured: false`, даже если инструменты успешно готовы.

## 4. Получить исходники и собрать EXE/MSI

Получи архив **согласованной ревизии** либо клонируй доступный репозиторий.
Адрес ниже внутренний: без маршрута к нашей сети используй переданную копию.
Если исходники уже распакованы в нужной папке, второй clone не выполняй.

```powershell
git clone http://10.10.26.11/pdoexception/telehack2026 C:\MandatnikDev\src\mandatnik
Set-Location C:\MandatnikDev\src\mandatnik
git rev-parse HEAD
```

Сохрани ревизию. Для архива сохрани его имя/дату. Корень проекта содержит
`go.mod` и `Makefile`. Выполняй по одной команде, при ошибке остановись:

```powershell
go mod download
if ($LASTEXITCODE -ne 0) { throw 'Не загружены зависимости' }
go mod verify
if ($LASTEXITCODE -ne 0) { throw 'Не прошла проверка зависимостей' }
make check
if ($LASTEXITCODE -ne 0) { throw 'Проверки не прошли' }
make package WIX_DIR=C:/Tools/wix314
if ($LASTEXITCODE -ne 0) { throw 'Сборка не завершилась' }
```

`make check` запускает unit-тесты и `go vet`, SQL не нужен. На Windows запускай
его от администратора: тесты используют ACL SYSTEM/Administrators, иначе
возможны `Access is denied` для журналов и DPAPI-файлов. Нельзя считать проверки
пройденными только потому, что удалось отдельно собрать EXE.

Без Make/Chocolatey вместо двух `make`-команд выполни:

```powershell
go run ./tools/build unit
if ($LASTEXITCODE -ne 0) { throw 'Unit-тесты не прошли' }
go run ./tools/build lint
if ($LASTEXITCODE -ne 0) { throw 'Статические проверки не прошли' }
go run ./tools/build frontend
if ($LASTEXITCODE -ne 0) { throw 'Не собрался интерфейс' }
go run ./tools/build build -out artifacts/ci
if ($LASTEXITCODE -ne 0) { throw 'Не собрались EXE' }
go run ./tools/build msi -out artifacts/ci -wix C:/Tools/wix314
if ($LASTEXITCODE -ne 0) { throw 'Не собрался MSI' }
```

`make package` включает `npm ci`, сборку Vue и встраивание интерфейса в EXE.
В `artifacts\ci` получишь `mandatnik-backend.exe`, `mandatnik-agent.exe`,
`mandatnik-acceptance.exe`, `MandatnikAgent-<версия>.msi`, `build-info.json`
и `SHA256SUMS`. Версия определяется кодом, не переименовывай старый MSI в новый.

```powershell
.\artifacts\ci\mandatnik-backend.exe version
.\artifacts\ci\mandatnik-backend.exe help
Get-FileHash .\artifacts\ci\*.exe, .\artifacts\ci\*.msi -Algorithm SHA256
Copy-Item .\artifacts\ci\mandatnik-backend.exe C:\MandatnikDev\server\
Copy-Item .\artifacts\ci\*.msi C:\MandatnikDev\deploy\
```

Для готовых файлов сравни SHA-256 с доверенным списком поставщика. Сохрани
`build-info.json` и ревизию. **Если в `help` нет `setup`, новый сценарий установки
ещё недоступен в этом EXE.** Получение более новой ветки/сборки согласуй
с поставщиком; наличие версии 0.5.0 само по себе не подтверждает наличие мастера.
Подробности сборки: [CONTRIBUTING.md](../CONTRIBUTING.md).

## 5. Подготовить SQL Server до мастера

Если SQL ещё нет, установи **SQL Server 2019 Express** через параметр скрипта
или [официальный установщик Microsoft](https://go.microsoft.com/fwlink/?linkid=866658).
Выбери Custom, Database Engine Services, экземпляр SQLEXPRESS, Mixed Mode,
добавь своего SQL-администратора. Данные SQL-администратора нужны только для
подготовки SQL, **мастер Мандатника не запрашивает `sa`**.
Для управления установи [SSMS](https://learn.microsoft.com/en-us/ssms/install/install)
или используй имеющуюся административную машину.

1. В `SQLServerManager15.msc` открой SQL Server Network Configuration →
   Protocols for SQLEXPRESS, включи TCP/IP.
2. В TCP/IP → IP Addresses → IPAll очисти TCP Dynamic Ports, задай TCP Port
   `1433`, проверь включение нужных IP и перезапусти SQL Server (SQLEXPRESS).
3. Проверь с машины backend:

```powershell
Test-NetConnection 127.0.0.1 -Port 1433
```

Для удалённого SQL замени адрес. Ожидается `TcpTestSucceeded: True`.
SQL Browser при явном TCP-порте не нужен.

Через SSMS с административными правами SQL:

1. **Databases → New Database**: создай **пустую** БД `Mandatnik`.
2. **Security → Logins → New Login**: создай `mandatnik_app`, SQL Server
   authentication, индивидуальный сильный пароль. Не требуй смены пароля при
   следующем входе; политику срока действия согласуй с администратором SQL.
3. **User Mapping**: выбери только `Mandatnik`, назначь `db_datareader`,
   `db_datawriter`, `db_ddladmin` для работы и миграций. `sysadmin` не выдавай.
4. Проверь вход под этим логином в `tcp:127.0.0.1,1433`, база `Mandatnik`.
   Таблицы вручную не создавай. Готовую БД с данными и ключами предыдущей
   установки нельзя использовать как пустую для новой установки.

**Подключение SQL:** для штатного варианта подготовь TLS-сертификат службы SQL,
доверенную цепочку и имя в SAN, назначь его через Configuration Manager,
предоставь службе SQL доступ к ключу и перезапусти её. См.
[настройку SQL TLS Microsoft](https://learn.microsoft.com/en-us/sql/database-engine/configure-windows/configure-sql-server-encryption).
Сертификат HTTPS Мандатника не заменяет сертификат SQL.

Согласованный мастер предлагает SQL TLS с проверкой имени/цепочки либо
**явное отключение требования шифрования** с предупреждением и подтверждением.
Если SQL принудительно требует шифрование, фактическое поведение зависит от
сервера/драйвера; выбор не обещает отсутствия TLS. Старый режим «шифровать,
но не проверять сертификат» в новую инструкцию не переносится.
В текущем коде до мастера второй режим не поддерживается — не редактируй
старый конфиг ради имитации нового сценария.

## 6. Первичная установка backend через мастер — после реализации

**Этот раздел — согласованный порядок, ожидающий реализации и Windows-проверки.**
Он заменяет ручное создание `backend.json`, OpenSSL-УЦ, `bootstrap`,
`license-init`, `admin-create` и задачу планировщика из старой инструкции.
Новый мастер сам должен сохранить конфигурацию, выполнить миграции,
создать ключи и суперадминистратора, зарегистрировать Windows-службу.

Подготовь до запуска:

- Клиентское имя/IP WS, привязки и порты, разрешённые сети.
- Адрес/порт SQL, имя **уже созданной пустой БД**, логин и пароль приложения;
  для SQL TLS — имя сервера и CA, если требуется.
- Имя, email и новый пароль первого суперадминистратора.
- Вариант HTTPS: свой УЦ мастера, импорт PFX/P12 либо PEM с ключом/цепочкой,
  или CSR для организационного УЦ Windows. Один публичный `.cer` без ключа
  не является готовым серверным комплектом.
- Защищённое место вне сервера для комплекта восстановления и пароля к нему.

Открой PowerShell администратора на WS и **только для EXE с `setup` в help**:

```powershell
Set-Location C:\MandatnikDev\server
.\mandatnik-backend.exe setup
```

Пройди шаги мастера:

1. **Адреса.** Простой режим — одно имя и один сертификат, разные порты;
   расширенный — отдельные адреса/сертификаты интерфейсов. Проверь DNS с АРМ.
2. **HTTPS.** При импорте мастер должен проверить ключ, срок, SAN всех адресов,
   назначение TLS-сервера и цепочку. При CSR передай запрос администратору УЦ,
   получи сертификат с Server Authentication и нужными SAN, верни его с цепочкой
   в мастер. При внешнем выпуске ключ должен соответствовать запросу; для
   импорта PFX заранее проверь возможность экспорта ключа из исходной системы.
3. **Свой УЦ.** Если выбран, сохрани публичный CA для машин и зашифрованный
   экспорт закрытого ключа отдельно. Удаление рабочей копии ключа УЦ на сервере
   подтверждай после успешного экспорта; серверные TLS-ключи службе нужны.
4. **БД.** Передай логин приложения, проверь режим TLS и результаты проверки
   подключения/прав. Мастер не должен устанавливать SQL или создавать БД/логин.
   Чужая непустая БД и старая установка требуют отдельного разбора/восстановления.
5. **Служба.** Предпочтительно отдельная локальная учётная запись со случайным
   паролем либо предоставленная существующая локальная запись. Не добавляй её
   в администраторы. Доступ к ключам/секретам должен назначить мастер.
6. **Суперадминистратор.** Введи имя, email и пароль с повтором скрытым вводом.
   Переменные окружения с паролями для штатной установки не нужны.
7. **Восстановление.** Сохрани зашифрованный комплект и проверь его успешный
   экспорт по результату мастера. Копия БД делается отдельно; ключ УЦ может
   выдаваться отдельным экспортом. Точные имена/состав файлов ждут реализации.
8. **Применение.** Проверь сводку без секретов, подтверди. Завершённой установка
   считается после старта службы и проверки SQL и настроенных HTTPS-интерфейсов.

После прерывания повторный `setup` должен предложить продолжение защищённого
черновика, а не незаметно заменить ключи. Повторный `setup` завершённой
установки должен направить в `configure`. Для старого конфига без маркера
готовности нужен документированный переход, не повторная инициализация.

Мастер должен выдать URL, фактическое имя службы, пути конфигурации/логов,
публичного CA и защищённых экспортов. **Не считать эти имена известными до
реализации.** Проверь, что служба читает секреты после перезагрузки; успешный
запуск из окна администратора этого не подтверждает.

DNS и firewall настраивает администратор. После мастера разреши предложенные
им порты для нужных источников. Например, если сохранились порты по умолчанию,
команды на WS (подсети замени на свои):

```powershell
New-NetFirewallRule -DisplayName 'Mandatnik agent HTTPS' -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8443 -RemoteAddress '192.168.1.0/24'
New-NetFirewallRule -DisplayName 'Mandatnik admin HTTPS' -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8444 -RemoteAddress '192.168.1.10'
```

8446 открывай отдельно только если используешь интеграцию. Входящих портов
на агенте нет. Корневой CA установи на WS/машину браузера/АРМ вручную или GPO;
в `LocalMachine\Root` импортируется публичный корневой сертификат, не ключ.
Открой **URL админки из итоговой сводки**, войди заданным email/паролем.

Для изменения настроек в согласованном сценарии используется
`mandatnik-backend.exe configure`, затем мастер перезапускает службу и проверяет
результат. При обычной перезагрузке повторять setup, выпуск ключей и создание
администратора не нужно. Имя команды локального восстановления суперадмина
не согласовано окончательно: используй `help` и документацию реализации,
не старый `admin-create` как безусловную замену операции восстановления.

## 7. Ручная установка агента на АРМ — основной быстрый путь

Скопируй на АРМ собранный MSI и публичный корневой CA, выданный мастером.
В примере его имя — `tls-ca.cer` (при другом имени поправь команду).
Папка поставки на АРМ — `C:\MandatnikDeploy`.
Не копируй туда серверные ключи и пароль SQL. Далее — PowerShell администратора
**на АРМ**, не на сервере:

```powershell
$AgentUrl = Read-Host 'Полный HTTPS URL агентского API из сводки мастера (например https://ws.example.test:8443)'
Import-Certificate -FilePath C:\MandatnikDeploy\tls-ca.cer -CertStoreLocation Cert:\LocalMachine\Root
New-Item -ItemType Directory -Force C:\ProgramData\Mandatnik | Out-Null
@{ server_url = $AgentUrl; request_timeout_seconds = 30 } | ConvertTo-Json | Set-Content -Encoding ascii C:\ProgramData\Mandatnik\agent-config.json

$AgentUri = [uri]$AgentUrl
Test-NetConnection $AgentUri.DnsSafeHost -Port $AgentUri.Port
$msi = 'C:\MandatnikDeploy\MandatnikAgent-0.5.0.msi'
$p = Start-Process msiexec.exe -ArgumentList "/i `"$msi`" /qn /norestart /l*v C:\MandatnikDeploy\install.log" -Wait -PassThru
$p.ExitCode
Get-Service MandatnikAgent
& 'C:\Program Files\Mandatnik\Agent\mandatnik-agent.exe' status
```

Путь MSI поправь под свою версию. Код 0 — успешная установка, 3010 — успешная
установка с требованием перезагрузки; остальные коды разбирай по `install.log`.
MSI запускает службу автоматически от LocalSystem. Если она остановлена,
проверь лог и выполни `Start-Service MandatnikAgent`.
Рабочий конфиг надо создать **до установки**: MSI содержит только пример.
Входящие порты на АРМ открывать не нужно — агент сам обращается к серверу.

### Альтернатива: установка из EXE без MSI

На чистом АРМ после установки корня и создания того же конфига можно поставить
службу непосредственно из EXE. Выбери один способ установки на одной машине:

```powershell
New-Item -ItemType Directory -Force 'C:\Program Files\Mandatnik\Agent' | Out-Null
Copy-Item C:\MandatnikDeploy\mandatnik-agent.exe 'C:\Program Files\Mandatnik\Agent\mandatnik-agent.exe'
& 'C:\Program Files\Mandatnik\Agent\mandatnik-agent.exe' install -config C:\ProgramData\Mandatnik\agent-config.json
& 'C:\Program Files\Mandatnik\Agent\mandatnik-agent.exe' start
& 'C:\Program Files\Mandatnik\Agent\mandatnik-agent.exe' status
```

EXE должен оставаться по этому пути: служба запускает именно его. Для проверки
поведения в реальной эксплуатации используй службу LocalSystem. Команда `run`
запускает процесс в контексте текущего пользователя и не заменяет эту проверку.

## 8. Альтернатива: раскатка через GPO

Нужна доменная тестовая OU с выбранными компьютерами. Сервер приложения при
этом не обязан быть контроллером домена.

1. Создай сетевую папку, например `\\FILESERVER\MandatnikDeploy`. Размести там
   MSI под именем **`MandatnikAgent.msi`** и `agent-config.json` из раздела 7.
   Компьютерным учётным записям тестовых АРМ нужны права чтения **и на шару,
   и NTFS**; запись оставь только администраторам развёртывания.
2. Создай отдельную GPO, привяжи к тестовой OU. Через **Computer Configuration
   → Policies → Windows Settings → Security Settings → Public Key Policies →
   Trusted Root Certification Authorities** импортируй только `tls-ca.cer`.
3. Возьми `..\deploy\gpo\install-mandatnik.ps1` и `install-mandatnik.cmd` из кода.
   В копии PS1 замени `$share` с `\\SERVER-WINDOWS\MandatnikDeploy` на свою шару.
4. В этой GPO открой **Computer Configuration → Policies → Windows Settings →
   Scripts (Startup/Shutdown) → Startup → Show Files**, скопируй туда оба
   скрипта и через **Add** добавь `install-mandatnik.cmd` как startup script.
   Настраивай через редактор GPO: он зарегистрирует нужное расширение и версии.
5. Для доступности шары при старте включи **Computer Configuration → Policies →
   Administrative Templates → System → Logon → Always wait for the network
   at computer startup and logon**.
6. На тестовом АРМ выполни `gpupdate /force` и перезагрузи его. Если корень ещё
   не успел примениться при первом старте, после применения политики перезапусти
   службу агента. Проверь `gpresult /r /scope computer`, службу и админку.

Скрипт копирует конфиг, ставит MSI, если EXE ещё нет, и запускает службу.
**Автоматическое обновление уже установленного EXE этот скрипт не выполняет**:
для upgrade запусти новый MSI отдельно. Он также не ставит CSP и сертификаты
пользователей. Держи исходный MSI доступным для Windows Installer repair.
Логи: `C:\ProgramData\Mandatnik\gpo-install.log`,
`C:\Windows\Temp\mandatnik-gpo-msi.log`, `mandatnik-gpo-wrapper.log` в той же Temp.
Подробности ручного формирования GPO: [deploy/gpo/README.md](../deploy/gpo/README.md).

## 9. Что проверить как проверяющий

1. В админке появился АРМ с правильным именем. Первый сбор идёт после
   регистрации; обновление статуса/задач по умолчанию опрашивается раз в 60 с.
2. В карточке видны результаты инвентаризации сертификатов и CSP (если он
   установлен), время последнего сбора и ошибки/неполнота сбора, если они есть.
3. Запусти ручной сбор из интерфейса и дождись завершения задания и новой даты
   отчёта. Плановый сбор по умолчанию раз в сутки — для проверки не надо ждать день.
4. Для проверки файлов `.cer` создай на АРМ папку `C:\MandatnikTestCerts`,
   скопируй туда выбранные публичные сертификаты из
   `test-data\certificates-2026-11-14`, создай в админке политику папок с правилом
   `C:/MandatnikTestCerts/`, назначь её машине или её группе и запусти новый сбор.
   Без назначенной политики агент папки не обходит. Ожидаемые данные сертификатов
   описаны в README/манифесте указанного набора.
5. Для проверки личного хранилища импортируй выбранный публичный `.cer` в
   `Cert:\CurrentUser\My` под тестовым пользователем, затем проверь сбор при
   входе и после выхода этого пользователя. Закрытые ключи для инвентаризации
   не нужны; тестовый ГОСТ-УЦ в доверенные корни устанавливать не надо.
6. Перезагрузи АРМ: служба должна подняться, карточка остаться той же.
   При включённой задаче сервера проверь и перезагрузку сервера.
7. Повтори установку/repair или обновление MSI: идентичность АРМ и история
   должны сохраниться. После обычного удаления и повторной установки тоже
   используется прежнее состояние.

Новая чистая установка с именем уже существующего АРМ может попасть в
**«АРМ → Ожидают подтверждения»**: подтверди замену в интерфейсе. Это ожидаемый
сценарий, а не повод удалять БД. Не копируй `ProgramData\Mandatnik\Agent`
с одной машины на другую и не клонируй уже зарегистрированный агент в шаблон VM.

## 10. Диагностика и повторный запуск

| Ошибка | Действие |
| --- | --- |
| Скрипт требует права/не запускается | 64-разрядный PowerShell администратора, команда с `-ExecutionPolicy Bypass -File`; доменную политику согласовать с администратором |
| Не загрузился инструмент/пакет | Проверить Интернет, доступ к Microsoft/GitHub/Chocolatey/Go/npm; не отключать проверку TLS или checksum. Лог в `C:\MandatnikDev\logs` |
| Не совпадает версия Go/Node | Проверить `Get-Command go.exe,node.exe -All`, версии и PATH; согласовать замену существующих инструментов |
| `Access is denied` в тестах агента | Выполнять проверки в повышенном окне; ACL продукта не ослаблять |
| `undefined: machineOffline` | Получить согласованную полную ревизию исходников; права администратора ошибку компиляции не исправляют |
| `unknown command "setup"` | Мастер отсутствует в EXE. Не продолжать новый сценарий; получить реализованную сборку |
| `ERR_CERT_COMMON_NAME_INVALID` | Имя/IP в URL отсутствует в SAN. Заменить сертификат через configure, не отключать проверку. Установка CA не исправляет SAN |
| `unknown authority` | Проверить доверие к цепочке на конкретной машине; корень для службы агента ставить в LocalMachine\Root |
| SQL недоступен | TCP/IP, фиксированный порт, служба SQL, firewall между backend и SQL, проверка SQL-логина и SAN SQL-сертификата |
| АРМ не появился | Полный URL агентского API, сеть, доверие TLS, служба, раздел ожидающих подтверждения |

Диагностика на АРМ:

```powershell
& 'C:\Program Files\Mandatnik\Agent\mandatnik-agent.exe' diag
Get-Content C:\ProgramData\Mandatnik\Agent\logs\current.txt -Tail 100
```

У backend используй фактическое имя службы и пути логов из завершённого
мастера. После обычной перезагрузки служба должна запуститься сама, email и
пароль администратора остаются прежними. Не создавай параллельную задачу
планировщика для того же backend и не запускай второй процесс на тех же портах.

Для разбора сохрани ревизию, build-info, шаг, код ошибки и нужный лог.
Не пересылай ключи, пароли, DPAPI-файлы или комплект восстановления.

## 11. Завершение теста и сохранение данных

Сначала отключи GPO-развёртывание на тестовом АРМ, если оно включено.
Обычное удаление сохраняет идентичность и состояние агента:

```powershell
& 'C:\Program Files\Mandatnik\Agent\mandatnik-agent.exe' uninstall
```

`uninstall -purge` используй только для намеренного полного сброса агента:
это удаляет ключи, очередь и журнал. Внешний конфиг остаётся.
Новая установка с тем же именем может требовать подтверждения в админке.

Backend останови через оснастку «Службы» по имени из мастера. Удаление
окружения/службы не заменяет резервного копирования: сохрани совместимую
копию БД, зашифрованный комплект восстановления и, если применимо, экспорт
ключа CA отдельно от публичного корня. После ротации ключей обновляй комплект.
Не удаляй ключи и БД ради обычного перезапуска.

## 12. Что подтверждено, а что ещё проверить на Windows

Инструкция сверена с существующими командами сборки и согласованным заданием
на мастер. Для остальных конфигураций нужно отдельно проверить подготовку на чистой
Windows 10 x64, необходимость перезагрузки и дополнительные режимы SQL/SSMS. Подготовка инструментов и повторный запуск скрипта проверены на WS1
(Windows 10 Enterprise 19045): в новом сеансе без настройки PATH успешно
выполнены `make build` и `make msi`, перезагрузка не потребовалась.
Подробности и границы проверки: [WS1-VERIFICATION.md](WS1-VERIFICATION.md).
Мастер, Windows-служба backend, его экспорты и восстановление ожидают реализации
и отдельной проверки; точные имена файлов/службы не подменены предположениями.
