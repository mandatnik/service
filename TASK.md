# Задача: модуль сбора данных о СКЗИ

## 1. Назначение и правила чтения

Этот файл представляет условия кейса №03 в структурированном виде для агента-разработчика. Текущий запрос пользователя состоит в подготовке этого файла; реализация приложения в рамках этого запроса не выполняется.

- Разделы 2-7 содержат актуальные требования из PDF с учетом ответов кейсодержателей и дополнительных договоренностей пользователя. Идентификаторы прежних требований сохранены; измененные требования имеют новый источник.
- Раздел 8 содержит проверяемые сценарии, выведенные из требований, а не отдельные правила организаторов.
- Раздел 9 перечисляет недостающие сведения и неоднозначности. Они не должны молча превращаться в подтвержденные требования.
- Англоязычные идентификаторы полей в этом файле служат для однозначных ссылок; это не предоставленная организаторами SQL-схема.
- Приоритет источников: явные договоренности пользователя, затем ответы кейсодержателей, затем исходный PDF. Согласованный Go заменяет требование C#/.NET Framework 4.5.
- Слова «Нужно ли» в заданных вопросах означали «Полезно ли будет», а не запрос на включение функции в обязательное ТЗ. Пожелания не становятся обязательными автоматически.
- Статусы: `required` - обязательное требование; `preferred` - желательная функция; `optional` - при наличии времени после основного ТЗ; `deferred` - отложено, обязательность не подтверждена; `out_of_scope` - не включать в текущий объем по ответам кейсодержателей; `open` - ответ или решение отсутствует.
- Примеры логов и исходного кода в PDF иллюстрируют оформление, а не задают бизнес-функции приложения.
- Раздел 10 фиксирует ответы на вопросы Q-001 - Q-009 и дополнительные договоренности AGR-001 - AGR-003. Другие вопросы остаются без ответа; список из ранее предложенных 100 вопросов не является согласованным ТЗ.

## 2. Цель

Разработать ПО с панелью управления, позволяющее пользователю сканировать указанные им ПК в локальной сети, собирать сведения обо всех установленных на них личных сертификатах и версии установленного КриптоПро, разбирать сертификаты и сохранять полученные данные в таблицу MSSQL. Источник: страница 2.

По уточнениям приоритет - получать сведения о сертификатах без беспокойства их владельцев, видеть серийный номер и дату окончания действия, проверять статус лицензий КриптоПро CSP 4 и 5. Один сертификат учитывать один раз, сохраняя все ПК, на которых он обнаружен. Источник: Q-001, Q-004, Q-008, Q-009.

Кейсодержатели планируют проверять решение на домашних ПК вне сети предприятия. Это ограничивает проверку инфраструктурных функций, в частности отзыва сертификатов; базовое требование сканирования указанных ПК не отменено. Источник: Q-002, Q-003.

Точные SQL-типы и перечень статусов лицензии не согласованы. Отсутствие КриптоПро, истекшая лицензия и невозможность определить статус - разные состояния; конкретную модель состояний требуется определить отдельно.

Логика сохранения, нормализованная из пунктов 4-4.2:

```text
получить результаты сканирования и парсинга
если целевая таблица отсутствует:
    создать целевую таблицу
для каждого сертификата:
    найти существующую строку по серийному номеру
    если строка отсутствует:
        внести данные сертификата
        задать дату/время первоначального внесения
        задать дату/время обновления равными дате/времени внесения
    иначе:
        актуализировать данные существующей строки
        актуализировать дату/время обновления
        сохранить дату/время первоначального внесения
        не добавлять дубликат
    добавить связь сертификата с текущим ПК, если ее еще нет
    сохранить ранее обнаруженные связи с другими ПК
сохранить результаты определения версии КриптоПро и статуса лицензии по ПК
```

Сохранение первоначальной даты при обновлении следует из назначения поля «Дата и время внесения»; отдельной формулировки об этом в PDF нет.

- [ ] AC-007: При первом внесении сертификата `created_at` и `updated_at` равны. Покрывает DB-007.
- [ ] AC-008: При повторном внесении сертификата с тем же серийным номером обновляется существующая строка и время обновления; количество строк с этим номером остается равным одному. Покрывает DB-004 - DB-006.
- [ ] AC-009: Ошибки и исключения попадают в файл логов; каждая запись содержит дату и время до миллисекунд. Покрывает LOG-001 - LOG-004.
- [ ] AC-010: Исходный код соответствует требованиям к комментариям, именам, пробелам и табуляции. Покрывает CODE-001 - CODE-004.
- [ ] AC-011: На ПК с КриптоПро CSP 4 и на ПК с CSP 5 определяются версия ПО и статус лицензии, включая истекшую лицензию. Покрывает TECH-004, FUNC-008, DATA-010, DATA-011.
- [ ] AC-012: Для сертификата доступны серийный номер и дата окончания действия. Покрывает FUNC-009, DATA-008.
- [ ] AC-013: Один сертификат, найденный на двух ПК, представлен одной записью с обеими машинами; повторное сканирование не создает дубль сертификата или связи с ПК. Покрывает FUNC-010, DB-008, DATA-009; отсутствие дублей связей - производная проверка.

Проверки желательных функций, если они реализованы; не являются обязательными условиями приемки исходного ТЗ:

- [ ] AC-P01: После сканирования администратор видит всплывающее уведомление об отсутствии КриптоПро или истекшей лицензии. Покрывает EXTRA-001.
- [ ] AC-P02: Формируется `.msi`, устанавливающий компонент как службу Windows. Покрывает TECH-005.
- [ ] AC-P03: Общая логика отделена от Windows-зависимых компонентов; описано, какие адаптеры потребуются для Linux-демона. Покрывает TECH-006; способ проверки - проектная интерпретация.

Функции EXTRA-002 и EXTRA-004 проверяются отдельно при их реализации и наличии тестовых материалов. Невозможность проверки в инфраструктуре кейсодержателя не считается подтверждением корректности. Набор обязательных статусов лицензий сверх истечения срока пока не согласован.
