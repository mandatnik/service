# «Мандатник» — итоговый отчёт о полном тестировании

- Дата кампании: 2026-11-15, 05:45–09:30+ (по времени рабочей станции).
- Объект: продукт «Мандатник» (Telehack 2026), версия 0.5.0, HEAD `85762a2`.
- Полигон: изолированный тестовый инстанс на реальном стенде
  `192.168.189.138` (Windows Server 2022 + SQL Server 2019 Express) и
  `192.168.189.136` (Windows 10, КриптоПро CSP 5.0.13003).
- Метод: 30 автономных сабагентов (волнами), black-box + white-box,
  деструктивные проверки с откатом, полный авторизованный пентест,
  нагрузка 350 клиентов-агентов, фиксация доказательств.

> В отчёте намеренно нет паролей, токенов, приватных ключей и полных
> серийных номеров лицензий. Все секреты остаются в `.secrets/`.

## 1. Резюме

Кампания покрыла 30 зон: протокол агента, админку и её API, интеграционный
API, TLS, UI в трёх браузерах, установку/MSI/GPO, сбор с профилей и папок,
разбор сертификатов и лицензий, сетевые и серверные отказы, целостность БД,
изоляцию инстансов, длительную работу и нагрузку 350 клиентов-агентов.

Главное:

- **Найдено и исправлено 3 critical + 5 high.** Критичные: потеря всех личных
  сертификатов профиля из-за элемента КриптоПро (F-01), падение всего отчёта
  на одном битом сертификате (F-15) и реальный серийный номер лицензии в
  репозитории (F-14). High: CPU-DoS через JCS (F-02), сломанный список задач
  (F-03), «отравленный» сертификат, навсегда блокирующий инвентаризацию
  (F-26), и старый `uninstall`, уничтожавший identity (F-28, в HEAD уже
  исправлен); переиспользование ключа identity (F-04) — medium/high.
- **Каждый critical/high проверен на стенде после фикса** (E2E, повторные
  замеры, независимая перепроверка зоной 26). Для F-04 дополнительно закрыт
  обход через `/register`.
- **Стенд изолирован и восстановлен:** рабочие `:8443/:8444/:8446`, БД
  `Telehack2026` и служба `TelehackAgent` не пострадали; тестовый контур
  удалён, старый агент отчитывается.
- **Остаточные риски:** серийник лицензии остаётся в истории git и на
  `main` (нужен отзыв/перевыпуск); pre-auth обработка 16 МиБ тела отчёта
  всё ещё даёт ~1.5–2 с CPU (F-02 исправлен частично); регистрация остаётся
  trust-on-first-use по проекту; часть low/medium не исправлялась сознательно.

### 5.2. Детали critical/high

#### F-01 — Critical: потеря личных сертификатов (зона 15/сбор)

На WS1 в профиле `HACK\mimbol` лежали два реальных личных сертификата:
обычный v3-элемент и элемент контейнера КриптоПро (TLV-заголовок 300 байт,
далее DER, имя файла = SHA-1(DER)). Агент поддерживал только v3 и raw DER,
поэтому падал на втором элементе, а коллектор отбрасывал **все** записи
профиля при любой ошибке источника. Итог: `partial`, 0 сертификатов,
бесконечная ошибка `unsupported file-store element format`.

Исправление: разбор встроенного DER по SHA-1 имени файла + сохранение
успешно прочитанных сертификатов при `partial`. После пересборки:
`complete`, 2 сертификата, 0 ошибок. Персональные данные в отчёт не
включены; в evidence — только структура заголовка и хэши.

#### F-02 — High: CPU-DoS на JCS (зона 12)

`register/report` канонизировали `data` до проверки подписи. Один объект с
20 000 ключей (318 КБ) занимал секунды CPU; 8–16 МиБ — минуты, а 64 слота
лимитера выбивали админку. Исправление: линейный бюджет формы JSON
(≤512 членов на объект, глубина ≤64) до канонизации + лимит 1 МиБ для
не-report тел. E2E: 318 КБ/20 000 ключей → `400 invalid_envelope` за
~0.10 с (включая TLS), три повтора стабильны.

#### F-03 — High: список задач (зона 11)

`task_id` (UNIQUEIDENTIFIER) сканировался в `string`, ключи карты не
совпадали, все задачи отображались `failed`, `counts.total=0`. Исправлено
сканирование в `mssql.UniqueIdentifier`; тот же паттерн — в
`ResolveLicenseSerial`. После фикса: `state=completed`, `counts.succeeded=1`,
фильтр `state=queued` отдаёт `items:[]`, а не `null`.

#### F-04 — Medium/High: повторное использование ключа (зона 10)

`rebind` не проверял, что ключ уже активен на другой регистрации; один
приватный ключ аутентифицировал две identity (`sync` 200/200). Добавлена
проверка уникальности в транзакции. Проверка воспроизведением — в зоне 26
(ожидается 422).

#### F-14 — Critical: реальный серийник лицензии в git (зона 17)

Полный 25-символьный серийный номер действующей лицензии КриптоПро был
в `internal/protocol/license_test.go`, `docs/acceptance/INTEGRATION-API-0.5.0.md`,
OpenAPI и `.deploy`-копиях; SHA-256 совпал с ProductID на WS1. Заменён
синтетическим во всех рабочих файлах, тест и примеры обновлены.
**Остаточный риск:** значение остаётся в истории git (коммиты `db38f50`,
`5924602`) и, вероятно, на Gitea; нужен отзыв/перевыпуск лицензии и
согласованная очистка истории.

#### F-15 — Critical: 500 на отчёте с битым сертификатом (зона 01)

Сертификат с `parse_error` приводил к `500 database_error "upsert certificate"`:
`issuerHash` был `nil` (`any`), драйвер объявлял параметр `nvarchar`, а
`MERGE` в `BINARY(32)` падал. Исправлено `CAST(@p7 AS VARBINARY(32))`.
Проверка: собственный repro (регистрация + отчёт с битым DER и
`parse_error`) — до фикса 500, после `200 accepted applied=true`.

## 6. Нагрузка 350 клиентов-агентов

### 6.1. Методика

Нагрузка выполнялась отдельной стадией после функциональных тестов, чтобы
не искажать их результаты. Генератор `loadgen` (Go, `internal/protocol`)
создаёт 350 независимых identity с ECDSA P-256, регистрируется на :8543,
затем в цикле выполняет `sync` и `report` с реалистичным конвертом
(`status=complete`, CSP отсутствует, пустые источники). Рампа — 10 минут,
удержание — 15 минут, опрос каждого клиента — 60 секунд. Параллельно на
`.138` снимались CPU, свободная память, RSS/потоки/handles backend,
установленные TCP-соединения, размер БД и число отчётов/машин (CSV каждые
5 секунд).

### 6.2. Результаты

| Метрика | Значение |
| --- | --- |
| Клиентов зарегистрировано | **350 / 350** |
| Машин в БД после | 368 (18 до нагрузки) |
| Отчётов принято | ~5657 |
| `report` p50 / p95 / p99 / max | 23 мс / **54 мс** / 264 мс / 8.9 с |
| `sync` p50 / p95 / p99 / max | 24 мс / **2049 мс** / 2223 мс / 4.4 с |
| `register` p50 / p95 / p99 / max | 2075 мс / 2232 мс / 11.6 с / 14.9 с |
| Ошибки генератора | 8 / 5600 (`internal_error` = 503) — **0.14%** |
| 5xx в логе backend | 8 × 503 (report), 500/panic — 0 |
| CPU `.138` (пик) | 52.4% |
| Свободная память (мин) | 441 МБ |
| Backend RSS / threads / handles (пик) | 34 МБ / 22 / 666 |
| TCP-соединений на :8543 (пик) | 351 |
| Админка во время удержания (p95) | overview 153 мс, machines 154–228 мс |
| `/healthz` | 200 всё время, кроме окон тестов зоны 19 |

Регистрация ~2 с на клиента — это DNS-проверка имени синтетического
клиента (`LOAD350-*` не разрешаются), а не обработка БД. Всплеск `sync`
p95 ≈ 2 с объясняется синхронным опросом всех клиентов раз в 60 с без
джиттера; реальный агент добавляет ±10%, поэтому в бою пик будет ниже.
8 отказов 503 — мгновенный load-shedding при переполнении
`max_concurrent_reports`; реальный агент повторяет отчёт (идемпотентно),
генератор — нет, поэтому они попали в ошибки.

### 6.3. Выводы

- 350 клиентов-агентов обслуживаются одним backend-процессом на SQL Server
  Express без деградации админки до неприемлемых значений: p95 отчёта 54 мс,
  админка ≤ 230 мс.
- Узкое место — синхронные всплески `sync` (p95 ~2 с) и отсутствие
  Retry-After у 503. Рекомендации: джиттер опроса на стороне агента уже есть,
  добавить `Retry-After` и, при необходимости, очередь вместо мгновенного
  503; регистрацию можно ускорить, не блокируя ответ на DNS-проверку.
- Утечек памяти за 25 минут не видно (RSS 16→34 МБ, handles 230→666,
  после нагрузки стабилизируются); длительный soak — зона 23.
- Нагрузка не выявила потери данных: все 350 identity зарегистрированы,
  отчёты идемпотентны, БД консистентна.

## 10. Ограничения и честные границы

- **WS2 (`.137`) выключена.** Сценарии с CSP 4.0 и второй рабочей станцией
  проверялись только кодом/юнит-тестами и через офлайн-имитацию; живой
  прогон на `.137` невозможен без включения машины.
- **Реальный токен Rutoken не подключался** (по решению заказчика), поэтому
  сценарии с физическим носителем и приватным ключом на токене не входили
  в кампанию.
- **Реальная активация лицензий КриптоПро не выполнялась.** Проверялись
  чтение, маскирование, пулы, preview и откат; расход реальных серийников
  исключён.
- **GPO/AD** — только в объёме, который разрешали доступные инструменты;
  если RSAT/GPMC отсутствовали, сценарий помечен BLOCKED, а не «пройден».
- **Нагрузка 350** использовала синтетические отчёты без реальных
  сертификатов; это проверка пропускной способности и устойчивости, а не
  P11-SLA на 200+ реальных АРМ. SQL Server Express — общий стенд.
- **Изоляция тестового контура** была логической (отдельные БД, порты,
  каталоги, задачи), но не привилегированной: оба backend'а и оба агента
  работают как SYSTEM, тестовый TLS-сертификат совпадает с рабочим. Это
  артефакт схемы, а не дефект продукта; отмечено в F-11/F-12.
- **Персональные данные** сертификатов (субъекты, серийники) в отчёт и
  публичные доказательства не включались; в evidence остались структуры,
  хэши и синтетические примеры.
- **История git** по-прежнему содержит реальный серийник лицензии
  (F-14). Это остаточный риск до отзыва/перевыпуска и очистки истории.
- **MSI в зонах 13/20** собран вручную с новым случайным ProductCode, чтобы
  не пересекаться с уже установленным продуктом. Официальный `make package`
  использует детерминированный ProductCode (`{2CB85794-986A-546F-A94D-6F59225FC9A7}`
  для 0.5.0). Поэтому «два продукта» и часть 1603 при повторной установке —
  артефакт тестовой сборки, а не дефект продукта. Финальный official MSI:
  `db8214be…2489b`.
- Часть low/info-находок не исправлялась сознательно: они не входят в
  критерий «critical», а их правка меняет поведение продукта и приёмки.
- Временные рамки: кампания шла в режиме реального времени на живом
  стенде; приоритет отдавался critical/high и воспроизводимости, поэтому
  отдельные экзотические комбинации (например, одновременный BSOD + обрыв
  сети + смена часов) не проверялись.

### 11.3. Как воспроизвести кампанию

1. Собрать артефакты из HEAD на Go 1.26.11:
   ```bash
   GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -o telehack-backend.exe ./cmd/backend
   GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -o telehack-agent.exe ./cmd/agent
   go build -o telehack-acceptance ./cmd/acceptance
   ```
2. Развернуть изолированный backend на отдельной БД/портах
   (`8543/8544/8546`, `Telehack2026_Test`, `telehack_test`), выполнить
   `bootstrap`, `admin-create`, `license-init`, зарегистрировать задачу
   `TelehackBackendTest`.
3. На WS1 запустить HEAD-агента отдельным экземпляром с
   `ProgramData=C:\ProgramData\TelehackTest` и конфигом на `:8543`
   (задача `TelehackAgentTest`); рабочую службу `TelehackAgent` не трогать.
4. Прогнать приёмку:
   ```bash
   ./telehack-acceptance contract -config acceptance.json -evidence evidence/
   ```
5. Нагрузка:
   ```bash
   ./loadgen -base https://192.168.189.138:8543 -ca ca.crt \
     -clients 350 -ramp 10m -hold 15m -poll 60s -prefix LOAD350
   ```
6. Уборка: `cleanup-srv.ps1` (drop DB/login, task, firewall, каталоги) и
   `cleanup-ws1.ps1` (task, тестовый агент, каталоги), затем проверить
   старые `:8443/:8444/:8446` и службу `TelehackAgent`.

Скрипты и конфиги тестового контура удалены после кампании вместе с
тестовыми паролями и токенами; отчёты сабагентов и доказательства — в
`evidence/test-campaign/` (локально, не коммитятся).

#### F-26 — High: «отравленный» сертификат блокировал весь отчёт (зона 16) — ИСПРАВЛЕНО

Файл `.cer` с `notAfter` вне 2000–2200, subject > 8192 байт или DER > 1 МиБ
попадал в отчёт, `ValidateReport` возвращал 422, и агент удалял отчёт из
очереди навсегда: машина переставала обновлять инвентаризацию.

Исправление в `observeDER`: subject/issuer/OwnerCN/INN/SNILS обрезаются
до лимита, дата вне диапазона превращается в `parse_error`, DER > 1 МиБ
пропускается с ошибкой источника (остальные сертификаты сохраняются).
Проверка: папка с `notAfter=9999` и обычным сертификатом — отчёт принят,
`file_certificates=2`, 422 нет; unit-тесты на все три случая.

#### F-28 — High: старый `uninstall` уничтожал identity (зона 13) — В HEAD УЖЕ ИСПРАВЛЕНО

Сборка `e881f93` при `uninstall` без `-purge` удаляла `AgentDir` целиком
(identity, DPAPI, очередь, state) до коммита `47e78f2`. В HEAD поведение
исправлено и подтверждено: MSI HEAD сохраняет identity/state/queue при
uninstall. Риск актуален только для парка, обновляемого со старых сборок;
рекомендация — сначала обновить агент, затем выполнять удаление.

### 5.3. Рекомендации по medium/low (не блокируют приёмку)

- **F-16 (роли).** Вызывать `requireAdminRole` на маршрутах выпуска API-ключей
  и изменения конфигурации либо явно задокументировать паритет `admin` и
  `superadmin` до появления управления учётными записями.
- **F-17 (disabled).** При `disabled=1` отзывать активные сессии, а не только
  блокировать новые входы.
- **F-20 (доступность).** Меню действий АРМ должно управляться стрелками/Esc,
  модалки — удерживать фокус; поднять контраст вторичного текста до ≥4.5:1.
- **F-21 (маска серийника).** Оставлять 4+4 символа, а не 20 из 25; миграция
  `license_id` потребуется отдельно.
- **F-27 (folder/files).** Либо включать сертификат в `files[]`, либо не
  помечать его исчезнувшим в той же транзакции.
- **F-29/F-30 (API).** 404/409 вместо 503 для машины без регистрации;
  `is_trial` — `boolean` (или явно `null`) по OpenAPI.
- **F-31 (ACL конфига).** Проверять DACL bootstrap-файла: писать должны только
  SYSTEM/Administrators; иначе предупреждать и не принимать конфиг.
- **F-32 (устаревшие сертификаты).** Разрешить «полному» сканированию
  снимать наблюдения, даже если отдельный файл не разобрался, либо дать
  администратору ручную команду retire.
- **F-33 (TOFU).** Опциональный enrollment-токен/подтверждение первой
  регистрации для закрытых контуров.
- **F-34 (GPO/MSI).** Подписывать MSI и проверять SHA-256 конфига в
  GPO-скрипте; не доверять SMB-шаре без проверки.
- **F-35 (UI).** `overflow-wrap:anywhere`, `max-width`, ellipsis для
  `display_name`; обернуть таблицы карточки в `overflow-x:auto`.
- **F-37 (агент).** Чистить маркеры `evicted-*`, добавить named mutex
  single-instance и корректно завершать дочерний процесс при stop.
- **F-38 (документация).** Описать все admin-маршруты в OpenAPI или убрать
  недокументированные.
