# Поэтапный план реализации

План описывает будущую работу. Наличие прототипов в tools/research и успешно выполненное исследование не означает готовность Go-продукта. Сроки и распределение по людям здесь не оцениваются: сначала нужен первый сквозной результат и измерение оставшейся сложности.

## Исходная точка

- На .136 CSP **5.0.13003**, на .137 **4.0.9963**; Windows 10 Enterprise **19045.7807**.
- LocalSystem SCM-служба прочитала 3/3 сертификата незагруженного user1/user2 без их паролей и процессов. Проверен локальный registry-backed physical MY; дополнительные хранилища пока не доказаны.
- COM-чтение даты лицензии работает из SYSTEM. Обязателен также тип **клиентская/серверная**, независимо от срока/пробности. Дополнительным экспериментом подтверждены GetType=0 → client на CSP 5 и GetType=1 → server на CSP 4 без CAdES. Перенос этого соответствия в Go еще предстоит.
- SQL Server **2019 Express 15.0.2000.5 RTM**, .138:1433 доступен; базы приложения нет. SQL TLS проверен только с диагностическим обходом доверия сертификату.
- Есть 20 разных сертификатов и корень в test-data, манифест ожидаемых данных и инструменты исследования. Ключи тестового УЦ находятся отдельно в .secrets.

## P01. Зафиксировать контракты и создать каркас

**Работа:**

- Создать Go-каркас с отдельными точками входа агента и бэкенда, общими DTO/подписью, Windows-адаптерами, миграциями, frontend и packaging. Имена каталогов выбрать при реализации; код продукта не размещать в tools/research.
- Закрепить версии Go/Node и зависимости. Решить, как воспроизводимо включать cpro-go/x509gost в сборку: локальный игнорируемый node_modules не должен быть единственным источником release-зависимостей.
- Описать версионированный REST-контракт регистрации, опроса, конфигурации, заданий и отчетов; ошибки hostname/UUID/ключа/DNS.
- Подписанное data содержит UUID, hostname, request_id и payload. Включение метода/пути — рекомендуемая деталь протокола, которую нужно явно закрепить и проверить на несовпадение.
- PEM PUBLIC KEY/SPKI, JCS UTF-8, SHA-256, ECDSA P-256, ASN.1 DER/Base64; request_id новый на попытку, report_id постоянный на результат.
- Определить стабильный внутренний machine_id, историю UUID регистраций, подписанный переход при переименовании и прекращение авторизации старого UUID.
- Определить источник наблюдения: личный store с SID либо .cer с путем. Не смешивать владельца Subject и локального пользователя. Полнота задается по конкретным профилям/источникам.
- Закрепить порядок отчетов: устойчивый счетчик сбора/поколение регистрации либо другой явный механизм. Запоздавший отчет сохраняется как принятый, но не откатывает более новое состояние источника.
- Задать конфигурационные значения по умолчанию и лимиты: пути GPO-файла/состояния/логов, порты, размер запроса/файла/элемента очереди, число файлов, тайм-ауты и повторные попытки. Не изменять уже согласованные 10 минут, 1 день, 2 отчета и два TXT-файла по 10 MB.

**Готовность:** описанные примеры запросов/ответов и JSON-схемы согласованы между агентом и сервером; спорные технические решения записаны, а не оставлены скрытыми предположениями. Есть контрольные векторы JCS/подписи, включая кириллицу, изменение UUID/hostname, повторяющиеся JSON-ключи и неверную кривую.

## P02. Перенести сборщик в Go и реальную Windows-службу

**Работа:**

- Реализовать управление SCM: start/stop, отмену операции, локальную диагностику. Базовый аккаунт — LocalSystem; никаких пользовательских паролей.
- Перенести перечень профилей и read-only WinAPI-путь из исследования: HKU\SID для загруженного профиля; временное подключение NTUSER.DAT и CERT_STORE_PROV_REG для незагруженного.
- Управлять Backup/Restore-привилегиями, registry/store/context handles; не создавать отсутствующее MY при обычном чтении. Отсутствующий store отличать от запрета доступа.
- Обработать изменение Loaded между проверкой и подключением, занятый hive, поврежденный профиль, отмену и выгрузку. Не выгружать чужие HKU-ветки и не изменять права пользователя для обхода ошибки.
- Из DER извлекать serial, issuer, owner и срок; дедупликация SHA-256 полного DER. Атрибуты Subject читать по OID, а не локализованным подписям ИНН/INN.
- Добавить .cer из папок админки: DER и PEM как явно поддерживаемые кодировки, исходный путь, ошибки отдельных файлов, дубли по содержимому. Правила рекурсии/исключений закрепить в конфигурации P01; поврежденный файл не прерывает весь сбор.
- Системные/машинные certificate stores не читать. Отсутствие CSP на поддерживаемой ОС — отдельное состояние; не прекращать доступный сбор .cer/открытых сертификатов без причины.
- Windows-зависимый код отделить от общих моделей. Будущие Linux-адаптеры — явные заглушки, а не заявленная поддержка.

**Готовность:** Go-служба на обоих стендах читает ожидаемые фикстуры загруженного и незагруженного пользователя, .cer и их дубли; выдает совпадающие SHA-256/поля. После нормального завершения и обработанных ошибок не остаются собственные mounts/handles. Закрытые ключи, Root store и лицензии не изменяются.

## P03. Версии и лицензирование КриптоПро

**Работа:**

- Получать release-версию продукта и, отдельно, версию ядра. Не подменять release версией cpcsp/cplicmgmt DLL.
- Создать Windows COM-адаптер CPCSPLicense для срока/исходного кода типа, с корректным жизненным циклом COM в Go и освобождением объектов. Проверять именно из службы.
- **Реализовать тип client/server на CSP 4 и 5:** использовать подтвержденные GetType 0=client / 1=server для проверенных сборок; raw/unknown для новых значений, ошибок и неподтвержденных вариантов. Независимая проверка SDK server-флага уже выполнена; CAdESCOM.Type остается дополнительным контрольным источником. Не объявлять коды 0/1 расшифрованными по одному примеру и не делать CAdES-плагин обязательным без отдельного решения.
- Разделить независимые поля: `csp_product_version`, `license_kind` client/server/unknown, срок и состояние, trial/perpetual-признак, исходный код и источник. Тип не выводить ни из версии CSP, ни из Windows Client/Server. Подтвержденные результаты .137=server/.136=client — данные конкретных установок, а не правило для всех CSP 4/5.
- Уточнить модель пробности: trial и ограниченность срока не взаимоисключающие признаки. Предлагается отдельно `is_trial` true/false/unknown и `term_kind` time_limited/perpetual/unknown; окончательный DTO закрепить в P01. Если API не дает достоверного ответа, не превращать отсутствие demo-флага закодированного номера в доказанное отсутствие пробного режима установки.
- Read-only сопоставить тип и срок в штатных средствах Windows с COM и SDK на этих же установках, проверить наличие временного режима и временную семантику. При доступной истории/метаданных установки уточнить происхождение лицензий. Не вводить новые лицензии, не перезапускать пробный период и не переустанавливать CSP ради классификации. Гипотезу о разных демо-лицензиях дистрибутивов до проверки не использовать в логике.
- В тестах предусмотреть разные client/server при одной версии CSP и одну классификацию при разных версиях/ОС, без изменения реальных лицензий стенда: применять DTO/контрольные ответы адаптеров. Отдельно проверить расхождение Windows COM-срока и SDK-проверки номера, а также неизвестные коды.
- Подтвердить временную семантику COM-даты до преобразования в UTC; при неопределенности передавать raw и unknown time basis.
- Отдельно проверить наличие встроенной лицензии в сертификате через документированный SDK/OID. Не считать тестовые фикстуры лицензированными и не имитировать лицензию вставкой неподтвержденного расширения.
- Предусмотреть отсутствие продукта, лицензии, ошибку COM и неизвестный ответ. Номер лицензии в диагностике и логах не требуется.

**Готовность:** на обеих конкретных сборках из SYSTEM получаются версии, срок и подтвержденный тип либо явно описанная диагностическая неопределенность. До финальной приемки client/server должен быть подтвержден на обеих поддерживаемых ветках; неподтвержденный источник не заменяется догадкой. Для встроенной лицензии есть проверяемый образец или явно отмеченный оставшийся пробел. В модели и тестах тип не привязан к версии CSP/Windows; подтвержденные поля отделены от unknown и гипотез. Необъясненное происхождение лицензии не блокирует сбор достоверного типа, но не позволяет заявлять подтвержденный trial/perpetual-режим.

## P04. SQL Server: схема и сохранение

**Работа:**

- Настроить подключение к выбранной БД, нормальное доверие TLS и способ передачи секретов. Не встраивать sa-пароль или постоянный обход проверки сертификата в EXE/исходники.
- Подготовить bootstrap БД/учетной записи и миграции таблиц. Создание отсутствующих таблиц в выбранной БД автоматизировать; создание самой БД отдельно документировать, не выполнять скрыто в master.
- Сущности: machines, registrations/keys, machine_users, certificates, observations, csp/license_state, configs, jobs, reports, events, request_ids, administrators/sessions. Физические названия — проектное решение, а не навязанная внешняя схема.
- Certificate SHA-256 уникален; machine_users привязаны к машине/SID; пользовательские связи many-to-many. Для файлов — наблюдение на машине с путем и nullable user.
- Уникальные ограничения для request_id, report_id и связей; обработка гонок и повторной регистрации. Сохранение report payload hash для конфликта одного report_id с другим содержимым.
- Обновлять только успешно обследованные области, сохранять previous state при ошибке/частичности. Исчезновение фиксировать только после полного успешного обследования той же области.
- Текущее состояние + события изменений; глубина снимков отложена до ответа кейсодержателя. Replay-ID не чистить по произвольному TTL при активной идентичности без срока запросов.

**Готовность:** миграции работают на чистой и существующей SQL Server 2019 БД без потери данных. Проверены повторный отчет, конкурирующий request_id, одинаковый DER на разных машинах, .cer без пользователя, частичный/запоздавший отчет и сохранение created_at.

## P05. Агентский REST/HTTPS API бэкенда

**Работа:**

- Один процесс запускает административный и агентский listeners на разных настраиваемых портах. HTTPS/конфигурация/подключение к БД независимы от установленного CSP.
- Реализовать регистрацию ключа/UUID, резервирование hostname, повтор с прежним ключом, отказ другому ключу и административную перепривязку.
- DNS hostname → source IP — доверительный признак. При несовпадении/ошибке DNS корректно подписанный отчет принимается, событие показывается администратору. Не доверять произвольному X-Forwarded-For в прямой схеме.
- Проверять JCS/подпись/идентичность до бизнес-изменений; request_id фиксировать атомарно с операцией. Схема проверки включает bootstrap-запрос регистрации.
- Реализовать идемпотентный прием report_id, конфигурацию по хешу и задания. При неизменном config hash задания все равно возвращаются.
- Ограничить размер/время запроса, объем отчетов и параллелизм; отклонять неверный JSON, подпись, curve, DER и несоответствие внешнего host.

**Готовность:** реальные запросы/негативные случаи проходят контрактные проверки; повтор после рестарта сервера не исполняется заново. Переименование сохраняет machine_id/историю и меняет UUID только по подтвержденному переходу. Бэкенд стартует обычным EXE без контейнера и балансировщика.

## P06. Рабочий цикл агента

**Работа:**

- Читать адрес сервера из GPO-файла; тот же формат доступен ручному тестовому запуску вне домена. Не отключать проверку HTTPS через доверие ОС.
- Генерировать UUID/ключ один раз, хранить ключ DPAPI + ACL. Проверить выбранный scope в реальном SYSTEM-контексте, после рестарта и обновления.
- Первый сбор сразу; по умолчанию ежедневно, затем n дней из админки. Опрос конфигурации/заданий раз в 10 минут; запрет одновременных сборов одной машины.
- Долговечная очередь — ровно два последних отчета, атомарная запись файлов/метаданных и восстановление после перезапуска. Новый request_id на попытку, прежний report_id/исходное время сбора на повтор отчета.
- Вытеснение старого отчета явно учитывается: нельзя обещать доставку каждого снимка. Частичный отчет не удаляет серверное состояние необследованных областей; потерянные до доставки данные не выдаются за известные и при возможности пересобираются.
- Повторы доставки не ждут следующего n-дневного срока. Подтверждать ручные задания и сохранять их состояние; не терять результат завершения задания при ротации двух отчетов.
- TXT-логи significant events/errors до миллисекунд, current/previous по 10 MB, удаление старого previous, без сжатия и секретов.

**Готовность:** автоматический цикл работает после отключения сети и перезапуска службы/ПК, очередь не превышает двух элементов, утрата ответа не создает дубль, ключ/UUID сохраняются, CLI не требуется в нормальном режиме.

## P07. Первый сквозной результат на обеих сборках

**Работа:** установить Go-службу на .136/.137, направить отчеты в отдельную тестовую БД на .138, выполнить полный цикл и сопоставить записи с манифестом.

**Готовность:** в БД видны обе машины, их пользователи, версии CSP, лицензии с client/server, пользовательские и файловые наблюдения сертификатов. Один DER объединяется между двумя ПК; повтор не создает дубль. Проверены полный, частичный, пустой успешный и запоздавший результаты. Все временные фикстуры устанавливаются/удаляются контролируемо.

Этот этап — первая демонстрируемая вертикальная часть. До него не расходовать основной объем работы на внешний вид админки и дополнительные интеграции.

## P08. Админка Vue + Vite

**Работа:**

- Локальная авторизация, стойкий хеш пароля, безопасные сеансы. Администратор создается напрямую в БД: документировать совместимый формат/способ получения хеша и SQL-вставку без пароля в исходниках.
- Экраны machines/users/certificates/licensing с источниками, сроками, client/server, сырым unknown при ошибке, временем/полнотой сбора и событиями. Версию CSP, client/server и пробность/срок показывать раздельно; не помечать server на Windows 10 как ошибку только из-за такого сочетания.
- Настройка n дней и папок .cer, постановка ручного сканирования, состояние заданий, hostname/DNS-конфликты и разрешенная перепривязка.
- Пагинация/поиск/фильтры для реального объема данных; display subject отдельно от идентификатора пользователя.
- Сборка в один HTML + один CSS + один JS, embed в backend EXE. Никаких обязательных Node-сервера, CDN и дополнительных JS-чанков.

**Готовность:** администратор входит, просматривает оба стенда и тип лицензии, меняет папки/расписание и получает результат ручного задания после очередного опроса. Установленная админка работает из EXE с ограниченными внешними соединениями.

## P09. MSI, GPO и полный жизненный цикл

**Работа:** MSI со службой/EXE, каталогами/ACL, CLI, runtime-зависимостями только по результатам сборки, Installer-метаданными. Индивидуальные ключи не входят в пакет; CSP и пользовательские корни не устанавливаются агентом.

Проверить установку через GPO и вручную; первый сбор; upgrade через новый MSI с сохранением UUID/ключа/очереди; отказ от некорректного обновления; полное удаление через CLI/uninstall, вызывающий штатное MSI-удаление. GPO-конфиг и доверенные сертификаты ОС не являются собственными данными, автоматически не удаляются.

**Готовность:** установка/обновление/удаление работают на обеих станциях, службы и MSI-регистрация согласованы, после uninstall нет собственного ключа/очереди/логов/службы. История машины на сервере сохранена. После переустановки новая идентичность проходит согласованные правила конфликтов, а не молча захватывает старую.

## P10. Отказы и эксплуатационные границы

Проверить недоступные профиль/папку/COM/БД, поврежденный .cer/конфиг/очередь, заполнение диска, потерю питания/процесса в середине операции, остановку при подключенном hive, вход пользователя во время сбора, конфликты имен/ключей и смену hostname при неотправленной очереди.

Проверить отсутствие входящих портов агента, корректное доверие TLS обоих каналов, сохранение replay-защиты после рестарта, невозможность повторного исполнения отчета и отсутствие секретов в артефактах/логах. Проверить ошибки при недостаточных правах вместо расширения прав на профили.

**Готовность:** нет ложного «сертификат исчез» при неполном сборе; очищаются только собственные mounts, ошибки диагностируемы, следующий запуск восстанавливает работу. Непроверенные дополнительные хранилища явно отмечены, а не объявлены пустыми.

## P11. Один сервер под нагрузкой 200+

**Работа:** профиль нагрузки из реальных отчетов P07, 200+ независимых идентичностей, массовая регистрация/первый сбор, периодический опрос, пакетная отправка после восстановления сети, одновременно работающая админка. Использовать тестовую БД и один процесс backend EXE.

Измерить CPU/RAM, размер БД и рост request_ids/events, пул SQL-соединений, время обработки отчетов/страниц и очереди. SQL Express/RTM фиксируется как конфигурация стенда; ее ограничения учитывать по измерениям и актуальной документации, не заменять несколькими бэкендами.

**Готовность:** документирован измеренный результат на заданных CPU/RAM и объеме сертификатов. Конкретные пороги приемки согласовать до итогового прогона; не подменять их одной фразой «нагрузку выдерживает». При проблемах исправлять запросы/индексы/параллелизм и повторять затронутые измерения.

## P12. Поставка и приемка

Артефакты: версия/контрольные суммы MSI агента и portable backend EXE, пример конфигов, миграции/bootstrap, инструкция GPO/ручной установки, процедура создания администратора через БД, обновление/удаление, TLS-настройка, восстановление БД/ключа, таблица совместимости и протокол проверок.

Демонстрация: невошедший пользователь → личные сертификаты → подписанный отчет → SQL → админка; .cer из папки; клиентский/серверный тип и срок лицензии; ручной сбор; отсутствие сети и повтор доставки; исчезновение только после полного успешного сканирования.

**Готовность:** продуктовый Go-путь проверен на CSP 4.0.9963 и 5.0.13003, установка воспроизводима, подтвержден одиночный сервер 200+, известные ограничения перечислены. Поддержку Windows Server 2019 не объявлять проверенной только из-за стенда Windows Server 2022. Публичная публикация/развертывание за пределами согласованного стенда этим планом не поручается.

## Оставшиеся внешние ответы и что они блокируют

| Неизвестное | Действие | Что пока можно делать |
| --- | --- | --- |
| Подтверждение Windows Server 2019 | Вернуться после ответа кейсодержателя; добавить тест целевой ОС | Разрабатывать portable EXE на текущем Server 2022 |
| Глубина истории | Пока состояние + события; не закладывать обязательные полные снимки | Реализовать текущую модель и метаданные сборов |
| Go-перенос лицензирующих кодов | Соответствие 0=client / 1=server уже подтверждено на CSP 4/5; проверить из Go/SYSTEM в P03 | Реализовывать базовый COM без CAdES; новые значения — unknown |
| Временная семантика COM и пример встроенной лицензии | Подтвердить SDK-контракт/получить пример | Хранить raw/time_basis, не выдавать фикстуры за лицензию |
| Происхождение и эффективный trial/perpetual-режим лицензий стенда | Проверить read-only штатные сведения и доступную историю; гипотеза о дистрибутивах пока не подтверждена | Собирать подтвержденные client/server; режим/происхождение оставлять unknown, не определять по версии CSP или ОС |

Linux-демон, токены, CRL/OCSP, интеграционный API и самообновление не являются обязательными этапами первой поставки. Задел — интерфейсы и разделение платформенных частей; возвращаться к функциям после основного объема и новых указаний.
