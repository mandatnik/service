# Проверка активации CSP из службы — 14.11.2026

## Текущий результат: рабочий ключ установлен

14.11.2026 пользователь предоставил отдельный ключ для одной активации.
Он записан одной попыткой только на WORKSTATION-1, CSP 5.0.13003,
из настоящей SYSTEM-службы, Session 0. Проверка из свежего процесса
подтвердила точное совпадение переданного ключа с реестром и PP_LICENSE.
CAdESCOM.CPLicense возвращает `IsValid=true`, `Type=Client`, `ValidTo=Unlimited`.
Лицензия оставлена установленной. WORKSTATION-2 не изменялась.
Подробности в последнем разделе.

## Предыдущий этап: подтверждён способ без окон

Повторный эксперимент 14.11.2026 подтвердил на обеих воркстанциях запись
`ProductID` через Registry64 из SYSTEM-службы. При заведомо неверном номере
сами CryptoAPI/COM возвращают ошибки, после точного восстановления номера
чтение лицензии возвращается к исходному успешному состоянию. Подробнее
в разделе «Замена ProductID из службы» ниже. Новая действующая лицензия
пока не проверялась: тестового ключа нет.

## Первоначальный вывод о COM API

Через используемый агентом COM-интерфейс `CPCSPLicense.CPCSPLicense`
ввести лицензию нельзя: в опубликованном IDispatch-интерфейсе обеих
проверенных сборок есть только `GetType`, `GetInstallDate`, `GetExpireDate`.
LocalSystem успешно читает лицензию конкретного установленного продукта по
GUID. Отсутствие метода записи не связано с правами или интерактивным входом.

Это не доказывает невозможность активации из службы вообще. Для неё нужен
другой, подтверждённый для конкретной сборки механизм. Установка CSP с
`PIDKEY` и замена лицензии уже установленного CSP — разные сценарии;
успешный код завершения MSI сам по себе не доказывает замену лицензии.

## Эксперимент

На каждой рабочей станции временно создана настоящая SCM-служба
`TelehackResearchProbe`. Служба запустила 64-битный PowerShell в Session 0
под `NT AUTHORITY\SYSTEM`, SID `S-1-5-18`. Проверены опубликованные COM-методы,
вызваны методы чтения с обнаруженным GUID CSP, выполнен поиск именованных
экспортов `license_get`, `license_check`, `license_set`, `SetLicense`,
`SetSerialNumber` в явно указанных установленных библиотеках.

| Машина | CSP | GUID продукта | COM API |
| --- | --- | --- | --- |
| WORKSTATION-1, .136 | 5.0.13003 | `{50F91F80-D397-437C-B0C8-62128DE3B55E}` | 3 метода чтения |
| WORKSTATION-2, .137 | 4.0.9963 | `{407E5BA7-6406-40BF-A4DC-3654B8F584C1}` | 3 метода чтения |

В `cplicmgmt.dll` и `cpcsp.dll` на обеих станциях проверенные именованные
экспорты отсутствуют. `cpconfig.cpl` загрузился на CSP 4, эти экспорты также
отсутствуют. На CSP 5 LoadLibrary для указанного пути вернул NULL;
причина этим экспериментом не устанавливалась. Отсутствие этих экспортов
не исключает другие библиотеки, COM-интерфейсы или механизмы установщика.

Локальный SDK macOS содержит `license_set` в `license_api.h`, но её наличие
не подтверждает доступность такого ABI в установленных Windows-библиотеках.

Номера лицензий не читались и не записывались. Установка/repair CSP,
изменение реестра лицензий, создание контейнеров и ключей не выполнялись.
Временные службы и каталоги удалены, отсутствие проверено после удаления.
Код продукта и его протокол не менялись.

## Замена ProductID из службы

Пользователь разрешил проверку механизмов с неверным ключом; действующего
нового тестового ключа пока нет. Основание выбора способа —
[ответ сотрудника КриптоПро, сообщение №4](https://cryptopro.ru/forum2/default.aspx?g=posts&t=13583):
для Windows CSP 4/5 предлагается записывать собственный серийный номер без
разделителей в `ProductID` раздела MSI. Более поздний
[ответ сотрудника, сообщение №72](https://www.cryptopro.ru/forum2/default.aspx?g=posts&m=147376)
уточняет принудительную замену значения через `reg add /f`.

Эксперимент использовал `RegistryKey.SetValue`, поэтому запуск `reg.exe`,
передача лицензии в командной строке и подтверждение перезаписи не нужны.
Проверены конкретные ветки **64-битного** системного реестра:

```text
HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Installer\UserData\S-1-5-18\Products\<PackedProductGUID>\InstallProperties
```

| Машина | Версия CSP | PackedProductGUID |
| --- | --- | --- |
| WORKSTATION-1 | 5.0.13003 | `08F19F05793DC7340B8C2621D83E5BE5` |
| WORKSTATION-2 | 4.0.9963 | `7AB5E7046046FB044ACD63458B5F481C` |

Алгоритм теста:

1. Настоящая SCM-служба выполнялась как `NT AUTHORITY\SYSTEM`, SID `S-1-5-18`, Session 0.
2. Исходное значение `ProductID` и его тип сохранены только на воркстанции
   в каталоге с ACL для SYSTEM/Administrators. Дополнительно создана SYSTEM-задача
   аварийного восстановления через две минуты.
3. До изменения отдельный процесс подтвердил: CryptoAPI `PP_LICENSE` совпадает
   с реестром, COM читает тип и срок.
4. Служба записала 25 нулей как заведомо неверный тестовый номер. Новая копия
   процесса проверила состояние через CryptoAPI и COM.
5. В блоке `finally` восстановлены исходное значение и тип, проверено точное
   совпадение. Новый процесс снова подтвердил исходную лицензию через оба API.
6. Удалены аварийная задача, исследовательская служба, защищённая резервная
   копия и временный каталог. Отсутствие службы/каталога/задачи проверено.

### Результаты на обеих станциях

| Проверка | До изменения | Неверный номер | После восстановления |
| --- | --- | --- | --- |
| `CryptAcquireContext(VERIFYCONTEXT|SILENT)` | `0` | `0` | `0` |
| `CryptGetProvParam(PP_LICENSE)` | `0`, номер совпадает с реестром | `0x8009000A` | `0`, исходный номер |
| `CPCSPLicense.GetType/GetExpireDate` | успешно | `0xFFFFFFFF` | успешно |
| Срок, возвращаемый COM | 2027-02-14 18:59:59 | ошибка | 2027-02-14 18:59:59 |

Тип после восстановления: `0` на CSP 5, `1` на CSP 4 — как до изменения.
Здесь используются только сравнения в памяти, номера не попали в отчёты.

Важно: `0x8009000A` — общий код **NTE_BAD_TYPE**, а не документированный
специальный код «Неверный лицензионный ключ». `0xFFFFFFFF` также неспецифичен.
[Справочник Microsoft](https://learn.microsoft.com/en-us/windows/win32/com/com-error-codes-4).
В этом контролируемом эксперименте обе ошибки возникли при замене единственного
параметра на неверный номер и исчезли при его восстановлении. Это подтверждает
реакцию провайдера на изменение лицензии. Нельзя по этим кодам в произвольном
окружении автоматически диагностировать именно неверный ключ.

`CryptAcquireContext` оставался успешным даже с неверным номером, поэтому
одного успешного AcquireContext недостаточно для проверки активации.
Положительная активация новой действующей лицензии не заявляется.

Запуск выполнен без интерактивного UI и ввода пользователя, без перезагрузки,
перезапуска CSP и переустановки. Нативные обращения к провайдеру использовали
флаг SILENT. Возможность будущей работы уже запущенных сторонних приложений
с их кэшами отдельно не проверялась. Права проверены именно для LocalSystem;
служба под другой учётной записью должна иметь доступ к указанному разделу.

### Проверка через Windows Installer

На обеих станциях из SYSTEM-службы также вызвано действие `ValidatePID`
из локально кэшированного MSI с `MsiSetInternalUI(INSTALLUILEVEL_NONE=2)`.
Пакет открыт через `MsiOpenPackageEx(..., MSIOPENPACKAGEFLAGS_IGNOREMACHINESTATE=1)`;
`InstallExecuteSequence` не запускалась. `MsiDoActionW` вернул **1626** на
обеих версиях. Это ошибка выполнения действия, **не** результат «Неверный ключ».
Наличие в MSI строки `You have entered invalid serial number.` не означает,
что валидатор был успешно вызван. Исходный реестр остался неизменным.
Этот путь для валидации и активации не подтверждён.

Для конкретной машины получить ключ через защищённый файл, записать его без
разделителей в соответствующий `ProductID`, затем из свежего процесса проверить

## Положительный тест с ключом пользователя — WORKSTATION-1

Из службы выполнена одна запись нового номера без разделителей через
`RegistryKey.SetValue(ProductID, ..., REG_SZ)`. Ключ не передавался на
WORKSTATION-2, повторной записи/ввода не было. Все последующие обращения
к КриптоПро — только чтение. Ключ в файлах исходного кода и отчётах отсутствует.

Результат:

- Registry64 и CryptoAPI `PP_LICENSE` содержат точно переданный номер:
  сравнение выполнено без вывода номера в журнал.
- `CPCSPLicense.GetType = 0`, вызовы чтения успешны.
- `GetExpireDate = 1899-12-30T00:00:00`, то есть нулевая OLE-дата.
- Независимый Windows API `CAdESCOM.CPLicense`: `IsValid() = true`,
  `Type() = Client`, `ValidTo() = Unlimited`. Эти же значения подтверждены
  из отдельной настоящей SYSTEM-службы, Session 0, без повторной записи ключа.
- Дополнительный офлайн-контроль локальным macOS SDK: `license_check = 0`,
  `validity = 2`, `extra = 0`, `unix_end = 0`. Windows-проверка остаётся
  основным доказательством установленного состояния.

Следовательно, на этой станции ключ принят как действующая бессрочная
клиентская лицензия. Проверка подписания пользовательским закрытым ключом
не выполнялась; онлайн-учёт числа активаций у продавца не проверялся.

При сохранении первичного отчёта запуск дополнительной read-only проверки
локального PS1 был заблокирован политикой выполнения PowerShell; запись
лицензии к этому моменту уже завершилась успешно. Повторная активация не
выполнялась. Итог подтверждён независимым read-only сценарием с явно заданной
политикой выполнения и отдельной SYSTEM-службой. Первичный полный отчёт
службы применения не сохранился; сохранены последующие проверки.

Исследовательские службы, аварийные задачи восстановления и временные
каталоги удалены, TelehackAgent продолжает работать. Лицензия остаётся
установленной; исходный номер не возвращался после успешного применения.

### Обнаруженная особенность учёта

Текущий `internal/agent/winapi/csp_license_windows.go` до версии 0.5.0
считал любое читаемое значение `GetExpireDate` конечной датой. В 0.5.0
нулевая OLE-дата распознаётся как `term_kind=perpetual` и `state=active`;
она не отображается как просроченная и не превращается в 1899 UTC.

### Дополнительный API, обнаруженный при контроле

На WORKSTATION-1 установлен `CAdESCOM.CPLicense`, у которого существует
`SetLicense(string, string, string, int)`, в отличие от базового
`CPCSPLicense`. Это отражено в
[документации производителя](https://docs.cryptopro.ru/cades/reference/cadescom/cadescom_class/cplicense).
`SetLicense` с предоставленным разовым ключом не вызывался: использован
только уже проверенный механизм реестра, а CAdES — для чтения результата.
На WORKSTATION-2 наличие CAdES ранее не подтверждено; зависимость продукта
от него этим экспериментом не вводилась.

## Область действия: agent и mimbol

14.11.2026 выполнены отдельные SSH-входы на WORKSTATION-1 под
`HACK\agent` и `HACK\mimbol` с предоставленными пользователем доступами.
Получены разные Windows SID и разные профили `C:\Users\agent` /
`C:\Users\mimbol`. Оба сеанса имели административный токен.
В каждом сеансе создан отдельный процесс PowerShell; проверены CAdES COM,
базовый COM и CryptoAPI с VERIFYCONTEXT|SILENT.

| Сеанс | IsValid | Type | ValidTo | PP_LICENSE совпадает с предоставленным ключом |
| --- | --- | --- | --- | --- |
| HACK\agent | true | Client | Unlimited | true |
| HACK\mimbol | true | Client | Unlimited | true |

Сравнение полного номера выполнено в памяти через SHA-256; ни номер,
ни его хеш не включены в отчёты. Лицензия не записывалась повторно.
Параметр установлен в HKLM, а не HKCU, и оба различных пользователя видят
один и тот же принятый ключ. Вместе с предыдущей проверкой SYSTEM это
подтверждает общемашинную область установленной лицензии, а не привязку
к профилю пользователя службы. Пользовательские контейнеры/закрытые ключи
и права на них этой проверкой не исследовались. Отдельный обычный
неадминистративный пользователь в этом опыте не проверялся.

Временный проверочный PS1 на станции удалён, SSH control-соединения закрыты.
