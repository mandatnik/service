# Админка P08

Админка — Vue 3 + Vite, собирается в **один HTML, один CSS и один JS** и
встраивается в `mandatnik-backend.exe`. Node.js нужен только при сборке
интерфейса; на стенде отдельный Node/статserver/CDN не требуется.

## Сборка

```bash
cd frontend
npm ci
npm run build
```

Vite кладёт результат в `internal/backend/web/dist`:

```text
dist/index.html
dist/app.css
dist/app.js
```

Каталог `dist` закоммичен. Backend использует `go:embed` (пакет
`internal/backend/web`), поэтому свежий clone собирается без Node.js.
После изменения `frontend/src` повторите `npm run build` и закоммитьте
`dist` вместе с исходниками.

## Локальный администратор

Пароль не хранится в исходниках и не принимается аргументом командной
строки. Хеш — bcrypt cost 12.

Вход выполняется по электронной почте. У каждой учётной записи есть
отображаемое имя (например, `Малыгин А. Е.`) и роль `admin` или
`superadmin`.

Создание/смена пароля через backend:

```powershell
$env:MANDATNIK_ADMIN_PASSWORD = '<сильный пароль>'
mandatnik-backend.exe admin-create -config C:\ProgramData\Mandatnik\Backend\backend.json `
  -email admin@example.com -name "Малыгин А. Е." -role superadmin
Remove-Item Env:MANDATNIK_ADMIN_PASSWORD
```

Прямая SQL-вставка (если администратор создаётся DBA):

```powershell
$env:MANDATNIK_ADMIN_PASSWORD = '<сильный пароль>'
mandatnik-backend.exe hash-password
# скопируйте полученный bcrypt-хеш в SQL ниже
Remove-Item Env:MANDATNIK_ADMIN_PASSWORD
```

```sql
INSERT INTO dbo.administrators
  (username, email, display_name, role, password_hash, disabled, created_at)
VALUES
  (N'admin', N'admin@example.com', N'Малыгин А. Е.', N'superadmin',
   N'<bcrypt-$2a$12-хеш>', 0, SYSUTCDATETIME());
```

Колонка `username` оставлена только для совместимости со старыми
инструментами; приложение её больше не читает и не показывает. Уникальность
входа обеспечивает `email`.

Публичной регистрации администраторов нет.

## Роли

- `admin` — обычный администратор.
- `superadmin` — администратор с правом управления обычными
  администраторами (создание, изменение email/пароля/ФИО, заморозка,
  разморозка и удаление).

Раздел «Админы» виден и доступен только `superadmin`; обычный администратор
получает `403` от каждого маршрута `/api/admin/v1/admins` независимо от
скрытия навигации. Через этот раздел и его API нельзя создать `superadmin`,
повысить роль или изменить/удалить существующую суперадминскую учётную
запись: сервер принимает только роль `admin`, а операции над `superadmin`
отклоняются. Суперадминские учётные записи по-прежнему создаются только
локальной командой `admin-create`.

Миграция `0007_admin_identity.sql` переводит существующие записи на почту и
отображаемое имя и назначает самого старого администратора (`MIN(admin_id)`)
ролью `superadmin`.

### Управление администраторами

Все изменяющие действия требуют cookie сессии `superadmin` и CSRF. Пароль
хешируется тем же bcrypt cost 12, что и при локальном создании; API никогда
не возвращает хеш. Email нормализуется, ФИО обязательно, пароль — не короче
12 символов.

- Заморозка (`disabled=1`) и удаление немедленно отзывают все сессии
  администратора; `ValidateAdminSession` дополнительно требует `disabled=0`,
  поэтому доступ прекращается и без ожидания истечения cookie.
- Смена email или пароля также отзывает старые сессии. Смена только ФИО
  сессии не затрагивает.
- Удаление учётной записи удаляет её сессии, но не журнал: события
  `admin_created`, `admin_updated`, `admin_frozen`, `admin_unfrozen`,
  `admin_deleted` хранят email автора и цель. Строковые авторы задач и
  лицензий остаются читаемыми.
- Список администраторов отдаёт только `id`, `email`, `display_name`, `role`,
  `disabled`, `created_at`.


## Сессии и защита

- Вход: `POST /api/admin/v1/login` с JSON `{"email": "...", "password": "..."}`
  (HTTPS).
- Пароль проверяется bcrypt; при неверном пароле/неизвестной почте
  возвращается одинаковый ответ.
- `POST /login` и `GET /session` возвращают `email`, `display_name`, `role`,
  `expires_at` и `csrf_token`; устаревший `username` не отдаётся.
- Сервер создаёт случайный 32-байтовый токен; в SQL хранится только
  SHA-256 токена. Сессия живёт `admin_session_hours` (по умолчанию 12 ч).
- Cookie `mandatnik_admin` — `HttpOnly`, `Secure`, `SameSite=Strict`.
- Cookie `mandatnik_csrf` доступна JS; для `POST/PUT/DELETE` требуется
  заголовок `X-CSRF-Token`, совпадающий с cookie (double-submit).
- На 401 интерфейс показывает форму входа; административные API без
  валидной сессии недоступны.
- В памяти backend действует ограничение попыток входа (5 неудач за 5 минут
  на источник).
- Статика отдаётся с CSP, `X-Frame-Options: DENY`, `nosniff`,
  `Referrer-Policy: no-referrer`, HSTS.

## Интеграционный API и API-ключи

Интеграционный listener — отдельный HTTPS-порт `8446` (настраивается
`integration_listen`), префикс маршрутов `/api/integration/v1`. Он не
использует cookie администратора и не принимает агентские подписи.

- Ключ создаётся в разделе «API-ключи». Формат токена:
  `mndk_<64 строчных hex>`. Токен показывается один раз; в БД хранится только
  SHA-256, префикс и метаданные.
- У ключа полный доступ ко всем интеграционным маршрутам. Ограничение —
  список разрешённых IP/CIDR. При создании нужен хотя бы один адрес; пустой
  список при последующем редактировании отключает ключ (403).
- Проверяется только IP сокета. `X-Forwarded-For`, `Forwarded` и другие
  заголовки не используются; при reverse proxy нужен реальный source IP.
- Отозванный ключ отвечает 401. Все ответы содержат `Cache-Control: no-store`.
- Ключи и их использование фиксируются событиями `api_key_created`,
  `api_key_updated`, `api_key_revoked`.

Маршруты: `machines`, `groups`, `folder-policies`, `certificates`,
`licensing`, `events`, `scan-jobs`. Пагинация — `page`/`page_size`, по
умолчанию 50, максимум 500. Контракт и схемы:
[api/integration-openapi.yaml](../api/integration-openapi.yaml).

`POST /scan-jobs` идемпотентен: машины с уже ожидающим или доставленным
scan пропускаются и возвращаются в `skipped`; при частичном успехе — HTTP 207.
Режима «все машины» нет — нужен явный список `machine_ids` или `group_id`.

Инвентаризация лицензий в интеграционном API отражает только текущее
состояние, полученное агентом с рабочих станций. Полный серийный номер не
покидает рабочую станцию: агент передаёт `serial_masked` и
`license_id = SHA-256(serial_masked)`. Одна лицензия на продукт на машину;
одинаковый номер на двух машинах считается конфликтом и не объединяется
автоматически.

## Таблица АРМ

`GET /machines` возвращает для каждой машины не только регистрацию и CSP, но
и данные, из которых собирается таблица админки:

| Поле | Значение |
| --- | --- |
| `display_name` | имя АРМ; если оно пустое, подставляется UUID регистрации, а при её отсутствии — `machine_id` |
| `display_name_custom` | `true`, если имя задано администратором и не должно перезаписываться hostname |
| `uuid`, `hostname`, `source_ip` | идентичность и последний источник |
| `dns_status`, `dns_reverse_status` | прямой (hostname → IP) и обратный (IP → hostname) результаты последней DNS-проверки |
| `dns_verified` | `true`, только если оба направления подтверждены для текущих hostname/IP и результат не старше 15 минут |
| `dns_verified_at` | время проверки, на которой основан `dns_verified` |
| `offline`, `last_seen_at` | связь; offline — нет активной связи 3 минуты и более |
| `csp_present`, `product_version`, `license_kind` | установлен ли CSP, версия и клиентский/серверный тип |
| `license_state`, `is_trial`, `term_kind`, `license_valid_to` | состояние, пробность, срок и дата окончания лицензии |
| `registry_certificates` | уникальные сертификаты в личных хранилищах (`user_store`) |
| `file_certificates` | уникальные файловые сертификаты (`folder`) |
| `licensed_certificates` | уникальные личные сертификаты со встроенной лицензией |
| `groups[]` | `id` и `name` групп, в которые входит машина (отсортированы по имени) |
| `status` | вычисленный статус: `csp_missing`, `trial`, `license_required`, `ok` |

Статус не зависит от связи: «Не в сети» показывается отдельно в колонке
«Онлайн» и не скрывает состояние CSP/лицензии. Приоритет статуса: нет CSP →
покрытие сертификатов/лицензия. Правила `trial`, `license_required` и `ok`
применяются только при `registry_certificates > licensed_certificates` и
ненулевом числе личных сертификатов; активная непробная лицензия или полное
покрытие встроенными лицензиями дают `ok`. Статус `ok` отображается как
«Работает» (зелёный) для машины в сети и как «В норме» (серый) для машины
не в сети; остальные статусы от связи не зависят.

Зелёный бадж «Проверен DNS» справа от IP показывается только при взаимном
соответствии: hostname резолвится в source IP и PTR-запись source IP
соответствует hostname. Результат привязан к конкретным hostname и IP;
смена любого из них, отсутствие обратной проверки, `unknown`, `error`,
`mismatch` или результат старше 15 минут не считаются подтверждением.
Список машин читает сохранённый результат и не выполняет DNS-запросы в
обработчике запроса; проверка выполняется в фоновом DNS-кэше агентского API.


## Установки агента и замена установки

Новый UUID с именем, которое уже связано с машиной (текущее имя, любая
историческая регистрация или архивированная карточка), не создаёт новую
машину. Он создаёт одну заявку в `/installations`; повторные подписанные
обращения обновляют её, а смена ключа при том же UUID отклоняется. Пока
заявка не решена, установка не получает конфигурацию, задания и историю
машины.

В разделе «АРМ» появляется очередь «Ожидают подтверждения». В карточке
машины действие «Заменить установку агента» показывает:

- выбранную карточку и её `machine_id`;
- старую регистрацию, последнее обращение и состояние связи;
- hostname, UUID, отпечаток ключа, адрес и время обращения новой установки;
- предупреждение, если старая установка была на связи менее 20 минут назад.

Администратор ставит явную галочку подтверждения пары «машина — новая
установка». Запрос содержит `request_version` и `key_fingerprint`, поэтому
изменённая или устаревшая заявка не может быть подтверждена старым окном.
Повторное подтверждение идемпотентно.

Решения:

- **Заменить установку** — в одной транзакции старая регистрация становится
  `replaced`, новая активной; `machine_id`, отчёты, пользователи,
  сертификаты, события, группы и политики сохраняются. Hostname
  переназначается новой регистрации. Старые capabilities и ключи шифрования
  не копируются.
- **Создать отдельную машину** — только после явного разрешения совпадения
  имени; история существующей карточки не переносится.
- **Отклонить** — заявка остаётся в истории со статусом `rejected`.
  Повторная регистрация того же UUID получает `installation_rejected`; для
  новой попытки нужен `reset-identity` или решение администратора.

Если новая установка уже зарегистрирована в другой карточке, интерфейс
показывает это ограничение и не выполняет частичное слияние.

Совместимость: новый backend можно развернуть раньше агентов. Старый агент
на заявку получает `409 installation_pending`, повторяет регистрацию по
своему обычному интервалу и не создаёт новый UUID; подтверждение всё равно
требуется. Новый агент дополнительно сохраняет состояние ожидания, пишет его
в `registration-state.json`/`diag` и повторяет запрос не чаще раза в 5 минут. Порядок
развёртывания: сначала backend, затем (при возможности) агент; откат
backend не требует менять идентичность агента.

Исторические карточки без активной регистрации можно архивировать отдельным
действием в карточке; архивированная карточка не используется как цель
замены (только отдельная машина или отказ). По умолчанию они не показываются среди действующих,
но доступны через фильтр «Архивные» с причиной, автором и временем; отчёты и
события не удаляются. Архивирование действующей карточки через старый
`/archive` запрещено.

Действие «…» → «Деактивировать» в строке АРМ выполняет soft-delete
действующей машины: используется тот же механизм архивации
(`archived_at`, `archived_by`, `archive_reason`), но дополнительно активные
регистрации переводятся в `revoked`, hostname освобождается, ключи шифрования
деактивируются, а ожидающие legacy-задания отменяются. Карточка, отчёты,
наблюдения, задачи, события и авторы сохраняются. Повторная деактивация
идемпотентна; уже архивная карточка показывает действие недоступным.

## Переименование АРМ

Имя АРМ в таблице и карточке по умолчанию равно hostname агента, но его можно
изменить через «…» в строке таблицы или кнопку «Переименовать» в карточке.
Меняется только `machines.display_name`; hostname, UUID, `machine_id`,
регистрации и задания не затрагиваются. Это действие не является подписанным
`rename` агента и не заменяет установку.

Пользовательское имя помечается `display_name_custom=1` и сохраняется при
последующей замене установки или штатной смене hostname агентом. Пустое имя,
управляющие символы и значение длиннее 253 символов отклоняются. Изменение
фиксируется событием `machine_display_name_changed` с прежним и новым именем
и администратором.

## Ручное сканирование

`POST /machines/{id}/jobs` создаёт задание `scan` со стабильным `job_id` и
связанную задачу/выполнение. Агент получает его на ближайшем опросе (новые
агенты — по настраиваемому интервалу, по умолчанию 60 с) даже при неизменном
`config_hash`; выполнение подтверждается `job_ack`/task result. Ручной scan не
ждёт прежнего 10-минутного ограничения. Результат появляется после отправки
отчёта; `succeeded` задачи scan связан с принятым `report_id`.

В разделе «Задачи» получатели выбираются чекбоксами: машины и группы,
поиск по каждому списку и счётчик уникальных получателей. Форма отправляет
`machine_ids` и `group_ids` в существующий `POST /tasks`; сервер объединяет
их без дублей и сохраняет снимок в задаче. Машина, выбранная напрямую и
входящая в несколько групп, получает одно выполнение. Архивные машины и
машины без активной регистрации не попадают в задачу ни напрямую, ни через
группу. Ошибка загрузки каталога получателей показывается в форме с
возможностью повторить загрузку.

## Пулы лицензий и активация

- Пул задаёт CSP 4/5, client/server и заявленный срок 1 год/2 года/бессрочно.
  После добавления ключей эти поля неизменяемы; переименование и архивирование
  разрешены.
- Номера вводятся по одному или списком. Импорт сначала проверяет все строки;
  при ошибке/дубликате не добавляется ни один номер. Ответы содержат только
  маску, ID и безопасный код, но не исходный номер.
- Состояния ключа: `available`, `reserved`, `used`, `outcome_unknown`,
  `blocked`. Резерв создаётся атомарно вместе с задачей; дефицит не приводит к
  скрытой частичной выдаче.
- «Активировать лицензию» доступна из выбранных машин и групп. Preview
  показывает четыре списка: нужна активация (без лицензии/триал), можно не
  активировать, уже активирована (disabled), нужна проверка (disabled).
  Действующие приобретённые лицензии защищены; триал включается вручную, при
  наличии подходящего сертификата.
- Задача установки использует один пул и снимок получателей. Изменение групп
  после создания задачу не меняет; несовместимые машины исключены с причиной.
- `outcome_unknown` удерживает ключ. «Сверить» запускает только read-only
  проверку; отмена не доказывает, что номер не был записан.

## Изменение конфигурации

`PUT /config` проверяет `scan_interval_days`, `poll_interval_seconds`,
`inventory_freshness_seconds`, `task_ttl_seconds`, `max_files`,
`max_file_bytes`, увеличивает версию и пересчитывает JCS-хеш. Новые агенты
получают поля расписания и обновляют таймер без рестарта; старые получают
прежнюю проекцию без новых полей. UI показывает версию и хеш. Изменение
фиксируется событием `config_changed`.

Папки управляются через отдельные политики с назначениями машинам и группам.
Непустой `cert_directories` в `PUT /config` отклоняется. Новые методы и точные
приоритеты: [Политики папок](folder-policies.md). Флажки таблицы машин позволяют
массово добавить машины в группу; состав группы редактируется отдельно.

## Ограничения и решения

- Админка работает только через HTTPS. HTTP-слушателя нет.
- Для ручного сканирования не требуется менять интервал опроса.
- Старые регистрации после переустановки/переименования остаются в истории,
  но могут быть отозваны администратором; hostname освобождается и
  назначается новой регистрации. Это явное действие, а не автоматическое
  доверие новому ключу.
- Бандл не использует CDN, внешние шрифты, `vue-router` или дополнительные
  JS-чанки.

## Текущий объём: сканирование и автообновление

Удалённая активация КриптоПро временно исключена из продукта по решению
кейсодержателя. Пулы, импорт ключей и создание/выдача установочных заданий
отключены; история и существующие зашифрованные данные БД сохранены. Сбор
сведений о лицензиях и задачи scan продолжают работать.

Таблицы обновляются каждые 15 секунд. Селект «Автообновление» позволяет
выбрать 5, 15, 30, 60 секунд или выключить обновление. Выбор сохраняется
в браузере и действует при переходах между разделами. В скрытой вкладке,
при вводе текста или открытом диалоге опрос приостанавливается. Фоновое
обновление сохраняет страницу, фильтры и выбранные строки; редактируемые
формы настроек не перезагружаются.
