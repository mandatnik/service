# Приёмка P07: первый сквозной результат на CSP 5 и CSP 4

Дата: 2026-11-14. Стенд: Windows 10 `.136` (CSP **5.0.13003**) и `.137`
(CSP **4.0.9963**), Windows Server 2022 `.138` с SQL Server 2019 Express
**15.0.2000.5** и портативным Go-бэкендом.

Агенты — настоящие SCM-службы `TelehackAgent` (LocalSystem, session 0).
Бэкенд — один процесс `telehack-backend.exe` на `.138` (на стенде запущен
планировщиком как SYSTEM; контейнеры/балансировщик не используются).
TLS бэкенда и SQL проверяется по стендовому CA; `TrustServerCertificate`
не является настройкой продукта.

## 1. Полный сбор

| Параметр | `.136` | `.137` |
| --- | --- | --- |
| Служба / identity | SYSTEM, S-1-5-18, session 0 | SYSTEM, S-1-5-18, session 0 |
| Профилей / источников | 5 / 6 | 5 / 6 |
| Сертификатов в первом отчёте | 17 | 16 |
| Уникальных DER на машине | 9 | 8 |
| CSP release / core | 5.0.13003 / 5.0.10013 | 4.0.9963 / 4.0.9019 |
| Тип лицензии (COM raw) | client (0) | server (1) |
| Состояние / срок | active / 2027-02-14 18:59:59 | active / 2027-02-14 18:59:59 |
| Отчёт `scan_seq=1` | complete, applied, 6 источников | complete, applied, 6 источников |

- Незагруженные `user1`/`user2`: по 3 личных сертификата из
  registry-backed MY, прочитаны через временный hive.
- Вошедший `agent`: 5 сертификатов из файлового user-MY.
- `mimbol` (RDP-сессия на `.136`): логическое MY через токен сессии,
  1 реальный сертификат; он не входит в тестовые фикстуры и не изменялся.
- Папка `.cer`: 8 уникальных из 9 файлов (DER, PEM, дубль DER) на каждой
  машине; дубль не создал вторую запись сертификата.
- Один и тот же fixture DER на `.136` и `.137` имеет **одну** строку
  `certificates` и наблюдения на двух машинах. Финальная историческая
  выборка: 8 fixture SHA-256, у каждого `machines=2`, `observation_rows`
  от 2 до 8; после очистки `active_rows=0`.
- Все fixture SHA-256/серийные номера совпадают с `manifest.json`
  (см. P02 evidence: `matches_manifest=true`).

## 2. Частичный отчёт

На `.136` добавлен повреждённый `corrupt.cer` в тестовую папку и создано
ручное задание. Отчёт `scan_seq=2`: `status=partial`, `applied=true`,
6 источников. Повреждённый файл попал в `files[].error`, остальные
сертификаты сохранены; наблюдение сертификата `02-individual-expired`
осталось активным. Задание подтверждено `completed`.

Дополнительно проверена отмена сбора при остановке службы: отменённый
скан не ставится в очередь (после исправления), старые отменённые отчёты
`scan_seq=4/5` имеют `applied=false` и ничего не удалили.

## 3. Очередь из двух отчётов и восстановление сети

- Бэкенд остановлен, тайм-аут агента временно 5 с.
- Три последовательных сбора с интервалом: очередь **1 → 2 → 2**;
  третий сбор вытеснил старейший отчёт (лог:
  `report queue evicted oldest report ...`).
- Бэкенд запущен; агент доставил два последних отчёта (`scan_seq=8`, `9`),
  очередь **0**. Вытесненный `scan_seq=7` на сервере отсутствует —
  обещание доставки каждого промежуточного снимка не даётся.
- identity UUID и machine_id после перезапусков не изменились.

## 4. Конфигурация и ручное задание

- Серверная конфигурация менялась: интервал `1 → 2 → 1`, папка `.cer`
  `test-certs → []`. Агент получил новый `config_hash` и применил его.
- Ручное задание при **неизменном** config hash доставлено в `sync`,
  выполнено (`scan_seq=10`, complete), подтверждено `completed`.
- После удаления папки и установки `cert_directories=[]` финальный
  `scan_seq=13` на `.136` и `scan_seq=4` на `.137` не содержат folder
  source; старые folder-наблюдения корректно деактивированы полным
  пустым сканом папки перед её удалением.
- Максимальные/минимальные лимиты конфигурации проверены unit-тестами и
  серверной валидацией; значения 10 минут/1 день/2 отчёта не меняются
  конфигурацией.

## 5. Перезапуск и replay

- Перезапуск агентской службы: identity, `scan_seq`, очередь и задания
  сохраняются (DPAPI bundle, state/jobs JSON).
- Перезапуск бэкенда: SQL-состояние сохраняется; подписанный запрос,
  использованный до перезапуска, после перезапуска отклонён с
  `replay` (отдельный сценарий `replay-prepare` / `replay-check`).
- Повтор отчёта с прежним `report_id` и новым `request_id` даёт
  `duplicate=true` без повторного применения; тот же `report_id` с
  другим payload — `report_conflict` (contract suite).
- Одновременная отправка двух одинаковых `request_id`: ровно один
  успешен, второй — `replay`.

## 6. Подписанное переименование

На `.136` выполнено реальное переименование Windows:

1. `WORKSTATION-1` → `WORKSTATION-1A`; служба после перезагрузки
   обнаружила изменение hostname, подготовила новый UUID/ключ и
   подписала переход старым ключом.
2. `WORKSTATION-1A` → `WORKSTATION-1`; аналогичный обратный переход.

Итог в БД: один `machine_id` `c7dddc94-...`, три регистрации
`23 (renamed) → 25 (renamed) → 26 (active)`, связи
`previous/replaced_by` сохранены, история машины и наблюдений не
потеряна. Старые UUID после перехода не авторизуют запросы
(`identity_revoked`). Занятое имя при конфликте не перезаписывается,
возвращается `hostname_conflict` (проверено contract suite).

## 7. Пустой успешный отчёт

На `.137` удалены только внесённые фикстуры из `agent` CurrentUser\My,
registry MY `user2` и тестовой папки. После этого реальный агент
сформировал `scan_seq=4`: `status=complete`, `applied=true`, 5 источников,
0 сертификатов. Все ранее активные наблюдения `.137` деактивированы
(`active_obs=0`). Это подтверждает полный успешный пустой результат, а не
ошибку чтения.

На `.136` после удаления фикстур остался один реальный сертификат
`mimbol`; отчёт `partial` из-за недоступного при выгруженном профиле
закрытого формата файлового элемента CryptoPro. Это честное состояние:
фикстурные наблюдения удалены, реальный сертификат не затронут.

## 8. Очистка

- `agent` CurrentUser\My: 5 → 0 на `.136`, 5 → 0 на `.137`.
- `user1`/`user2` registry MY: 3 → удалено; hive выгружен; повторная
  проверка `HKU\Telehack*` — пусто.
- Тестовые папки `.cer` удалены; временные ZIP/манифест/скрипты и
  SQL PFX/пароль удалены со стенда.
- Синтетические `accept-*` hostname-записи удалены; contract suite
  удалил свои машины/отчёты/события/request_id.
- Реальный сертификат `mimbol`, SQL-база/логин, TLS-корень стенда,
  сертификат SQL Server, службы агентов и бэкенд оставлены как рабочее
  развёртывание стенда. Тестовый ГОСТ-корень в доверенные ОС не
  устанавливался.
- После очистки: агенты Running, бэкенд Running, SQL Running,
  `test-certs` отсутствует, `.cer`/MY тестовых пользователей пусты.

## 9. Ограничения и границы доказательства

- Сложный файловый элемент CryptoPro в MY **незагруженного** пользователя
  не разбирается; источник помечается `partial`. Для загруженного
  пользователя используется токен сессии и логическое MY (проверено на
  `mimbol`). Это известное ограничение, а не пустой успешный результат.
- Пустой/запоздавший отчёт и конфликты `report_id`/`request_id` в
  серверной семантике проверены contract suite продуктовым Go-клиентом;
  реальный пустой отчёт дополнительно проверен на `.137`.
- Админка P08, MSI P09, нагрузка 200+ P11 и финальная поставка P12 в
  объём P07 не входят. Конфигурация/задания на стенде задавались
  acceptance-инструментом/БД, а не UI.
- SQLCMD выводит кириллицу в консоль как `?`; в БД поля `NVARCHAR`
  сохраняются корректно, сравнение с манифестом выполнено в P02 evidence.

## 10. Воспроизведение

```bash
# Backend (на .138)
telehack-backend.exe bootstrap -config backend.json   # TELEHACK_SA_PASSWORD
telehack-backend.exe migrate   -config backend.json
telehack-backend.exe run       -config backend.json

# Агент (на .136/.137)
telehack-agent.exe install -config C:\ProgramData\Telehack2026\agent-config.json
telehack-agent.exe start

# Контракт/приёмка (с машины разработчика, CA и DB-пароль в .secrets)
go run ./cmd/acceptance contract -config .secrets/acceptance.json
go run ./cmd/acceptance replay-prepare -config .secrets/acceptance.json
# перезапуск backend
go run ./cmd/acceptance replay-check -config .secrets/acceptance.json
```
