# Приёмка: жизненный цикл установки агента

Проверено на стенде SQL Server 2019 и в собранной админке (backend локально,
HTTPS `127.0.0.1:9444`). Данные существующих машин не очищались; тестовые
фикстуры создавались с префиксами `INSTALL-TEST-`/`UI-*` и удалялись после
проверки.

## Автоматические проверки

```bash
MANDATNIK_POLICY_TEST_CONFIG=/path/to/authorized-acceptance.json \
  go test ./internal/backend/store \
  -run 'Test(AdminIdentity|ListMachinesSummary|Policies|Tasks|InstallationReplacement|MachineRename)SQLServer' \
  -count=1 -v
```

Результат: все тесты прошли, включая:

- обычная повторная регистрация и подписанный `rename` не создают новую
  машину;
- неизвестный UUID с занятым именем создаёт одну заявку, число машин не
  растёт;
- историческая карточка без активной регистрации также требует решения;
- замена сохраняет `machine_id`, группы, политики и отчёты;
- старая регистрация становится `replaced` и не авторизует запросы, новая
  получает ту же карточку;
- новый `scan_seq=1` применяется в новом `scan_epoch`, последним выбирается
  новый отчёт, источники не помечаются устаревшими;
- повторное подтверждение и два одновременных подтверждения создают ровно
  одну активную регистрацию;
- устаревшая или отклонённая заявка не подтверждается;
- задания старой установки: не начатые — `expired`, начатый scan — `failed`,
  начатая установка лицензии — `outcome_unknown`;
- отдельная машина с тем же именем создаётся только явным решением и
  идемпотентна;
- архивная карточка исчезает из действующего списка и находится в фильтре
  «Архивные» с причиной; история и события сохраняются;
- `purgeAgentState(false, …)` сохраняет identity, `purgeAgentState(true, …)`
  удаляет состояние (unit-тест в `internal/agent`).

## Интерфейс

Сценарий в браузере:

1. Войти в админку, открыть «АРМ».
2. В очереди «Ожидают подтверждения» нажать «Рассмотреть».
3. Проверить пару: `machine_id`, старая регистрация, последнее обращение,
   состояние связи; hostname/UUID/отпечаток ключа/IP/время новой установки;
   предупреждение о недавней связи старой установки.
4. Поставить явную галочку и нажать «Заменить установку агента».
5. Убедиться, что сообщение содержит прежний `machine_id`, а в карточке
   старая регистрация отмечена «заменена», новая — «активна», история и
   события сохранены.
6. Проверить фильтр «Архивные»: карточка отображается с бейджем
   «Архивирована», причиной и историей.

Снимки: `.playwright-mcp/ui/ui-install-review.png`,
`ui-install-success.png`, `ui-install-detail.png`, `ui-archive-filter.png`
(вне git, локальная проверка).

## Переименование АРМ

Проверено в таблице через «…» и в карточке кнопкой «Переименовать»:

- имя меняется без изменения hostname, UUID и `machine_id`;
- `display_name_custom=1`, событие `machine_display_name_changed`;
- поиск по новому имени находит карточку;
- пользовательское имя сохраняется после замены установки и подписанного
  `rename` агента;
- пустое имя и управляющие символы отклоняются.

Снимки: `.playwright-mcp/ui/ui-rename-table.png`, `ui-rename-detail.png`.

## Ограничения

- Архивированная карточка не является целью замены: доступны отдельная
  машина или отказ. Операции восстановления архива в интерфейсе нет.
- Если UUID уже зарегистрирован в другой карточке, замена/отдельная
  регистрация отклоняются без частичного слияния истории.
- Старый агент не показывает структурированное состояние ожидания в CLI,
  но получает `installation_pending`, сохраняет идентичность и не обходит
  подтверждение. Новый агент пишет состояние в `registration-state.json` и `diag`.
- Смена пароля/ключей CryptoPro, удаление сертификатов и прочие данные,
  полученные агентом, остаются историей машины и не привязаны к конкретной
  установке.
