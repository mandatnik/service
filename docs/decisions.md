# Принятые технические решения (P01–P07)

Документ фиксирует решения, которые нельзя оставлять скрытыми допущениями.
Он не заменяет требования `TASK.md`/`ARCHITECTURE.md`; при расхождении
приоритет у явных требований пользователя.

## D01. Один Go-модуль, монорепозиторий

Агент, бэкенд, общие контракты и приёмочный клиент живут в одном модуле
`telehack2026`. Причина: контракт не может разойтись между двумя
репозиториями; сборка из одного clone воспроизводима. Агент и бэкенд — разные
`main`-пакеты и разные EXE.

## D02. WinAPI напрямую, без cgo и без runtime-зависимости от cpro-go

`node_modules/cpro-go` изучен. Его публичный API перечисляет только `MY`
текущего процесса; для продукта нужны личные хранилища всех профилей,
временное подключение `NTUSER.DAT` и `CERT_STORE_PROV_REG`. Поэтому адаптер
написан напрямую через WinAPI (`x/sys/windows`, `syscall`) и COM через
`go-ole`. Это тот же WinAPI-путь, что подтверждён исследованием, но без
C#/PowerShell и без cgo. `gost-ca` использован только для генерации тестовых
фикстур (вне продукта); продуктовый разбор X.509 реализован в
`internal/certparse`.

Следствие: `CGO_ENABLED=0`; для кросс-сборки не нужен mingw; зависимости
восстанавливаются из `go.mod/go.sum`, а не из `node_modules`.

## D03. JCS и подпись

JCS — официальная реализация `cyberphone/json-canonicalization` (RFC 8785).
Перед канонизацией собственный сканер отвергает повторяющиеся ключи на любой
глубине, не-UTF-8 и trailing data. Подпись — `ecdsa.SignASN1` над
`SHA-256(JCS(data))`, Base64 standard padded. Публичный ключ — PEM
`PUBLIC KEY`/SPKI, только P-256; fingerprint — SHA-256 SPKI.

## D04. Подписанные method/path и внешний host

`data.method` и `data.path` входят в подпись и сверяются с фактическим
запросом. `host.uuid`/`host.hostname` не подписаны отдельно, но обязаны
совпадать с подписанными `data.uuid`/`data.hostname`; это проверяется до
бизнес-логики.

## D05. request_id и report_id

`request_id` — новый UUID v4 на каждую HTTP-попытку, включая повтор после
потери ответа. `report_id` — постоянный UUID v4 одного результата сбора.
Реестр `request_id` хранится в SQL Server и фиксируется в той же транзакции,
что и операция. TTL нет; очистка допустима только после прекращения
авторизации соответствующей идентичности. Идемпотентность `report_id`
проверяется отдельно по JCS-хешу содержимого.

## D06. Порядок отчётов

У агента устойчивый `scan_seq`, который увеличивается на каждый начатый сбор
и сохраняется в `state.json`. Сервер хранит `last_scan_seq` по каждому
источнику (`machine_id`, `source_type`, `source_key`). Отчёт с меньшим seq
для источника сохраняется, но не применяется к этому источнику. Это позволяет
запоздавшему отчёту не откатывать более новое состояние, но применить
область, которой в новом отчёте не было.

## D07. Полнота по источникам

Источник — личное хранилище конкретного SID или конкретная папка `.cer`.
`complete=true` означает: все сертификаты источника перечислены успешно.
Только для такого источника разрешено помечать отсутствующие сертификаты
удалёнными. Ошибка профиля/файла/COM даёт `complete=false`, отчёт `partial`,
старые наблюдения сохраняются. Пустое успешное хранилище — `complete=true` с
нулём сертификатов; отсутствие ключа MY не создаётся.

## D08. Идентичность и переименование

Первый запуск генерирует UUID v4 и ECDSA P-256 ключ. При изменении hostname
агент генерирует новую пару и сохраняет `pending_rename.json`, затем
подписывает переход старым ключом. Сервер сохраняет `machine_id` и историю,
отзывает старую регистрацию. Если сервер недоступен, агент продолжает работу
со старой идентичностью и повторяет переход. Занятое имя не перезаписывается:
переход принимается с предупреждением и событием администратору.

## D09. DPAPI и права

Идентичность и ключ хранятся в едином `identity.dpapi` под
`%ProgramData%\Telehack2026\Agent`, защищённом DPAPI в user-scope учётной
записи службы (LocalSystem). Единый bundle делает переход при переименовании
атомарным (`os.Rename`); отдельный `identity-public.json` не содержит секретов.
Файлы и каталог получают DACL: только SYSTEM и Administrators, наследование
отключено. При повреждении/потере ключа агент не создаёт молча новую
идентичность: требуется административная команда `reset-identity`, которая
архивирует старое состояние. Это сохраняет историю машины и делает конфликт явным.

## D10. GPO-конфиг

Стартовый файл: `C:\ProgramData\Telehack2026\agent-config.json` (путь можно
переопределить `-config` для стенда). Формат — только адрес сервера и
безопасные тайм-ауты; `insecure_skip_verify` отсутствует. Для ручного запуска
вне домена используется тот же файл. Период опроса 10 минут, интервал сбора
по умолчанию 1 день и лимит очереди 2 не конфигурируются.

## D11. Очередь и задания

Очередь — каталог с JSON-файлами, атомарная запись (tmp + fsync + rename).
Хранятся два последних отчёта; третий вытесняет старейший с записью события.
Состояние заданий (`jobs.json`) хранится отдельно, поэтому подтверждение
завершения не теряется при вытеснении отчёта; статус
`report_evicted` честно сообщает об утрате тела отчёта.

## D12. SQL Server и TLS

Приложение использует отдельную БД (не `master`), создаваемую отдельной
bootstrap-командой. Пароль sa никогда не встраивается: bootstrap читает
`TELEHACK_SA_PASSWORD`, runtime — `TELEHACK_DB_PASSWORD` (имя переменной
задаётся конфигом). TLS к SQL включён; `TrustServerCertificate=true` не
является настройкой по умолчанию. Для стенда выпускается отдельный
RSA TLS-УЦ, его корень указывается в `db.ca_file`; сертификат SQL Server
имеет SAN с IP и именем. Приложение использует `db.server_name` для проверки
имени, не полагаясь на глобальное доверие ОС.

## D13. Hostname/DNS

Source IP берётся из TCP-соединения, не из `X-Forwarded-For`. DNS-проверка
`hostname → A/AAAA` — доверительный сигнал: при совпадении фиксируется
`dns_verified`, при несовпадении/ошибке отчёт всё равно принимается, создаётся
событие. Резервирование имени — таблица `hostnames` с уникальным
нормализованным именем; конфликт не перезаписывает владельца.

## D14. Лицензии CSP

`license_kind` берётся из `CPCSPLicense.GetType`: на проверенных сборках
`0 → client`, `1 → server`. Сырой код, источник и версия сохраняются; иные
коды → `unknown`, без догадок. Тип не выводится из версии CSP/Windows.
`license_state` вычисляется по COM-дате; `valid_to_raw` и
`time_basis=system_local_assumed` сохраняются отдельно. `is_trial` остаётся
`unknown` (нет достоверного Windows API); `term_kind=time_limited` только при
явной читаемой дате окончания. Расхождение COM-срока и SDK-проверки номера не
делает установленную лицензию недействительной.

## D15. Логи

TXT, `current.txt` и `previous.txt` по 10 MiB, timestamp до миллисекунд.
При переполнении previous удаляется, current переименовывается, создаётся
новый current. Секреты, приватные ключи и номера лицензий не пишутся.
Ошибки источников попадают и в лог, и в отчёт как partial, а не превращаются
в пустой успешный отчёт.

## D16. Приёмка

`cmd/acceptance` использует те же `internal/protocol` и `internal/backend/db`,
что и продукт, и проверяет контракт на реальном бэкенде. Стендовые фикстуры
(сертификаты в профилях, папки `.cer`) устанавливаются отдельными
диагностическими скриптами и удаляются после проверки; продуктовый агент
ничего не добавляет в хранилища.
