# Удалённая активация КриптоПро и единая система задач

Дата: 14.11.2026. Статус: согласованное поведение и проект реализации.
Репозиторий: mandatnik. Документ сохраняет решения обсуждения и служит
основным заданием для реализации вместе с `remote-activation-agent-prompt.md`.
Изменения продукта в рамках проектирования не выполняются.

## 1. Цель и границы

Администратор хранит ключи КриптоПро в пулах и назначает задачи выбранным РС.
Первоначальные виды задач: `scan` — форсированный сбор сертификатов и CSP;
`install_license` — установка назначенного ключа КриптоПро на конкретную РС.
Одна общая задача содержит отдельные выполнения на машинах и их параметры.
Результат и журнал доступны как по общей задаче, так и по каждой РС.

Удалённая установка выполняется агентом Windows без окон, диалогов, входа
пользователя, перезагрузки и переустановки CSP. Действующая приобретённая
лицензия не заменяется. Действующий триал можно заменить после ручного выбора РС.
Это не механизм установки самого CSP и не система выполнения произвольных команд.
Закрытые пользовательские ключи, PIN и содержимое контейнеров не передаются серверу.

## 2. Согласованные решения

| Область | Решение |
| --- | --- |
| Пул | Название, CSP 4/5, клиентская/серверная, заявленный срок 1 год/2 года/бессрочно |
| Ввод номеров | По одному или вставкой списка строк; дубликаты запрещены во всей системе |
| Задача установки | Один выбранный пул; несовместимые РС исключаются с объяснением |
| Дефицит ключей | Частичная выдача только после явного выбора получателей администратором |
| Состояния ключа | Свободен, зарезервирован, использован, результат неизвестен, заблокирован |
| Неизвестный результат | Ключ остаётся закреплён за прежней РС, другой машине не выдаётся |
| Сертификаты для рекомендации | Действующие по датам личные сертификаты с подтверждённой привязкой к КриптоПро и без встроенной лицензии |
| Алгоритмы сертификатов | Включая RSA; фильтр «только ГОСТ» запрещён |
| Закрытый ключ | Наличие и доступность сейчас не проверяются; расширение модели предусмотрено |
| Неизвестный провайдер | Четвёртая категория «нужна проверка», если нет более определённого основания классификации |
| Повторы установки | Тот же номер, та же РС; максимум 3 попытки, паузы 30 и 120 секунд |
| Перед повтором | Сначала чтение: уже установленный действующий назначенный номер означает успех без новой записи |
| Действующая приобретённая лицензия | Защищена от замены, список 3, checkbox disabled |
| Действующий триал в списке 1 | Checkbox снят по умолчанию, но доступен для ручного включения |
| Нет действующей лицензии в списке 1 | Checkbox включён по умолчанию |
| Однозначно неверный/несовместимый номер | Автоматически не повторять |
| Опрос сервера | По умолчанию 60 секунд, диапазон 10–3600, настройка в секундах |
| Свежесть инвентаризации | По умолчанию 24 часа, настраивается |
| Ожидание задачи | По умолчанию 7 дней, настраивается; неизвестные установки не освобождают ключи по таймеру |
| Хранение ключей | Зашифрованы в БД; серверный ключ находится в защищённом файле вне БД |
| Передача параметров | Все параметры отдельного выполнения зашифрованы публичным ключом соответствующей РС |
| Доступ сервера к номеру | Разрешён кратковременно для назначения и шифрования |
| UI номеров | Только маска и внутренний ID; раскрытия полного номера и экспорта нет |
| Логи | Агент обязательно пишет события задач; номера и расшифрованные параметры в логи не попадают |

Поля пулов описывают заявленные свойства ключей. Реальный срок после установки
читается из CSP. Не обещать «год с момента назначения»: семантика зависит от лицензии.

## 3. Что уже есть и что требуется изменить

- `internal/protocol/constants.go`: фактический фиксированный опрос — 10 минут,
  не 15. Новая серверная настройка заменяет этот интервал.
- `internal/agent/runtime.go`: синхронный цикл, отдельный таймер работы 30 секунд,
  ограничение повторного сканирования 10 минут. Изменить нужно все эти места,
  а не только константу опроса.
- `internal/backend/store/sync.go`, `jobs.go`: задания `scan` по одной машине,
  повторная доставка до ACK, состояния pending/delivered и конечное подтверждение.
- `internal/agent/state.go`: локальные `jobs.json`; повреждённый журнал сейчас может
  заменяться пустым состоянием. Для установки лицензий такое поведение недопустимо.
- Транспортная идентичность — ECDSA P-256, защищённая DPAPI; это ключ подписи.
  Отдельную пару для шифрования нужно добавить без переиспользования ключа подписи.
- `internal/agent/winapi/certstore_windows.go` и `logicalstore_windows.go` возвращают
  преимущественно DER. Свойства связи с провайдером теряются; одного разбора DER
  для новой классификации недостаточно.
- Текстовые логи уже ротируются: `current.txt` + `previous.txt`, по 10 MiB.
  Сохранить ограничение; расширить состав событий и контекст задач.
- Очередь обычных отчётов ограничена двумя отчётами. Результаты установки и журнал
  попыток не должны исчезать при вытеснении такого отчёта.

## 4. Доказательства на стенде и ограничения

Эксперимент описан в `../research-license-activation.md`. На CSP 4.0.9963 и
5.0.13003 замена `ProductID` из SYSTEM-службы меняла состояние лицензии,
ошибочный номер вызывал ошибки CryptoAPI/COM, исходное значение восстанавливалось.
На WORKSTATION-1 CSP 5 предоставленный пользователем рабочий номер установлен
одной попыткой. CAdES вернул `IsValid=true`, `Type=Client`, `ValidTo=Unlimited`.
Проверены SYSTEM и отдельные пользователи agent/mimbol. Установка общемашинная.

Рабочий путь — нативная запись REG_SZ в 64-битном HKLM:

```text
SOFTWARE\Microsoft\Windows\CurrentVersion\Installer\UserData\S-1-5-18\Products\<PackedProductGUID>\InstallProperties
Value: ProductID
CSP 4: 7AB5E7046046FB044ACD63458B5F481C
CSP 5: 08F19F05793DC7340B8C2621D83E5BE5
```

Перед изменением требуется обнаружить установленный продукт и сверить ветку
с его GUID. Не создавать произвольную ветку для отсутствующего CSP. Предпочтителен
Go/WinAPI-адаптер; исследовательские PowerShell-скрипты не переносить в продукт.

Базовый `CPCSPLicense` содержит только методы чтения. `CAdESCOM.CPLicense`
на CSP 5 дополнительно имеет SetLicense, но этот метод установки не проверен
и CAdES отсутствовал на CSP 4. Обязательную зависимость агента от CAdES не вводить.

Важные ограничения проверки:

- Успешная запись реестра и один успешный CryptAcquireContext не означают активацию.
- Generic HRESULT, включая 0x8009000A/0xFFFFFFFF, не являются универсальным
  доказательством «неверный номер». Без определённого основания это ошибка проверки.
- Нулевая OLE-дата `1899-12-30` на проверенной бессрочной лицензии не означает
  просрочку. Исправление этого случая обязательно до классификации РС.
- Использовать независимую проверку применимости/действительности номера на Windows;
  SDK macOS не является зависимостью или окончательным источником Windows-состояния.
- Действующий разовый ключ из переписки не копировать в код, документацию и тесты,
  не использовать повторно или на другой машине.

## 5. Лицензионные пулы и ключи

### 5.1. Модель

`license_pools`: id, name, csp_major_version (4/5), license_kind (client/server),
term (one_year/two_years/perpetual), archived_at, created_at/by, updated_at.

`licenses`: id, pool_id, encrypted_serial, encryption_key_id, serial_fingerprint,
serial_mask, state, assigned_machine_id, assigned_task_item_id, reserved_at,
used_at, last_error_code, created_at/by. Отдельная история событий не затирается.

`serial_fingerprint` — HMAC-SHA-256 нормализованного номера с отдельным стабильным
ключом дедупликации. Уникальный индекс глобальный, не только внутри пула. Шифрование
и HMAC используют разные ключи. Ротация ключа шифрования не меняет fingerprint.
Ключ дедупликации также находится вне БД и входит в защищённый комплект восстановления.

Нормализация: trim, удалить допустимые разделители, верхний регистр, проверить
ожидаемый формат CSP 4/5. Форматная корректность не равна действительности лицензии.
Выдача — по стабильному порядку добавления, затем ID. Один номер — максимум одна РС.
Не поддерживать многоразовые ключи и счётчики допустимых активаций в первой версии.

### 5.2. Состояния ключа

| Состояние | Семантика |
| --- | --- |
| available | Можно резервировать, номер не выдавался либо достоверно не применялся |
| reserved | Закреплён за одним выполнением и одной РС; ожидается установка/повтор |
| used | Подтверждены назначенный номер и действующая совместимая лицензия |
| outcome_unknown | Применение могло произойти, достоверного результата нет; повторная выдача запрещена |
| blocked | Определённая ошибка номера/несовместимость либо ручная блокировка с причиной |

Резерв и назначение создаются в одной транзакции с task_item. Даже несколько админов
не могут получить один свободный ключ. Ошибка транзакции не оставляет частичный резерв.

Автоматическое возвращение available разрешено только при доказанном отсутствии
разрешения на изменение либо подписанном ответе агента «изменение не выполнялось ни в одной попытке»
при отсутствии прежних неподтверждённых разрешений на изменение.
После возможной записи ключ не возвращается в available по тайм-ауту, отмене,
переустановке агента или удалению РС. Успешно использованный ключ не освобождается,
когда лицензия истекла. Отдельный ключ автоматически взамен ошибочного не назначается.

До выдачи администратор может блокировать свободный ключ, архивировать пул,
переименовать его. Версию/тип/срок пула с добавленными ключами не менять.
Использованные записи и историю не удалять; архивирование сохраняет видимость в задачах.
В этой версии нет произвольного «сбросить использованность» и переноса использованного
ключа на другую машину. Разрешение outcome_unknown выполняется повторной проверкой.

### 5.3. Интерфейс пулов

Раздел «Пулы лицензий»: карточки/таблица пулов, счётчики по всем состояниям,
таблица ключей с маской, РС, задачей, датами и причиной блокировки. Создание пула
и вставка номеров с построчным результатом: принят, дубликат, неверный формат.
Сервер не возвращает исходный номер в ответе импорта и не включает его в ошибки.
Импорт списка атомарен: сначала проверка всех строк; при ошибках предложить удалить
их и подтвердить исправленный список. Не делать скрытого частичного импорта.

## 6. Сертификаты и принадлежность КриптоПро

### 6.1. Провайдер — свойство наблюдения

Один и тот же DER может встречаться в разных профилях, на разных РС и с разными
привязками к ключам. Хранить провайдер в наблюдении сертификата, а не единственным
полем глобальной сущности certificate. Не терять сведения до дедупликации DER.

Предусмотреть `provider_bindings[]` для наблюдения:

- provider_name, provider_api (capi/cng), provider_type, key_spec;
- binding_state (present/absent/unreadable);
- provider_owner (cryptopro/other/unknown), attribution_source, attribution_version;
- private_key_state (not_checked/available/missing/inaccessible), пока not_checked;
- metadata_error_code и время наблюдения.

Читать CERT_KEY_PROV_INFO_PROP_ID до освобождения CERT_CONTEXT; обрабатывать
CAPI и CNG/KSP. Не использовать получение private-key handle для этой задачи,
не проверять PIN и не инициировать диалог носителя. Имена контейнеров и частные
ключи серверу для классификации не нужны.

Атрибуция опирается на реальные сведения о провайдере, зарегистрированном модуле
и проверяемую таблицу поддержанных CryptoPro-провайдеров. Не считать достаточными
issuer сертификата, алгоритм RSA/ГОСТ или случайное вхождение «Crypto» в имени.
Неизвестное имя/непрочитанные свойства дают unknown, а не other.

Поддержать все существующие пути чтения: вошедшие профили, offline hive,
логическое/реестровое/файловое системное хранилище профиля. Сохранить прежнюю
семантику полноты источника. Записи из настроенных папок .cer не участвуют
в решении о необходимости установки: один DER без контекста хранилища не
доказывает связь с КриптоПро. Windows-сериализованный store blob профиля и
произвольный .cer из папки — разные источники, их нельзя смешивать.

### 6.2. Правило необходимости

Подходящий сертификат одновременно:

1. Находится в личном хранилище одного из профилей РС и имеет актуальное наблюдение.
2. Действует по датам: not_before <= момент оценки <= not_after.
3. Имеет хотя бы одну подтверждённую привязку к провайдеру КриптоПро.
4. Не содержит обнаруженной встроенной лицензии CSP.

Наличие встроенной лицензии пока определяется существующим признаком/OID;
это не обещание проверки юридической или криптографической действительности
самой встроенной лицензии. Не расширять проверку до CRL/OCSP и доверия цепочки.
Наличие закрытого ключа не является условием; его состояние остаётся not_checked.
RSA поддерживается наравне с ГОСТ. Обязательный сценарий приёмки — RSA с реальной
привязкой к КриптоПро, а не только синтетическая подстановка имени провайдера.

Неизвестная привязка действующего сертификата без встроенной лицензии создаёт
неопределённость, если нет уже подтверждённого основания необходимости. Если
метаданные отсутствуют по природе сертификата, повторное сканирование может
не помочь: UI должен предлагать диагностику, не бесконечную автоматическую проверку.

## 7. Модалка активации

Кнопка «Активировать лицензию» рядом с «Добавить в группу» в выборе машин.
Запуск также из групп и раздела задач. Начальный набор — объединение выбранных
РС и раскрытых групп с дедупликацией по machine_id. Пустая задача не создаётся.

Одна модалка, один выбранный пул. Показываются версия/тип CSP, последнее
наблюдение, основание классификации, статус подключения и причина исключения.
Несовместимые с пулом РС отдельно перечислены как исключённые, с disabled-контролами.
Они не становятся получателями и не учитываются в требуемом количестве ключей.
Точное соответствие major version 4/5 и client/server; не делать неявных upgrade,
выдачи серверного ключа вместо клиентского или смены срока пула. Неизвестная
совместимость требует проверки. Для Windows Server нужен совместимый серверный
пул; действующие приобретённые лицензии любого типа защищены от замены.
Действующий подтверждённый триал заменяется только после ручного подтверждения.

### 7.1. Четыре списка

Порядок принятия решения для совместимой РС:

| Список | Условие | Чекбокс |
| --- | --- | --- |
| 3. Уже активирована | Достоверно действующая приобретённая (непробная) лицензия по свежим данным | Выключен, disabled; ID отсутствует в финальном запросе |
| 4. Нужна проверка | Нет свежего достоверного состояния CSP; сведения о сертификатах неполны/устарели; либо существенна неизвестная привязка | Выключен, disabled; отдельное назначение scan |
| 1. Нужна активация — без лицензии | Свежий полный сбор; нет действующей лицензии; есть подходящий сертификат | Включён по умолчанию |
| 1. Нужна активация — триал | Свежий полный сбор; есть действующий подтверждённый триал и подходящий сертификат | Снят по умолчанию, enabled; можно включить вручную |
| 2. Можно не активировать | Свежий полный сбор; нет действующей приобретённой лицензии; подходящих сертификатов и существенной неопределённости нет | Выключен; админ может включить |

Свежесть состояния CSP и полноту личных источников учитывать отдельно от ошибок
сканирования произвольных папок: сбой папки не делает автоматически неизвестными
успешно прочитанные личные хранилища. При устаревших/частичных личных сведениях
выбирать список 4, даже если сохранён старый сертификат. Подтверждённая свежая
действующая приобретённая лицензия имеет приоритет и попадает в список 3.

Две строки списка 1 в таблице — подтипы одного визуального списка, не пятый
список. Снятый checkbox у триала не disabled: администратор может включить его
и явно выбрать замену. Просроченная лицензия, в том числе просроченный триал,
не является действующей: при наличии подходящего сертификата это список 1
с checkbox, включённым по умолчанию. Сам факт триала не заменяет условие
необходимости по сертификатам: при их отсутствии и без неопределённости — список 2.

Состояние trial/non-trial определяется отдельным достоверным источником, не
алгоритмом сертификата, client/server, версией ОС или наличием конечной даты.
Если лицензия действительна, но пробность неизвестна, это список 4 с причиной
license_mode_unknown; неизвестную пробность нельзя приравнивать к разрешению
на замену. В этом документе «приобретённая» означает подтверждённую непробную
лицензию; юридическое подтверждение покупки система не проверяет.

В списке 2 в заголовке — select all с indeterminate. Переключает только доступные
строки этого списка. Список 3 нельзя включить через общий выбор или REST вручную.
Для списка 4 кнопка «Проверить» создаёт scan; после результата можно обновить
preview, но активация без нового подтверждения не запускается.

Известное отсутствие CSP — несовместимость/исключение, а не приглашение расходовать
лицензию. Старый агент без необходимых возможностей помечается «нужно обновить
агент»; простое повторное сканирование это не исправит.

### 7.2. Preview и подтверждение

Preview не резервирует номера и не передаёт их браузеру. Возвращает preview_id,
снимок состава групп, основания/категории машин, доступность ключей и срок действия
preview (технический дефолт 10 минут). Выбор пользователя сохраняется при просмотре
списков. При пересчёте изменившиеся основания требуют явного подтверждения.

Финальный REST-запрос содержит pool_id, preview_id, выбранные machine_ids и ключ
идемпотентности. Ни ключей лицензий, ни выключенных строк, ни списка 3 в запросе нет.
Сервер повторяет проверки независимо от UI, проверяет выбранные ID по снимку preview.
Если изменилось состояние, определяющее защиту лицензии или разрешение на замену
триала, возвращает 409 preview_stale, не выполняя скрытой смены согласия.

Если свободных ключей не хватает, модалка показывает «нужно N, свободно M» и требует
снять лишние отметки. Сервер не выбирает получателей за администратора, не ставит
остальные РС в скрытую очередь ожидания пополнения. При конкурентном расходовании
пула подтверждение возвращает 409 с актуальным дефицитом, без частичного создания.

Для выбранной РС, у которой preview показывает действующий триал, сервер
фиксирует разрешение allow_trial_replacement=true в зашифрованных параметрах
item. Оно возникает только после явного выбора такой строки; чекбоксы триалов
не включаются автоматически при пересчёте. Если при выполнении вдруг обнаружен
триал, которого не было в preview, а разрешения нет, агент не меняет лицензию
и сообщает skipped(trial_replacement_not_confirmed). Нужно новое подтверждение.

После подтверждения состав получателей неизменен. Изменение групп не добавляет
и не удаляет машины из уже созданной задачи. Источники выбора сохраняются для аудита.

## 8. Общая задача и выполнение на РС

### 8.1. Сущности

`tasks`: id, kind, created_by/at, expires_at, settings_snapshot,
selection_snapshot, idempotency_key/request_digest, cancel_requested_at.

`task_items`: id, task_id, machine_id, registration_id, kind, state,
reason_code, delivery_version, encryption_key_id, encrypted_parameters,
license_id (nullable), attempt_count, next_attempt_at, started_at, completed_at,
last_seen_at, result_version, sanitized_result, scan_report_id.

`task_item_events`: id, item_id, sequence, attempt_no, event_type, time,
public details. Уникальность (item_id, sequence); журнал переходов добавляется,
а не перезаписывается. Секретных полей в details нет.

`license_assignments`/эквивалентная история закреплений хранит связь лицензия—РС—
выполнение. Уникальные ограничения предотвращают две активные установки лицензий
на одной РС и два активных назначения одного ключа. Дедупликация получателей:
unique(task_id, machine_id). Повтор POST с тем же idempotency_key и тем же телом
возвращает прежнюю задачу; с другим телом — 409.

Не ограничиваться единственным status общей задачи: отдавать счётчики всех
состояний, прогресс и состояние каждого получателя.

### 8.2. Состояния отдельного выполнения

| Состояние | Значение |
| --- | --- |
| queued | Создано, выполнение ещё не разрешено |
| delivered | Агент получил и сохранил; это не подтверждение выполнения |
| running | Сервер разрешил начало; агент выполняет |
| retry_wait | Ожидается очередная попытка с тем же ключом |
| succeeded | Подтверждён результат: для scan принят соответствующий отчёт, для лицензии проверены номер и применимость |
| skipped | Ничего не менялось; например, приобретённый действующий ключ появился до выполнения либо замена триала не была подтверждена |
| failed | Определённая ошибка; повторов больше нет или они неприменимы |
| outcome_unknown | Изменение могло произойти; разрешена дальнейшая проверка, ключ удерживается |
| cancelled | Отмена подтверждена до изменения |
| expired | Истёк срок до возможного изменения |

`cancel_requested` — отдельный признак запроса отмены, а не доказательство cancelled.
`outcome_unknown` останавливает новые изменения после лимита, но допускает позднее
согласование результата только чтением; переход в succeeded/failed журналируется.
Финальный succeeded не может быть затёрт устаревшим отрицательным событием.

### 8.3. Состояние общей задачи

Детерминированно вычислять из items, не обновлять независимыми несвязанными флагами.

- Есть queued/delivered и нет начавшихся items: queued.
- Есть running/retry_wait либо часть завершена, но другие ещё ждут: running.
- Есть outcome_unknown и нет способных сейчас выполняться items: requires_attention.
- Все items succeeded/skipped: completed.
- Все cancelled: cancelled; все expired: expired.
- Все завершены, есть успешные/пропущенные и ошибки/отмены/истечение: partially_failed.
- Все завершены, нет успешных/пропущенных и не подходят случаи выше: failed.

Если ещё есть выполняемые items, одновременно показывать флаг needs_attention
и счётчик неизвестных; не прятать проблему до завершения остальных машин.
Полная задача с нулём получателей не существует.

### 8.4. Отмена и истечение срока

Отмена всей задачи раскладывается на items; отмена одного item тоже поддерживается.
До выдачи разрешения на изменение можно отменить на сервере и освободить резерв.
После выдачи разрешения — cancel_requested и согласование с агентом; не обещать
мгновенную отмену записи реестра. Агент прекращает новые попытки, если запись ещё
не началась, и сообщает did_not_modify. Завершившуюся установку отмена не откатывает.

После 7 дней новые изменения не начинать. Достоверно не начатые items становятся
expired и освобождают резерв; начатые/неопределённые не теряют закрепление.
После срока разрешены доставка сохранённого результата и read-only согласование.
Ни отмена, ни истечение не снимают уже установленную лицензию.

## 9. Доставка, права на начало и восстановление

Сервер доставляет items до подтверждённого результата. Агент сохраняет параметры
и состояние до ACK доставки. Потеря ответа sync не теряет задачу. Каждый item
исполняется по постоянному ID; повторная доставка не создаёт новую попытку.

Перед началом изменяющей операции агент получает серверное разрешение claim/start.
Сервер атомарно проверяет назначение, состояние, отмену, срок и регистрацию.
Одна только доставка зашифрованных параметров не разрешает менять лицензию.
Разрешение ограничено по времени; технический дефолт — 5 минут. При необходимости
продления агент связывается с сервером. После истечения разрешения без связи —
только чтение и сохранение результата, новых записей нет. Таймеры рассчитываются
с учётом server_time; назад переведённые часы не продлевают разрешение.

На РС локальный durable-журнал отдельно от обычной очереди отчётов:
получено → расшифровано/проверено → precheck → intent(attempt_no) → запись → verify
→ сохранён результат → результат принят сервером. До записи persist + flush intent;
счётчик попыток переживает перезапуск. Авария между intent и записью считается
потенциальной попыткой, а не основанием сбросить счётчик.

Если журнал установки повреждён, не создавать пустой журнал и не выполнять
полученный ключ заново вслепую. Остановить изменение, сохранить диагностический
код, согласовать назначение с сервером и выполнить read-only проверку.

Повторы: первая попытка сразу, вторая не ранее 30 секунд после первой,
третья не ранее 120 секунд после второй. Перед каждой — проверка назначенного
номера, действующей лицензии, отмены/срока и полномочий. Даже при временной ошибке
четвёртой попытки в этом item нет. После лимита определённая неуспешность → failed;
если запись могла дать эффект → outcome_unknown. Новый item после ручного решения
не должен автоматически назначать этот номер другой РС.

Сеть, рестарт сервиса и потеря ACK сами по себе не являются неуспешной установкой.
Результаты и ACK отправляются повторно идемпотентно, независимо от повторов записи.
Повторная выдача параметров не изменяет назначенный ключ или адресата.

## 10. Выполнение install_license

1. Проверить адресата, подпись/аутентичность транспортного обмена, task/item IDs,
   версию шифротекста, ключ расшифрования, сроки, параметры и серверное разрешение.
2. Обнаружить установленный CSP и проверить версию, тип окружения и совместимость пула.
3. Прочитать текущий номер и фактическую действительность лицензии.
4. Если уже установлен именно назначенный действующий номер — succeeded без записи.
5. Если действует другой подтверждённый непробный номер — skipped(already_licensed),
   без его замены. Если это подтверждённый действующий триал, продолжать только
   при allow_trial_replacement=true. Иначе skipped(trial_replacement_not_confirmed).
6. Если состояние лицензии нельзя определить — не писать, вернуть проверяемую ошибку/
   необходимость диагностики; резерв удерживается до подтверждения отсутствия изменения.
7. Сохранить исходное значение/тип REG_SZ в DPAPI-защищённой локальной записи.
   Зафиксировать intent, выполнить одну нативную запись нового номера в Registry64.
8. Из свежего контекста проверить совпадение полного номера в памяти с назначенным,
   действительность, client/server, срок и совместимость. Код успеха SetValue не достаточен.
9. При определённом отказе восстановить исходное состояние, только если значение
   всё ещё принадлежит нашей попытке. Не затереть новый номер, установленный извне.
   При конфликте или невозможности доказать результат — outcome_unknown.
10. Сохранить итог и сверку CSP. Немедленно отправить отдельный результат задачи
    и обновление состояния CSP, чтобы UI не ждал суточного сканирования.

Для проверенной бессрочной лицензии нулевая OLE-дата требует корректного term_kind
и state. Независимое подтверждение использовать при наличии; отсутствие CAdES не
должно заставлять устанавливать его автоматически. Контракт проверки постоянной
лицензии на базовом API/поддержанных версиях установить отдельными Windows-тестами.
Если подтверждения недостаточно, возвращать unknown, а не expired или ложный success.

Перед каждым повтором с другой действующей лицензией обращаться как в шаге 5:
непробная защищена, триал требует сохранённого явного разрешения.
Если выполняется тот же item с уже установленным назначенным номером, шаг 4 имеет
приоритет над защитой «действующую приобретённую лицензию не менять».

## 11. Опрос и выполнение scan

Настройки сервера, включаемые в config_hash и возвращаемую конфигурацию:

| Поле | Дефолт | Проверка |
| --- | --- | --- |
| poll_interval_seconds | 60 | integer, 10–3600 |
| inventory_freshness_seconds | 86400 | integer, 60–2592000 (технический диапазон) |
| task_ttl_seconds | 604800 | integer, 60–2592000 (технический диапазон) |

Частота автоматического полного сбора `scan_interval_days` остаётся отдельной.
Настройки видны в админке; сохраняются на сервере, агент использует последний
корректный кэш и безопасный дефолт до регистрации. Некорректное значение не
создаёт busy loop и не подменяет настройки молча.

После получения новой конфигурации таймер опроса обновляется без рестарта службы.
Опрос идёт независимо от долгого сканирования/повторов установки. Применить небольшой
jitter (до ±10%), ограниченный разрешённым диапазоном. Ошибки связи — backoff;
нормальный опрос не превращать в ежедневное сканирование. Начальное получение
нового интервала старым агентом может ждать его старого цикла — это не обещание push.

Ручной scan выполняется при первой возможности после доставки и не ждёт прежнего
10-минутного ограничения scanWanted. Не добавлять лишний 30-секундный шаг ожидания.
Локальные изменяющие/собирающие операции сериализованы; сетевой опрос не блокируется.
Срок старта включает интервал опроса, очередь РС и backoff; «мгновенно» не обещается.

Одновременно пришедшие scan допускается обслужить одним новым полным сбором,
если сбор начат после получения всех этих items. Каждый item имеет свой результат,
связанный с принятым report_id. Старый готовый отчёт не выдавать за результат нового
форсированного scan. При частичном сборе показать complete=false и причины;
состояние задачи succeeded с предупреждениями означает доставленный отчёт,
а не гарантию полноты каждого источника. При вытеснении отчёта до приёма сервером
не сообщать успех: failed(report_evicted) с сохранённым контекстом.

## 12. Шифрование, ключи и доверие

### 12.1. Хранение пула

AES-256-GCM, уникальный случайный nonce на каждое шифрование; version/key_id/nonce/
ciphertext/tag. AAD связывает license_id и неизменяемые характеристики пула.
Защищённый server keyring вне БД, ACL для учётной записи backend и Administrators.
Секреты не помещать в backend.json, ENV-дампы, миграции, тестовые фикстуры и артефакты.
Конфиг содержит только путь/ID. Отсутствие ключа — явная недоступность операций,
без fallback к открытому тексту. Поддержать чтение старых key_id и ротацию без
потери доступа; удаление старого ключа только после перешифрования и проверки.

Восстановление требует резервной копии БД и keyring/HMAC-ключа. Документировать
раздельное защищённое хранение. Утеря keyring не «лечится» генерацией нового ключа
поверх имеющегося. Сервер кратковременно знает номер: это согласованная граница
защиты, а не end-to-end шифрование от самого сервера.

### 12.2. Ключ РС и конверт параметров

Проектное решение: отдельная RSA-3072 пара для шифрования. Использовать стандартные
Go crypto/rsa, crypto/aes, crypto/cipher; не разрабатывать собственную криптографию.
ECDSA P-256 остаётся ключом подписи. Приватный RSA-ключ — в DPAPI-защищённом
состоянии агента с ACL SYSTEM/Administrators. Локальный администратор не входит
в модель противника, от которого этот агент способен скрыть свой рабочий ключ.

Новый публичный ключ и encryption_key_id регистрируются в запросе, подписанном
существующей идентичностью. Запрещено заменять их неподписанным административным
или агентским запросом. Хранить историю ключей и возможности агента.

Все item.parameters, включая scan options и номер лицензии, шифруются JSON-конвертом:
случайный AES-256-GCM content key + RSA-OAEP-SHA256 для его упаковки. Поддержать
version, algorithm, recipient_key_id, wrapped_key, nonce, ciphertext. Параметры
не шифруются непосредственно RSA: их размер может превышать лимит RSA-OAEP.

AAD и OAEP label однозначно связывают protocol/purpose, task_id, item_id,
machine_id, registration_id, kind, params_version, recipient_key_id и expires_at.
Канонизация и кодирование зафиксированы и имеют межсторонние тестовые векторы.
Нельзя переставить шифротекст между задачами/РС, подменить срок или вид операции.
Серверная аутентичность обеспечивается обязательным проверяемым TLS существующего
протокола. AEAD защищает связность полей, но не заменяет доверие серверу.

Публичные поля доставки: IDs, kind, состояние, даты, metadata конверта — не секретны.
Открытого parameters, serial, аргументов командной строки и полного результата
сторонней утилиты в ответах sync/REST нет. Результаты содержат только разрешённые
поля, например candidate_matches, state, term_kind, version, sanitized_error_code.

При ротации/rename не терять ключ расшифрования незавершённых items. Машина,
регистрация и fingerprint адресата закреплены. Для доказанно не начатого задания
можно перевыпустить конверт на новый ключ той же подтверждённой машины с новой
delivery_version. После возможного начала — согласование результата; не менять
получателя или выдавать новый номер автоматически. Переустановка с новой
неподтверждённой идентичностью не наследует секреты старой регистрации.

## 13. REST и агентский протокол

Проектные административные маршруты под `/api/admin/v1/`:

- GET/POST `license-pools`; GET/PATCH `license-pools/{id}` (допустимые поля).
- POST `license-pools/{id}/licenses/import`; GET `license-pools/{id}/licenses`.
- POST `licenses/{id}/block` с причиной; без GET serial и без export.
- POST `tasks/activation-preview` — объединение machine_ids/group_ids, выбранный pool_id.
- POST `tasks` — kind, preview_id/pool_id для установки, machine_ids, idempotency key.
- Для scan POST tasks принимает machine_ids/group_ids и фиксирует объединение.
- GET `tasks`, GET `tasks/{id}`, GET `tasks/{id}/items`, GET `task-items/{id}/events`.
- POST `tasks/{id}/cancel`, POST `task-items/{id}/cancel`.
- POST `task-items/{id}/reconcile` — запрос read-only сверки, не сброс счётчика попыток.
- Настройки добавляются в существующий API настроек, без параллельного источника истины.

Новые агентские сообщения: capability/encryption key registration,
доставка tasks/items, delivery ACK, claim/start, progress/attempt events,
финальный результат и read-only reconciliation. Использовать существующий
подписанный envelope для agent → server, привязку method/path и replay protection.
Не доверять произвольным строковым статусам: сервер проверяет переходы и владельца.

Протокол расширяется с явными возможностями агента и версией DTO. Старые клиенты
используют DisallowUnknownFields: добавление полей в их ответы может сломать sync.
Обязательна стратегия совместимости: старому агенту старый DTO, новому — новое
согласованное представление; либо отдельная версия wire API с миграцией.
До обновления capabilities удалённая установка старому агенту запрещена.

Существующие jobs API и UI перенести на задачи через совместимый адаптер.
Исторический одиночный job становится singleton-задачей с сохранением старого ID
в legacy_job_id; pending/delivered не должны исчезнуть или выполнить новый scan
повторно. На время перехода исключить двойную выдачу через jobs и tasks.
SQL-миграция добавочная, без удаления истории и без изменения выпущенных миграций.
Точный способ версии протокола выбрать по фактическим клиентам и проверить контрактом.

## 14. Интерфейс задач и журналирование

Раздел «Задачи»: фильтры по виду, состоянию, машине/группе, датам; автор, прогресс,
счётчики ожидающих/успешных/ошибок/неопределённых, дата истечения.
Детали: список всех назначенных РС, маска/ID лицензии, стадия, число попыток,
причина ошибки, время последнего события, ссылка на scan report и журнал.
Показывать «частичный результат», «нет связи», «нужно обновление агента»,
«ключ удерживается» как разные основания, а не один общий failed.

Агент пишет минимум: received, decrypted, precheck, start_authorized,
attempt_intent, write_started, write_finished, verification, rollback,
retry_scheduled, skipped, cancelled, expired, result_persisted, result_acknowledged,
reconciliation, journal_corrupted. Контекст: task_id/item_id/machine_id,
license_id, attempt_no, stage, timestamp, duration, event_code, Windows error code.
Номер, даже в маске, в агентский лог не нужен: достаточно license_id.

Значимые переходы и ошибки логируются, пустой успешный poll каждую минуту не должен
вытеснять полезные события. Сохранить ротацию 2 × 10 MiB. Не логировать расшифрованные
JSON, тела запросов импорта/sync, DPAPI-блоки, ключи AES/RSA, пароли, исходные stdout/
stderr с номерами. Маски и ID UI формируются явно. Использовать структурированный
allowlist результата; редактирование регулярным выражением — только дополнительная
защита, а не основной способ убрать секреты.

Сервер ведёт аудит: создание/импорт/блокировка пула и ключа, автор создания задачи,
снимок получателей, резерв/возврат, разрешение на начало, отмена, попытки, смена
состояния, неизвестный результат и его согласование. Журнал не содержит номеров.

## 15. Этапы реализации

1. Зафиксировать DTO/состояния/инварианты, добавить SQL-модель и совместимость jobs.
2. Метаданные провайдера по наблюдениям; RSA/CAPI/CNG, offline/loaded profiles;
   корректная бессрочная лицензия; preview-классификация на актуальных данных.
3. Серверное хранение секретов, дедупликация, пулы, атомарные резервы и настройки.
4. Ключи шифрования РС и конверты, регистрация capabilities и безопасная ротация.
5. Durable-журнал/результаты/claim/reconcile; независимый polling и исполнитель scan.
6. Нативный исполнитель install_license, верификация, восстановление, 3 попытки.
7. UI пулов, модалка, задачи, детали, настройки, аудит.
8. Контрактные/интеграционные/Windows-проверки, сборки, документация и приёмка.

Реализационные решения выше — исходный проект, а не требование конкретного имени
файла. Изменение продукта должно сохранить эти инварианты. Существенное отклонение
в поведении фиксируется явно, а не прячется в коде.

## 16. Обязательные проверки и критерии готовности

- Четыре списка, select-all второго, disabled третьего/четвёртого; IDs третьего
  отсутствуют в POST; подделанный REST не обходит запреты.
- Пересечения групп/РС не дают дубликатов; состав задачи не меняется вслед за группами.
- RSA с реальной CryptoPro binding распознаётся; RSA Microsoft не становится CryptoPro;
  тот же DER с разными bindings не смешивается; unknown и отсутствие метаданных видимы.
- Даты сертификатов, источники, встроенная лицензия, полнота и свежесть проверяются
  отдельно; не учитывать произвольный .cer из папки как CryptoPro binding.
- Конкурентное подтверждение двух задач не выдаёт один ключ двум РС; rollback SQL
  не оставляет orphan reserve; дефицит не вызывает скрытую частичную выдачу.
- РС с действующей приобретённой лицензией исключена на preview, сервере и перед
  записью. Действующий триал с подходящим сертификатом остаётся в списке 1:
  checkbox снят, но enabled; без действующей лицензии checkbox включён. Ручной
  выбор триала даёт явное разрешение замены; пересчёт preview не включает его сам.
  Неизвестная пробность → список 4, а не разрешение записи.
- На одной РС невозможны параллельные установки; поздняя внешняя лицензия не затирается.
- Чужой/изменённый ciphertext, ID, срок, kind, key_id, неверный тег и устаревшая
  delivery_version отклоняются; параметры другой РС расшифровать нельзя.
- Нет plaintext ключа в БД, HTTP-ответах, логах, ошибках, локальном журнале, тестовых
  фикстурах и артефактах. В БД есть только ciphertext/HMAC/mask.
- Потеря sync/ACK, падение до/после записи, повтор доставки, сбой проверки, рестарт
  backend/агента, повреждение jobs/task journal не создают лишней выдачи/безлимитных попыток.
- Три попытки и паузы проверяются детерминированными часами; неверный номер не
  повторяется по одному недокументированному HRESULT; неопределённость удерживает ключ.
- Отмена/истечение до start освобождают резерв; после возможного изменения — не
  освобождают. Claim и отмена проверяются конкурентным тестом.
- Ротация transport/encryption keys и переустановка агента не раскрывают старые
  параметры чужой регистрации, не теряют журнал и не раздают использованные ключи.
- Активационный результат не вытесняется ограниченной очередью отчётов. Scan success
  связан с принятым report_id; частичность и report_evicted отображаются честно.
- Настройка опроса меняется без рестарта, длительный scan не блокирует sync;
  ручной scan не ждёт старые 10 минут; суточный плановый scan остаётся отдельным.
- Бессрочный ключ не отображается как просроченный с датой 1899; пример стенда —
  основание для отдельного meaningful regression test.
- Старый агент продолжает штатный sync/scan через согласованный адаптер; новое
  задание установки ему не выдаётся. Миграция сохраняет прежние jobs.
- Windows CSP 4/5: отрицательный ввод и восстановление без окон в реальной
  SYSTEM-службе на изолированной РС/согласованной копии без действующей лицензии;
  RSA binding; проверка разных пользователей. Новый действующий
  ключ испытывать только при отдельном предоставлении/разрешении, одну РС за раз.
- Выполнены go test ./..., Windows cross-build agent/backend/acceptance, сборка
  frontend, необходимые SQL integration/contract тесты; критические UI-потоки
  проверены в браузере. Не заявлять непроведённый Windows/paid-key E2E как выполненный.
