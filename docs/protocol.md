# Протокол агент ↔ бэкенд, версия 1

Статус: зафиксирован в P01. Изменения, ломающие совместимость, требуют
`protocol_version = "2"` и одновременного обновления агента/бэкенда.

## 1. Транспорт и маршруты

- REST/HTTPS, только исходящие соединения агента. Агент не открывает портов.
- Агентский listener по умолчанию: `https://<backend>:8443`.
- Административный listener: отдельный порт (по умолчанию 8444), в P07 отдаёт
  только `/healthz`; UI — P08.
- Все агентские запросы — `POST` с `Content-Type: application/json`.
- Доверие TLS — системные корневые сертификаты ОС. Отключение проверки
  сертификата не является настройкой продукта.
- Тайм-аут запроса по умолчанию 30 секунд; тело запроса ≤ 16 MiB, отчёт ≤ 8 MiB.

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/agent/v1/register` | первичная регистрация/повтор с прежним ключом |
| POST | `/api/agent/v1/rename` | подписанный переход при переименовании |
| POST | `/api/agent/v1/sync` | конфигурация по хешу + задания |
| POST | `/api/agent/v1/report` | идемпотентная доставка отчёта |
| POST | `/api/agent/v1/jobs/ack` | подтверждение завершения задания |

## 2. Конверт

```json
{
  "data": { "...": "..." },
  "sign": "base64(ASN.1 DER ECDSA signature)",
  "host": { "uuid": "5b0f1c4e-8a4c-4d1e-9f0a-3f0a5d6e7c8b", "hostname": "WORKSTATION-1" }
}
```

`data` — объект, канонизированный по RFC 8785 (JCS), UTF-8. Подписывается
`SHA-256(JCS(data))` алгоритмом ECDSA P-256; результат кодируется ASN.1 DER и
Base64 (standard padded). `host` не входит в подпись, но его `uuid` и
`hostname` обязаны совпадать с подписанными `data.uuid`/`data.hostname`.
Повторяющиеся имена свойств JSON отклоняются на любом уровне вложенности.

Публичный ключ — PEM `PUBLIC KEY` (SPKI DER внутри), только ECDSA P-256.
Идентичность ключа — SHA-256 SPKI DER (lower-case hex).

### 2.1. Общие поля `data`

| Поле | Обязательно | Смысл |
| --- | --- | --- |
| `protocol_version` | да | `"1"` |
| `operation` | да | `register`, `rename`, `sync`, `report`, `job_ack` |
| `request_id` | да | новый UUID v4 на каждую HTTP-попытку |
| `uuid` | да | UUID регистрации, v4 |
| `hostname` | да | текущее имя машины |
| `method` | да | `"POST"` |
| `path` | да | точный путь, например `/api/agent/v1/report` |
| `issued_at` | да | RFC3339Nano, UTC; не является окном действия |
| `agent_version` | да | версия продукта, не версия CSP |
| `os_version` | нет | версия ОС |
| `architecture` | нет | `amd64` и т.п. |

Подпись метода/пути проверяется до бизнес-изменений. Временного окна
действительности запроса нет: защита от повторов — постоянный реестр
`request_id` в SQL Server. Записи не удаляются по произвольному TTL, пока
идентичность может авторизовать старый запрос.

## 3. Регистрация

`data` дополнительно содержит `public_key` (PEM). Подпись проверяется этим же
ключом: это доказывает владение ключом, но не принадлежность машины
организации. Автоматическая регистрация согласована.

Пример:

```json
{
  "data": {
    "protocol_version": "1",
    "operation": "register",
    "request_id": "c3f8b5c1-5d1f-4f2e-9a4c-2a1f9d7e6b30",
    "uuid": "5b0f1c4e-8a4c-4d1e-9f0a-3f0a5d6e7c8b",
    "hostname": "WORKSTATION-1",
    "method": "POST",
    "path": "/api/agent/v1/register",
    "issued_at": "2026-11-14T10:00:00.123Z",
    "agent_version": "0.1.0",
    "os_version": "Windows 10 19045.7807",
    "architecture": "amd64",
    "public_key": "-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----\n"
  },
  "sign": "MEUCIQ...",
  "host": { "uuid": "5b0f1c4e-8a4c-4d1e-9f0a-3f0a5d6e7c8b", "hostname": "WORKSTATION-1" }
}
```

Ответ `200`:

```json
{
  "machine_id": "0f9d3a2e-7b1c-4a55-9e44-2d9a7f6c1b20",
  "uuid": "5b0f1c4e-8a4c-4d1e-9f0a-3f0a5d6e7c8b",
  "hostname": "WORKSTATION-1",
  "registered_at": "2026-11-14T10:00:00.456Z",
  "config": {
    "version": 1,
    "scan_interval_days": 1,
    "cert_directories": [],
    "recursive": true,
    "max_files": 2000,
    "max_file_bytes": 10485760
  },
  "config_hash": "64-char-lower-hex",
  "server_time": "2026-11-14T10:00:00.456Z",
  "warnings": []
}
```

### 3.1. Матрица идентичностей

| Ситуация | Поведение |
| --- | --- |
| новый UUID + новый ключ + свободное имя | новая машина, автоматическая регистрация |
| новый UUID + новое имя, совпадающее с текущим именем, исторической регистрацией или архивной карточкой | `409 installation_pending`; создаётся одна заявка, машина не создаётся |
| известный UUID + прежний ключ + то же имя | повтор допустим, дубль не создаётся |
| известный UUID + другой ключ | `409 key_conflict`, автоматической замены нет |
| известный UUID + прежний ключ + другое имя | `409 hostname_mismatch`, требуется подписанный `rename` |
| новый UUID + ранее использованный ключ | регистрация разрешена после обычных проверок имени; история не переносится |
| ожидающая заявка + тот же UUID и ключ | обновляется та же заявка; `request_version` растёт только при изменении отображаемых данных |
| ожидающая заявка + тот же UUID, другой ключ | `409 key_conflict`; содержимое заявки не меняется |
| отклонённая заявка + тот же UUID | `403 installation_rejected`; идентичность агента сохраняется, нужен `reset-identity` |

Совпадение имени, IP, DNS или аппаратных признаков — только сигнал
администратору. Оно никогда не разрешает автоматическое объединение.

### 3.2. Подтверждение установки

Заявка создаётся только подписанным запросом `register`; сервер проверяет
подпись ключом из `public_key` и сохраняет только публичный ключ,
отпечаток SHA-256 и метаданные. Закрытый ключ не передаётся.

Пока заявка ожидает решения, регистрация не создаётся: `sync`, `report`,
`capabilities` и `tasks/*` для этого UUID отвечают `unknown_identity`.
Новый агент показывает состояние ожидания, повторяет `register` не чаще
раза в 5 минут и сохраняет свою идентичность. Старый агент получает тот же
`409 installation_pending` и повторяет регистрацию по своему обычному
интервалу; обхода подтверждения нет.

Администратор подтверждает пару `request_id + request_version +
key_fingerprint + machine_id + old_registration_id`. Если заявка изменилась
или сменилась активная регистрация, сервер возвращает
`409 installation_stale`. Повторное подтверждение той же пары
идемпотентно. Для одной машины база данных допускает только одну активную
регистрацию (`UQ_registrations_one_active`).

Возможные решения: заменить установку у выбранной карточки (сохраняется
`machine_id`), создать отдельную машину с тем же именем (явное разрешение
конфликта) или отклонить заявку. Ручная связь с карточкой при отличающемся
имени доступна из карточки машины.


## 4. Переименование

`rename` подписывается **старой** идентичностью (`host.uuid` = прежний UUID).
`data` содержит `new_uuid`, `new_hostname`, `new_public_key`. Сервер проверяет
старый ключ, создаёт новую регистрацию в том же `machine_id`, копирует историю
и отзывает старую регистрацию. Старый UUID после этого не авторизует запросы.

- Новая пара UUID/ключ генерируется агентом заранее и сохраняется в
  `pending_rename.json`; при недоступности сервера переход повторяется.
- Занятое новое имя не блокирует переход, но возвращается
  `warnings:["hostname_conflict"]` и создаётся событие. Молчаливого захвата
  чужой записи нет.
- Совпадение публичного ключа само по себе не объединяет машины.

## 5. Синхронизация, конфигурация, задания

`data`: `config_hash` (опционально, 64 lower-case hex).

Ответ `200`:

```json
{
  "server_time": "2026-11-14T10:10:00.000Z",
  "config": { "...": "..." },
  "config_hash": "64-char-lower-hex",
  "jobs": [
    { "job_id": "6f1c2d3e-4a5b-4c6d-8e9f-0a1b2c3d4e5f", "kind": "scan", "created_at": "2026-11-14T10:05:00.000Z" }
  ],
  "warnings": []
}
```

- `config` присутствует только при изменении; `config_hash` — всегда.
- `jobs` возвращаются **всегда**, даже при неизменном `config_hash`.
- Кэш конфигурации не блокирует задания.
- Опрос — раз в 10 минут; ручная команда доставляется на ближайшем опросе.

## 6. Отчёт

`data` содержит `report_id` (UUID v4), `scan_seq` (устойчивый счётчик сбора),
`collected_at` (начало сбора) и `report` — объект отчёта. Поля
`report.report_id`, `report.scan_seq`, `report.collected_at` должны совпадать с
подписанными.

Каждый `request_id` новый на попытку; `report_id` постоянен при повторной
доставке. Сервер:

1. проверяет подпись/идентичность/путь;
2. в одной транзакции фиксирует `request_id` и обрабатывает отчёт;
3. при существующем `report_id` с тем же JCS-хешем возвращает
   `duplicate:true` без повторного применения;
4. при существующем `report_id` с другим содержимым — `409 report_conflict`;
5. применяет наблюдения по каждому источнику только если
   `(scan_epoch, scan_seq)` больше сохранённой пары этого источника. Запоздавший
   отчёт сохраняется, но не откатывает более новое состояние. `scan_epoch`
   увеличивается при подписанном переименовании и при подтверждённой замене
   установки, поэтому новая установка может начать `scan_seq` с 1;
6. удаляет прежние наблюдения источника только при `complete:true` этого
   источника и отсутствии сертификата в новом полном результате.

Ответ:

```json
{
  "accepted": true,
  "duplicate": false,
  "applied": true,
  "report_id": "0d9c8b7a-6f5e-4d3c-2b1a-0f9e8d7c6b5a",
  "received_at": "2026-11-14T10:01:00.000Z",
  "reason": "",
  "warnings": []
}
```

### 6.1. Полнота и исчезновение

Полнота задаётся по конкретному источнику: личное хранилище SID или папка
`.cer`. `profiles_complete` описывает перечисление профилей, `csp.complete` —
сбор CSP. Отчёт `partial`, если хотя бы один из этих флагов `false`.
Отсутствующее хранилище MY — успешный пустой источник; отказ доступа — partial.
Повреждённый `.cer` делает папку partial. Пустой успешный отчёт применяется и
может удалить ранее известные наблюдения только в полных источниках.

`status` отчёта обязан совпадать с вычисленным из флагов; сервер проверяет это.

### 6.2. Инвентаризация лицензий CSP

Поле `csp.licenses` — массив текущих лицензий продуктов, установленных на
машине. Новый агент передаёт его всегда, в том числе пустым массивом; пустой
массив успешного сбора очищает прежние строки. Старый агент поле не передаёт,
и сервер не меняет уже сохранённую инвентаризацию. Если COM-сбор лицензии
завершился ошибкой (`license.state=error` или ошибка `GetType`/
`GetExpireDate`), сервер сохраняет последнее известное состояние, а не
удаляет его по пустому массиву.

```json
{
  "license_id": "cc4036b72546fa95edf6de0c9196e60153f72212a1eae180aaef208fb8b06e0d",
  "serial_masked": "99999X00000999ZZZZZ0*****",
  "product": "csp",
  "product_code": 0,
  "product_name": "CryptoPro CSP",
  "kind": "client",
  "kind_raw": "0",
  "state": "active",
  "term_kind": "perpetual",
  "valid_to_utc": "2027-02-14T13:59:59Z",
  "complete": true
}
```

- `product`: `csp` (0), `ocsp` (1), `tsp` (2).
- `license_id = SHA-256(serial_masked)` в нижнем регистре. `serial_masked` —
  нормализованный номер без `-`/пробелов, в верхнем регистре, последние пять
  символов заменены на `*****`.
- Полный номер не передаётся и не логируется. Если номер отсутствует, короче
  пяти символов или не читается, запись не создаётся, а машина получает
  `license_status=unknown`.
- Одна текущая лицензия на продукт на машину. При новом полном отчёте
  прежняя запись продукта заменяется; одинаковый номер на двух машинах —
  конфликт, автоматического объединения нет.

## 7. Подтверждение задания

`data`: `job_id`, `job_status` (`completed`, `failed`, `report_evicted`),
`job_report_id` (опционально), `job_message` (опционально). Подтверждение
идемпотентно и не зависит от того, доставлен ли сам отчёт: состояние задания
хранится отдельно от двухэлементной очереди отчётов.

## 8. Ошибки

```json
{ "error": { "code": "replay", "message": "request_id has already been used" } }
```

| HTTP | Код | Смысл |
| --- | --- | --- |
| 400 | `invalid_json`, `invalid_envelope` | структура/JSON/дубликаты ключей |
| 400 | `invalid_signature`, `invalid_curve`, `invalid_key` | криптография/формат ключа |
| 401 | `unknown_identity`, `identity_revoked`, `invalid_identity` | нет активной регистрации |
| 409 | `replay` | `request_id` уже использован |
| 409 | `report_conflict` | тот же `report_id`, другое содержимое |
| 409 | `key_conflict`, `uuid_conflict`, `hostname_mismatch` | конфликт идентичности |
| 409 | `installation_pending` | установка ожидает решения администратора |
| 409 | `installation_stale` | заявка или активная регистрация изменились после просмотра |
| 409 | `installation_conflict` | заявка уже решена или UUID уже зарегистрирован в другой карточке |
| 403 | `installation_rejected` | заявка отклонена; нужен сброс идентичности |
| 409 | `license_deficit` | свободных ключей меньше выбранных получателей |
| 409 | `preview_stale`, `preview_invalid` | снимок preview истёк/изменился/уже использован |
| 409 | `idempotency_conflict`, `task_conflict`, `machine_busy` | конфликт идемпотентности/состояния/активной установки |
| 422 | `machine_not_eligible` | выбранная машина не входит в разрешённый список |
| 503 | `license_key_unavailable`, `agent_encryption_key_missing` | нет keyring или ключа РС |
| 413 | `payload_too_large` | превышен лимит |
| 422 | `report_invalid`, `config_invalid` | семантическая ошибка |
| 500 | `internal_error`, `database_error` | внутренняя ошибка; повтор допустим |

## 9. Ограничения

- `request_id`, `report_id`, UUID регистрации — v4.
- Имя хоста: 1–253 байта, DNS-метки, без пробелов; сравнение без учёта регистра.
- `scan_seq` — неотрицательное целое, монотонно растёт локально.
- Отчёт: ≤ 256 профилей, ≤ 256 источников, ≤ 5000 сертификатов, ≤ 8 MiB.
- Один сертификат в отчёте: DER ≤ 1 MiB, SHA-256 сверяется сервером.
- Очередь агента: ровно 2 последних отчёта; вытеснение старого явное.
- Логи: `current.txt`/`previous.txt` по 10 MiB, TXT, без сжатия.

## 10. Задачи, возможности агента и шифрование параметров

Протокол версии 1 расширен добавочными операциями. Старые агенты продолжают
использовать `/sync`, `/report` и `/jobs/ack` с прежними DTO; новые поля им не
отправляются. Новый агент после регистрации вызывает `/capabilities`, затем
получает задания через `/tasks/*`. Это позволяет не ломать
`DisallowUnknownFields` у старых клиентов.

### 10.1. Возможности и ключ шифрования

`POST /api/agent/v1/capabilities`, `operation=capabilities`, подписывается
существующей ECDSA P-256 идентичностью.

```json
{
  "capabilities": ["task_v1", "schedule_v2", "install_license_v1", "scan_v1", "rsa_oaep_sha256_aes_256_gcm_v1"],
  "encryption_key_id": "64-char-lower-hex",
  "encryption_public_key": "-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----\n",
  "encryption_algorithm": "RSA-OAEP-SHA256+AES-256-GCM",
  "encryption_bits": 3072,
  "encryption_key_rotate": false
}
```

- RSA-ключ 3072 бита, отдельный от ECDSA-подписи; `key_id` — SHA-256 SPKI.
- Первый ключ регистрируется без ротации. Другой ключ при уже активном
  принимается только с `encryption_key_rotate=true`; запрос всё равно подписан
  старой идентичностью. Старые ключи остаются в истории для незавершённых
  конвертов.
- Ответ содержит `accepted`, `server_time`, полную конфигурацию с
  `poll_interval_seconds`, `inventory_freshness_seconds`, `task_ttl_seconds`,
  `config_hash`, `task_ttl_seconds`.
- Агент без `task_v1`/`install_license_v1` не получает задание установки.

### 10.2. Конверт параметров

Каждый `task_item.parameters`, включая scan options, передаётся только как:

```json
{
  "version": 1,
  "algorithm": "RSA-OAEP-SHA256+AES-256-GCM",
  "recipient_key_id": "64-hex",
  "wrapped_key": "base64",
  "nonce": "base64(12 bytes)",
  "ciphertext": "base64"
}
```

`RSA-OAEP-SHA256` упаковывает случайный AES-256 content key; AES-256-GCM
шифрует JSON параметров. OAEP label и AEAD AAD — один и тот же канонический
JSON (RFC 8785) со всеми полями:

```json
{
  "protocol": "telehack2026/task-parameters/v1",
  "purpose": "task_item_parameters",
  "task_id": "uuid",
  "item_id": "uuid",
  "machine_id": "uuid",
  "registration_id": 42,
  "kind": "scan|install_license",
  "parameters_version": 1,
  "recipient_key_id": "64-hex",
  "expires_at": "RFC3339Nano"
}
```

Перестановка ciphertext между задачами, машинами, видами, ключами или сроками
отклоняется. Номер лицензии находится только внутри ciphertext; сервер
расшифровывает его из защищённого keyring на время назначения, а агент — своим
RSA-ключом. В HTTP-ответах и логах номера нет.

### 10.3. Доставка, ACK, claim, progress, result

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/agent/v1/tasks/sync` | элементы задач с конвертами |
| POST | `/api/agent/v1/tasks/ack` | durable delivery ACK |
| POST | `/api/agent/v1/tasks/claim` | разрешение на начало (5 минут) |
| POST | `/api/agent/v1/tasks/progress` | allowlist-события попытки |
| POST | `/api/agent/v1/tasks/result` | финальный/промежуточный результат |
| POST | `/api/agent/v1/tasks/diagnostic` | повреждение локального журнала |

`tasks/sync` возвращает только публичные поля: `task_id`, `item_id`,
`machine_id`, `registration_id`, `kind`, `state`, `delivery_version`,
`encryption_key_id`, конверт, `created_at`, `expires_at`, `cancel_requested`,
`reconcile_requested`, `attempt_count`. Состояние `delivered` после ACK не
означает выполнение. До `claim` изменяющая операция запрещена. `claim`
атомарно проверяет владельца, назначение, отмену, срок, попытки и резерв
лицензии; после истечения claim разрешены только чтение и сохранение
результата.

`tasks/result` содержит только разрешённые поля (`state`, `reason_code`,
`modified`, `serial_match`, `report_id`, санитизированное состояние CSP).
`modified` — `no|maybe|yes`; сервер по нему решает, можно ли вернуть ключ в
`available`. `outcome_unknown` удерживает ключ и допускает только read-only
согласование. Повтор результата с тем же `result_version` идемпотентен;
финальный `succeeded` не перезаписывается поздним отрицательным событием.

### 10.4. Настройки и совместимость

`poll_interval_seconds` (60, 10–3600), `inventory_freshness_seconds`
(86400, 60–2592000), `task_ttl_seconds` (604800, 60–2592000) участвуют в
`config_hash` только для агентов с `schedule_v2`. Для старого агента сервер
отдаёт прежнюю проекцию конфигурации и прежний хеш; поля с `omitempty` не
появляются в его JSON. `scan_interval_days` остаётся отдельной настройкой
планового сбора.

Исторические `jobs` мигрируются в `tasks` с `legacy_job_id`. Старый агент
продолжает получать их через `/sync`; агент с `task_v1` получает тот же item
через `/tasks/sync`, а старый jobs-канал для него исключается. Двойная выдача
одного scan исключена.

### 10.5. Замена установки и старые задания

Замена установки — не `rename` и не `rebind`: это новая установка с новым
UUID и ключом на той же карточке `machine_id`. В одной транзакции старая
регистрация переходит в `replaced`, новая становится `active`, связи
`previous_registration_id`/`replaced_by_registration_id` фиксируются,
hostname переназначается, а решение по заявке записывается с администратором
и временем.

Старые возможности и ключи шифрования не копируются. Новая установка не
получает доступ к заданиям старой: сервер проверяет и `machine_id`, и
`registration_id` элемента задачи. Политика незавершённых элементов:

- `queued`/`delivered`/`retry_wait` без начала — `expired`
  (`registration_replaced`), резерв лицензии освобождается; legacy job —
  `canceled`;
- начатый `scan` (`running`, `started_at` заполнен) — `failed`
  (`registration_replaced`); legacy job — `failed`;
- начатый `install_license` — `outcome_unknown`, ключ остаётся зарезервирован
  для read-only сверки; успех, отмена или автоматический повтор не
  выставляются;
- уже терминальные элементы не переписываются.

Новая установка начинает локальный `scan_seq` заново. Сервер хранит
`scan_epoch` регистрации и пару `(scan_epoch, scan_seq)` для источников,
наблюдений и CSP, поэтому первый отчёт новой установки применяется и
корректно выбирается как последний. Отчёты, пользователи, сертификаты,
события, группы и политики остаются историей той же машины.
