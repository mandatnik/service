# Протокол агент ↔ бэкенд, версия 1

Статус: зафиксирован в P01. Изменения, ломающие совместимость, требуют
`protocol_version = "2"` и одновременного обновления агента/бэкенда.

## 1. Транспорт и маршруты

- REST/HTTPS, только исходящие соединения агента. Агент не открывает портов.
- Агентский listener по умолчанию: `https://<backend>:8443`.
- Административный listener: отдельный порт (по умолчанию 8444), в P07 отдаёт
  только `/healthz`; UI — P08.
- Все агентские запросы — `POST` с `Content-Type: application/json`.
- Доверие TLS — системные корневые сертификаты ОС. Отключение проверки
  сертификата не является настройкой продукта.
- Тайм-аут запроса по умолчанию 30 секунд; тело запроса ≤ 16 MiB, отчёт ≤ 8 MiB.

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/agent/v1/register` | первичная регистрация/повтор с прежним ключом |
| POST | `/api/agent/v1/rename` | подписанный переход при переименовании |
| POST | `/api/agent/v1/sync` | конфигурация по хешу + задания |
| POST | `/api/agent/v1/report` | идемпотентная доставка отчёта |
| POST | `/api/agent/v1/jobs/ack` | подтверждение завершения задания |

## 2. Конверт

```json
{
  "data": { "...": "..." },
  "sign": "base64(ASN.1 DER ECDSA signature)",
  "host": { "uuid": "5b0f1c4e-8a4c-4d1e-9f0a-3f0a5d6e7c8b", "hostname": "WORKSTATION-1" }
}
```

`data` — объект, канонизированный по RFC 8785 (JCS), UTF-8. Подписывается
`SHA-256(JCS(data))` алгоритмом ECDSA P-256; результат кодируется ASN.1 DER и
Base64 (standard padded). `host` не входит в подпись, но его `uuid` и
`hostname` обязаны совпадать с подписанными `data.uuid`/`data.hostname`.
Повторяющиеся имена свойств JSON отклоняются на любом уровне вложенности.

Публичный ключ — PEM `PUBLIC KEY` (SPKI DER внутри), только ECDSA P-256.
Идентичность ключа — SHA-256 SPKI DER (lower-case hex).

### 2.1. Общие поля `data`

| Поле | Обязательно | Смысл |
| --- | --- | --- |
| `protocol_version` | да | `"1"` |
| `operation` | да | `register`, `rename`, `sync`, `report`, `job_ack` |
| `request_id` | да | новый UUID v4 на каждую HTTP-попытку |
| `uuid` | да | UUID регистрации, v4 |
| `hostname` | да | текущее имя машины |
| `method` | да | `"POST"` |
| `path` | да | точный путь, например `/api/agent/v1/report` |
| `issued_at` | да | RFC3339Nano, UTC; не является окном действия |
| `agent_version` | да | версия продукта, не версия CSP |
| `os_version` | нет | версия ОС |
| `architecture` | нет | `amd64` и т.п. |

Подпись метода/пути проверяется до бизнес-изменений. Временного окна
действительности запроса нет: защита от повторов — постоянный реестр
`request_id` в SQL Server. Записи не удаляются по произвольному TTL, пока
идентичность может авторизовать старый запрос.

## 3. Регистрация

`data` дополнительно содержит `public_key` (PEM). Подпись проверяется этим же
ключом: это доказывает владение ключом, но не принадлежность машины
организации. Автоматическая регистрация согласована.

Пример:

```json
{
  "data": {
    "protocol_version": "1",
    "operation": "register",
    "request_id": "c3f8b5c1-5d1f-4f2e-9a4c-2a1f9d7e6b30",
    "uuid": "5b0f1c4e-8a4c-4d1e-9f0a-3f0a5d6e7c8b",
    "hostname": "WORKSTATION-1",
    "method": "POST",
    "path": "/api/agent/v1/register",
    "issued_at": "2026-11-14T10:00:00.123Z",
    "agent_version": "0.1.0",
    "os_version": "Windows 10 19045.7807",
    "architecture": "amd64",
    "public_key": "-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----\n"
  },
  "sign": "MEUCIQ...",
  "host": { "uuid": "5b0f1c4e-8a4c-4d1e-9f0a-3f0a5d6e7c8b", "hostname": "WORKSTATION-1" }
}
```

Ответ `200`:

```json
{
  "machine_id": "0f9d3a2e-7b1c-4a55-9e44-2d9a7f6c1b20",
  "uuid": "5b0f1c4e-8a4c-4d1e-9f0a-3f0a5d6e7c8b",
  "hostname": "WORKSTATION-1",
  "registered_at": "2026-11-14T10:00:00.456Z",
  "config": {
    "version": 1,
    "scan_interval_days": 1,
    "cert_directories": [],
    "recursive": true,
    "max_files": 2000,
    "max_file_bytes": 10485760
  },
  "config_hash": "64-char-lower-hex",
  "server_time": "2026-11-14T10:00:00.456Z",
  "warnings": []
}
```

### 3.1. Матрица идентичностей

| Ситуация | Поведение |
| --- | --- |
| новый UUID + новый ключ | новая машина, автоматическая регистрация |
| известный UUID + прежний ключ + то же имя | повтор допустим, дубль не создаётся |
| известный UUID + другой ключ | `409 key_conflict`, автоматической замены нет |
| известный UUID + прежний ключ + другое имя | `409 hostname_mismatch`, требуется подписанный `rename` |
| новый UUID + ранее использованный ключ | регистрация разрешена, событие `public_key_reused`; история не переносится |
| имя занято другой активной регистрацией | регистрация принимается, `warnings:["hostname_conflict"]`, событие администратору; владелец имени не перезаписывается |

## 4. Переименование

`rename` подписывается **старой** идентичностью (`host.uuid` = прежний UUID).
`data` содержит `new_uuid`, `new_hostname`, `new_public_key`. Сервер проверяет
старый ключ, создаёт новую регистрацию в том же `machine_id`, копирует историю
и отзывает старую регистрацию. Старый UUID после этого не авторизует запросы.

- Новая пара UUID/ключ генерируется агентом заранее и сохраняется в
  `pending_rename.json`; при недоступности сервера переход повторяется.
- Занятое новое имя не блокирует переход, но возвращается
  `warnings:["hostname_conflict"]` и создаётся событие. Молчаливого захвата
  чужой записи нет.
- Совпадение публичного ключа само по себе не объединяет машины.

## 5. Синхронизация, конфигурация, задания

`data`: `config_hash` (опционально, 64 lower-case hex).

Ответ `200`:

```json
{
  "server_time": "2026-11-14T10:10:00.000Z",
  "config": { "...": "..." },
  "config_hash": "64-char-lower-hex",
  "jobs": [
    { "job_id": "6f1c2d3e-4a5b-4c6d-8e9f-0a1b2c3d4e5f", "kind": "scan", "created_at": "2026-11-14T10:05:00.000Z" }
  ],
  "warnings": []
}
```

- `config` присутствует только при изменении; `config_hash` — всегда.
- `jobs` возвращаются **всегда**, даже при неизменном `config_hash`.
- Кэш конфигурации не блокирует задания.
- Опрос — раз в 10 минут; ручная команда доставляется на ближайшем опросе.

## 6. Отчёт

`data` содержит `report_id` (UUID v4), `scan_seq` (устойчивый счётчик сбора),
`collected_at` (начало сбора) и `report` — объект отчёта. Поля
`report.report_id`, `report.scan_seq`, `report.collected_at` должны совпадать с
подписанными.

Каждый `request_id` новый на попытку; `report_id` постоянен при повторной
доставке. Сервер:

1. проверяет подпись/идентичность/путь;
2. в одной транзакции фиксирует `request_id` и обрабатывает отчёт;
3. при существующем `report_id` с тем же JCS-хешем возвращает
   `duplicate:true` без повторного применения;
4. при существующем `report_id` с другим содержимым — `409 report_conflict`;
5. применяет наблюдения по каждому источнику только если
   `scan_seq > last_applied_scan_seq` этого источника. Запоздавший отчёт
   сохраняется, но не откатывает более новое состояние;
6. удаляет прежние наблюдения источника только при `complete:true` этого
   источника и отсутствии сертификата в новом полном результате.

Ответ:

```json
{
  "accepted": true,
  "duplicate": false,
  "applied": true,
  "report_id": "0d9c8b7a-6f5e-4d3c-2b1a-0f9e8d7c6b5a",
  "received_at": "2026-11-14T10:01:00.000Z",
  "reason": "",
  "warnings": []
}
```

### 6.1. Полнота и исчезновение

Полнота задаётся по конкретному источнику: личное хранилище SID или папка
`.cer`. `profiles_complete` описывает перечисление профилей, `csp.complete` —
сбор CSP. Отчёт `partial`, если хотя бы один из этих флагов `false`.
Отсутствующее хранилище MY — успешный пустой источник; отказ доступа — partial.
Повреждённый `.cer` делает папку partial. Пустой успешный отчёт применяется и
может удалить ранее известные наблюдения только в полных источниках.

`status` отчёта обязан совпадать с вычисленным из флагов; сервер проверяет это.

## 7. Подтверждение задания

`data`: `job_id`, `job_status` (`completed`, `failed`, `report_evicted`),
`job_report_id` (опционально), `job_message` (опционально). Подтверждение
идемпотентно и не зависит от того, доставлен ли сам отчёт: состояние задания
хранится отдельно от двухэлементной очереди отчётов.

## 8. Ошибки

```json
{ "error": { "code": "replay", "message": "request_id has already been used" } }
```

| HTTP | Код | Смысл |
| --- | --- | --- |
| 400 | `invalid_json`, `invalid_envelope` | структура/JSON/дубликаты ключей |
| 400 | `invalid_signature`, `invalid_curve`, `invalid_key` | криптография/формат ключа |
| 401 | `unknown_identity`, `identity_revoked`, `invalid_identity` | нет активной регистрации |
| 409 | `replay` | `request_id` уже использован |
| 409 | `report_conflict` | тот же `report_id`, другое содержимое |
| 409 | `key_conflict`, `uuid_conflict`, `hostname_mismatch` | конфликт идентичности |
| 413 | `payload_too_large` | превышен лимит |
| 422 | `report_invalid`, `config_invalid` | семантическая ошибка |
| 500 | `internal_error`, `database_error` | внутренняя ошибка; повтор допустим |

## 9. Ограничения

- `request_id`, `report_id`, UUID регистрации — v4.
- Имя хоста: 1–253 байта, DNS-метки, без пробелов; сравнение без учёта регистра.
- `scan_seq` — неотрицательное целое, монотонно растёт локально.
- Отчёт: ≤ 256 профилей, ≤ 256 источников, ≤ 5000 сертификатов, ≤ 8 MiB.
- Один сертификат в отчёте: DER ≤ 1 MiB, SHA-256 сверяется сервером.
- Очередь агента: ровно 2 последних отчёта; вытеснение старого явное.
- Логи: `current.txt`/`previous.txt` по 10 MiB, TXT, без сжатия.
